````markdown
## この作業でできるようになること

- できるようになること: （実行すると何が使える・動くようになるか）
- 実行するまでできないこと: （それまで何が止まる・使えないか）
- 急ぎ具合: （いつまでに必要か。急がないなら「急がない」）

## 前提条件

- 実行するデバイス: （手順の大半を実行する端末。サブPC / メインPC / VPS / ブラウザ のどれか1つ。SSHが要るなら接続コマンドも）
- カレントディレクトリ: （`cd`する場所。リポジトリでの作業でなければ「不要」）
- Gitブランチ: （原則`develop`。リポジトリでの作業でなければ「不要」）
- 先に完了している必要があるIssue・PR: （`#<番号>`がdevelopへマージ済み、など。無ければ「なし」）
- その他の前提: （必要な権限・トークン、起動しておくサービスなど。無ければ「なし」）

## やること

- [ ] （サブPC）1手順目。何をするかを1行で

  ```bash
  （その手順で実行するコマンド）
  ```

- [ ] （ブラウザ）2手順目

## 完了の確認方法

（実行後に何を見れば効いたと分かるか。確認用のコマンドと期待する出力、または画面のどこに
何が出ていれば完了かを書く）

## なぜエージェントが実施しないか

（権限が無い・無断で変更できない設定である、など）

## 関連

- 起点Issue: #<番号>
- 対応PR: #<番号>
````

**埋めるときに守る点。** issue-deck画面（手作業アシスタント）がこの書式を読んで手順・チップ・
代行実行を組み立てるため、崩すとその機能が黙って落ちる。

- `## 前提条件`の各項目は**1行に収める**。折り返した続きの行は項目として読まれず、値が途中で切れる
- **手順の文頭に`（サブPC）`のように端末を書く。** 書けるのは`サブPC`・`メインPC`・`VPS`・
  `ブラウザ`の4つで、書いた手順はその端末で扱われる（代行実行の可否も手順ごとに決まる）。
  「サブPCで〜する」のような散文からは読み取らないので、括弧書きで書くこと
- **「実行するデバイス」は1つだけ書く。** これは**デバイスを書かなかった手順の既定値**で、
  そのまま画面のチップにも出る。端末が複数書かれていると既定値が決まらず、デバイスを
  書いていない手順は代行実行の対象から外れる
- `## 関連`の起点Issue・対応PRは**`#<番号>`**（別リポジトリなら`owner/repo#<番号>`）で書く。
  URLで書くと前提条件の状況表示から落ちる
- **1つの手順に置くコードブロックはちょうど1つにする。** 2つ以上ある手順は「どれを実行したのか」が
  チェック1つに対応しないため、代行実行の対象から外れる
- コマンドのコードブロックは、その`- [ ]`項目の**2スペース下げ**で置く
- **人が値を埋めてから実行するコマンドは、埋める箇所を`<控えたkey>`のように`<…>`で書く。**
  プレースホルダを含む手順は代行実行の対象から外れ、「あなたが実行」として並ぶ（#2051）。
  `$HOME`のような**実在の環境変数参照は埋める箇所として扱われない**ので、値を埋めてほしい
  ところは必ず`<…>`にする
