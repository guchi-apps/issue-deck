# 無人実行の実装エージェントの参照文書（必要になったときに読む節）

いつ読むか: GitHub Actions上で無人実行されている実装エージェントが、実装プロンプト（`.github/prompts/implement.md`）の「必要になったら読むもの」に挙げた状況になったとき。

実装プロンプトには、どの実行でも毎回使う指示だけを載せている（#3024。ローカル実行と同じ整理で、[implementation-agent-reference.md](implementation-agent-reference.md)〈#3021〉の無人実行版）。ここにあるのは、一部の実行でしか使わない手順と、指示の背景にある実測値である。規則そのものはプロンプトから外したのではなく、読む時点を「必要になったとき」へ遅らせただけなので、該当する状況になったら**作業を進める前に**該当する節を読むこと。

- **この文書はプロンプトと違い、値の差し込み（`envsubst`）を通らない。** 文中の`<Issue番号>`はプロンプト冒頭の対応Issueの番号（`#<Issue番号>`）に、`<owner/repo>`はプロンプトの1行目にあるリポジトリ（`owner/repo`の形）に読み替える
- コメントを投稿するときの`<!-- issue-deck-source:claude-issue-dispatch -->`・`<!-- issue-deck-agent:implementer -->`マーカーの付与はプロンプト本文の規則のままで、この文書に書かれた形式のコメントにも同じく付ける
- `.shared-prompts/`がある実行（他リポジトリ）では`.shared-prompts/docs/multi-agent/`に、無い実行では`docs/multi-agent/`にある（`prompts-ref`で取得した共有側のチェックアウトの一部として届く。[prompts-and-models.md](prompts-and-models.md)「無人実行の実装プロンプトは毎回使う指示だけを載せる（#3024）」）

## 実装後にユーザーの手作業が残る場合
今回の変更を実際に効かせるために、あなたが代行できないユーザー自身の操作（本番サーバー上の
`.env`の書き換え、GitHub Appの権限追加、1Passwordでのトークン発行、他リポジトリへのラベル
配布、外部サービスの管理画面での設定など）が残る場合、**PR本文の「注意点」や完了報告コメントに
書くだけで終わらせないでください。** そこに書いた手順は、PRがマージされこのIssueが`Done`で
closeされた時点でどのカンバンにも残らず、やり残しとして追跡できなくなります。

**その手作業を単独の新規Issueとして起票してください。**

**ただし、VPS・サブPCの設定ファイルの変更は、手作業Issueの手順として書かないでください**（#2021）。
`/etc/apache2/sites-available/`・`/etc/systemd/system/`・`~/.config/systemd/user/`・crontab・
`/etc/fail2ban/`（VPS）、`/etc/netplan/`・`/etc/ssh/sshd_config.d/`・`~/.bashrc.local`（サブPC）
などは`guchi-apps/vps`・`guchi-apps/subpc`で管理されており、Git経由で反映できます。実機を直接
編集すると変更がGitに残らず、毎日のドリフト検知で後から差分としてだけ出てきます（対応表の正は
`guchi-apps/issue-deck`の`src/lib/infra-config-repos.ts`。**`deploy.yml`の`paths`に載っている
受け口だけ**が対象で、vpsの`mysql/`のような記録用ディレクトリは従来どおり手作業です）。

- **切り出す前に、対象リポジトリのopenなIssueを引いてください**（#2250）。同じ対象のIssueが
  既に開いていたら起票せず、そのIssueへコメントし、足りない手順があればそちらへ書き足します。
  `aide-bot`の立ち上げでは、同じ「vhostを作って公開する」作業のIssueが`guchi-apps/vps`へ4件
  立ちました。探す語は**対象の固有名**（アプリ名・ホスト名・サービス名）にします

  ```
  gh issue list --repo guchi-apps/vps --state open --search "<アプリ名・ホスト名>" --json number,title
  ```

  立ち上げが作ったIssueには本文の先頭に`<!-- new-app-launch: … -->`の印があり、**GitHubのIssue
  検索はHTMLコメントの中身も索引している**ので`--search "new-app-launch <アプリ名>"`でも引けます
- 該当する変更は**対象リポジトリへIssueを起票**して切り出す
  （`gh issue create --repo guchi-apps/vps ...`）。起点Issueのサブissueとして紐付け、PR本文と
  完了報告コメントにリンクを書く。**そのリポジトリでの実装（ファイルの変更・PR作成）は
  このセッションで行わないでください**——担当Issue以外の実装にあたります
- **無人実行（GitHub Actions）では、`guchi-apps/vps`・`guchi-apps/subpc`・`guchi-apps/docs`への
  上の2コマンドは404で失敗します**（#2908）。このステップの`gh`は、claude-code-actionがOIDC交換で
  発行した**実行中のリポジトリにスコープされたトークン**で動き、同じorgでも**privateリポジトリには
  届きません**（publicリポジトリへは届きます）。**これを「GitHub Appのインストール範囲に含まれて
  いない」と診断しないでください。** orgへのインストールは`repository_selection: all`で、範囲を
  広げる操作をしても直りません。失敗したら起票を諦めず、**起票したかった内容（対象リポジトリ・
  タイトル・本文・ラベル）を完了報告コメントへ書き切って**人へ渡します。ユーザー本人のトークンで
  動くローカルセッションからは、上のコマンドがそのまま通ります
- **実機へ出るまでのマージは2回**です。切り出したIssueのブランチが向くのは`develop`で、
  `deploy.yml`が起動するのは`main`へのpush。`develop`→`main`のリリースPRのマージは自動マージ
  不可カテゴリなので人が行います
- したがって手作業Issueは残ります。内容は実機のコマンドではなく
  「(1) 切り出したPRを`develop`へマージ (2) `develop`→`main`のリリースPRを作成・マージ
  (3) `deploy.yml`の成功を確認」の3手順にし、`## 前提条件`の「先に完了している必要がある
  Issue・PR」へ`guchi-apps/vps#<番号>`と書いて順序を残します

- **起票する前に、次のどれかに当てはまらないかを確認してください。当てはまるなら起票しません**
  （#2009。同じ内容の手作業Issueが5日で17件立ったため）
  - **issue-deck画面のボタンで実行できる操作**（サブPC上のチェックアウトの更新・再起動は、
    ホストの行に出るボタンで済む）。起票せず、PR本文の「注意点」と完了報告コメントに
    「マージ後に画面から更新して再起動する」と案内を書く
  - **同じ作業が繰り返し発生するもの**（デプロイのたび・pullのたびに必要になるもの）。
    2回目以降だと気付いたら、その作業を追跡するIssueではなく、**その作業をなくすIssue**
    （自動化する・画面の操作へ寄せる）を起票する
  - **openな同内容の手作業Issueが既にあるもの**。起票の前に必ず引いてください

    ```
    gh issue list --repo <owner/repo> --state open --label "71.manual-step" \
      --search "<やることの名詞1〜2語>" --json number,title
    ```

    見つかったら起票せず、その既存Issueへ「#<Issue番号>でも同じ作業が必要になった」と
    コメントし、完了報告コメントとPR本文にはそのIssueへのリンクを書きます。前提条件
    （対象ホスト・先に要るPR）が違うなら別の作業なので、起票して構いません

```
gh issue create --title "[手作業] <実行する場所>: <やること>" --label "71.manual-step" --body "..."
```

- タイトルは`[手作業] <実行する場所>: <やること>`の形にする
  （例: `[手作業] VPS: 本番の.envにAPI_TOKENを追加する`）
- ラベルは`71.manual-step`を付ける。**`00.check-user`は付けない**
  （手作業Issueには承認して再開させる実装フローが無く、承認ボタンの宛先が無いため）。
  **このラベルがまだ無いリポジトリでは`--label`を外して起票し、ラベルが無かった旨を
  完了報告コメントに一行残してください**（`gh label create`で勝手に作らないこと）
- 本文には次の見出しを**この順で**すべて入れる。**「やること」はコピーしてそのまま実行できるコマンド**に
  する（手順の要約ではなく実際のコマンド。GUI操作なら押す場所を順に書く）
  - `## この作業でできるようになること` / `## 前提条件` / `## やること` /
    `## 完了の確認方法` / `## なぜエージェントが実施しないか` /
    `## 関連`（起点Issue `#<Issue番号>`・対応PR）
- `## この作業でできるようになること`は**本文の先頭**に置き、次の2つを箇条書きで書く。
  **開く人は実装から日が空いた別の端末の前におり、その作業がどの機能を止めているのかを
  覚えていません。手順より先に効果と急ぎ具合が分かるようにします**
  - できるようになること（実行すると何が使える・動くようになるか）
  - 実行するまでできないこと（それまで何が止まる・使えないか。いつまでに必要かがあれば書く）
- `## やること`は、**手順が2つ以上あるなら`- [ ]`のチェックリストにする**（1手順＝1項目）。
  コマンドはその項目の下にインデントしたコードブロックで書く。チェックボックスはクリックして
  消し込めるため、実行する人が途中まで進めた記録として残る（#1486）
- **1Passwordを扱う手順に`op signin`を書かない**（#2401）。書き込みも同期も読み取りも、
  書き込み権限つきのサービスアカウント（`~/.config/issue-deck/op-writer.env`）で代行できる
  （後述の雛形の「埋めるときに守る点」に、そのまま使えるコマンドを載せてある）
- **それでも対話が要るコマンドを書く場合は、そのセッションを使う後続のコマンドと同じ
  コードブロックにまとめる**（#2025）。サインインは実行したシェルの環境変数にしか残らず、
  手順を分けると、続きを代行実行しても必ず失敗する。手作業アシスタントはその手順だけを
  「あなたが実行」として扱い、残りの手順は自動で流す
- `## 前提条件`には次を箇条書きで書く。**実行するのは別の端末の前にいる人で、どれか一つでも
  欠けると実行してよいかを判断できません**
  - 実行するデバイス（サブPC / メインPC / VPS / ブラウザ の**どれか1つ**。SSHが要るなら接続コマンドも。これは**デバイスを書かなかった手順の既定値**で、端末をまたぐ作業は各手順の文頭に`（サブPC）`のように書く）
  - カレントディレクトリ（`cd`する場所。リポジトリでの作業でなければ「不要」）
  - Gitブランチ（**原則`develop`**。本体チェックアウトがdevelopのため。`develop`を持たない
    リポジトリと、本番へデプロイ済みのコードを触る作業だけ`main`。リポジトリでの作業でなければ「不要」）
  - 先に完了している必要があるIssue・PR（例:「#1461がdevelopへマージされた後」。無ければ「なし」）
  - その他の前提（必要な権限・トークン、起動しておくサービスなど。無ければ「なし」）
- `## 完了の確認方法`には**確認用のコマンドと期待する出力、または画面のどこに何が出ていれば完了か**を
  書く（「動作を確認する」で終わらせない）
- 起票したら、起点であるこのIssueへGitHubネイティブのサブIssueとして紐付ける

  ```
  gh api repos/<owner/repo>/issues/<起票した番号> --jq .id
  gh api repos/<owner/repo>/issues/<Issue番号>/sub_issues --method POST -F sub_issue_id=<上で得たID>
  ```

- 最後の完了報告コメントとPR本文の「注意点」には、**手順そのものではなく起票したIssueへの
  リンク**を書く（手順を二重に持つと片方が古くなる）
- **あなたが実施できることを手作業Issueへ逃がさないでください。** 起票は追跡のための手段で、
  作業を人へ移す口実ではありません。目安は「権限・実行環境の都合で実施できない」か
  「Secretsや本番設定の変更にあたり、無断で行ってはいけない」かのどちらかに当てはまること
- 手作業が残らない場合は、このセクションの操作は何も行わないでください（空のIssueは作らない）

**本文の雛形。この形をそのままコピーして埋めてください。**

**埋めるときに守る点。** issue-deck画面（手作業アシスタント）がこの書式を読んで手順・チップ・
代行実行を組み立てるため、崩すとその機能が黙って落ちる。

- `## 前提条件`の各項目は**1行に収める**。折り返した続きの行は項目として読まれず、値が途中で切れる
- **手順の文頭に`（サブPC）`のように端末を書く。** 書けるのは`サブPC`・`メインPC`・`VPS`・
  `ブラウザ`の4つで、書いた手順はその端末で扱われる（代行実行の可否も手順ごとに決まる）。
  「サブPCで〜する」のような散文からは読み取らないので、括弧書きで書くこと
- **「実行するデバイス」は1つだけ書く。** これは**デバイスを書かなかった手順の既定値**で、
  そのまま画面のチップにも出る。端末が複数書かれていると既定値が決まらず、デバイスを
  書いていない手順は代行実行の対象から外れる
- `## 関連`の起点Issue・対応PRは**`#<番号>`**（別リポジトリなら`owner/repo#<番号>`）で書く。
  URLで書くと前提条件の状況表示から落ちる
- **1つの手順に置くコードブロックはちょうど1つにする。** 2つ以上ある手順は「どれを実行したのか」が
  チェック1つに対応しないため、代行実行の対象から外れる
- コマンドのコードブロックは、その`- [ ]`項目の**2スペース下げ**で置く
- **人が値を埋めてから実行するコマンドは、埋める箇所を`<控えたkey>`のように`<…>`で書く。**
  プレースホルダを含む手順は代行実行の対象から外れ、「あなたが実行」として並ぶ（#2051）。
  `$HOME`のような**実在の環境変数参照は埋める箇所として扱われない**ので、値を埋めてほしい
  ところは必ず`<…>`にする
- **1Passwordへの値の登録は、1Passwordアプリ（ブラウザ・デスクトップ）で行う手順として書く**
  （#2417）。サブPCの全シェルには`apps`ボールトへ**read権限しか無い**サービスアカウントが
  `~/.profile.local`から常時exportされており、`op`は`op signin`よりそちらを優先する。そのため
  `op item edit`・`op item create`をIssueへ書くと、代行実行でも人の実行でも
  `Couldn't update the item.`で落ちる（`op read`は通るので気付きにくい）。書くのは次の形

  ```
  - [ ] （ブラウザ）1Passwordで`apps`ボールトの`<item>`を開き、`<field>`に値を登録する
  ```

- **GitHubのsecretへの同期と本番への反映はCLIに任せる**（#1874・#2401）。`op signin`は書かない
  ——対話が要るため、書いた時点でその手順まるごとが代行実行から外れる。同期は書き込み権限つきの
  サービスアカウント（`~/.config/issue-deck/op-writer.env`）を読み込む次のコマンドで行う。
  **対象キーの行が`.github/secrets-manifest.tsv`にあること**が前提で、行を足すのは実装側の
  Pull Requestの仕事

  ```bash
  cd ~/apps/issue-deck && scripts/provision-secret.sh --repo guchi-apps/<repo> --key <KEY> --sync-only
  ```

  本番への反映を別の経路で行うなら`--no-deploy`、デプロイの完了待ちが5分の打ち切りに掛かり
  そうなら`--no-wait`を足す。organizationの共通値は`--manifest .github/org-secrets-manifest.tsv`
  を足す。**人が値を知る必要の無い機械生成の値**（ランダムなトークン等）は、そもそも手作業Issueに
  せずエージェントが`--generate hex32`で完結させる
- **`op read`だけの手順・確認にも`op signin`を書かない**（#2401）。代行実行のシェルには
  1Passwordのセッションが無いので、読むときも上と同じトークンを読み込む。`op signin`を書くと、
  読むだけの確認まで人の実行になる

  ```bash
  set -a; . ~/.config/issue-deck/op-writer.env; set +a; op read 'op://apps/<item>/<field>' >/dev/null && echo ok
  ```

- **`## 完了の確認方法`は、`## やること`の手順と1対1のコマンドで書く**（#2256）。手順を実行した
  かどうかではなく、**実行した結果が入っているか**を確かめるコマンドを、手順ぶん並べる。
  ここに置いたコマンドだけが手作業アシスタントの代行実行と定期巡回（#2008）の対象になり、
  「チェックは付いているが実施されていない」を画面から拾えるようになる（`aide-bot`の立ち上げでは
  1Passwordへの登録が未実施のままIssueがcloseされ、初回デプロイが`DB_NAME is required`で落ちた）
- **確認コマンドは、効いていなければ終了コードが0にならないものにする。** 代行実行も巡回も
  見ているのは終了コードだけで、出力と「期待する出力」の照合はしない。`--dry-run`のように
  常に0で終わるものを置くと、確かめていないのに通ったことになる
- **確認コマンドは書き換えない。** `## やること`の手順と違い、確認は人の承認なしに流れることが
  ある。読み取りだけのコマンドで書く

## ユーザー自身にコマンドを実行してもらう必要が出た場合

権限や実行環境の都合で**あなたが実行できないコマンド**（本番デプロイの`gh workflow run`、
対話的なログイン、許可リストに無い操作など）が出てきて、それを実行しないと先へ進めない場合、
**ログに書くだけで終わらせないでください**（#2002）。ワークフローのログは通知にならず、
実行が終わった時点で誰も見に来ません。

`gh issue comment`で次の3つを書いたコメントを投稿し、
`gh issue edit <Issue番号> --add-label "00.check-user" --add-label "01.check-blocked"`
を実行して停止してください（このバッチ実行は人の操作を待てないため、理由ラベルは待機を表す
`01.check-input`ではなく停止を表す`01.check-blocked`を使います）。

- **なぜあなたが実行できないか**（権限が無い・許可リストに無い・対話的な認証が要る など）
- **コピペで実行できるコマンド**（実行するデバイスとカレントディレクトリも書く。コードブロックにまとめる）
- **そのコマンドが済んだ後に何が残っているか**（実装を続けるために再実行が必要かどうかも書く）

**ブロックされたコマンドを回避しようとしないでください。** 本番へ出る操作をエージェントに
自動実行させないのは妥当な挙動です。直すべきなのは伝え方であって、ブロックそのものでは
ありません。実装がすべて済んでいて、PRのマージ後に残る手作業として渡せる場合は、この形では
なく「実装後にユーザーの手作業が残る場合」の`71.manual-step` Issueとして起票してください。

## 実装中に得た知見の記録
実装・調査の過程で、次に同じ領域を触るエージェントや人間にとって価値のある非自明な知見
（踏んだ制約、公式仕様の分かりにくい挙動、選んだ設計判断の理由など）を得た場合は、
次の2つを**両方**行ってください。

1. **このリポジトリのドキュメントへ書く。** 今回のPull Requestに同梱して`docs/`配下の適切な
   ファイル、または`CLAUDE.md`へ追記します。新規ファイルを増やす前に、既存ドキュメントへの
   追記で済まないかを先に検討してください。
2. **同じ内容を「知見メモ」コメントとしてIssueへ投稿する。**
   `gh issue comment <Issue番号> --body "..."` で下記の形式で投稿します。

**その知見を全アプリ共通の共有知識へ格上げすべきかどうかは、あなたは判定しません。**
判定は共有知識リポジトリ（`guchi-apps/docs`）側の専用エージェントが、全リポジトリの知見メモを
まとめて審査し、通ったものだけを共有知識へのPull Requestに変換します。**`.shared-context/`を
直接編集してはいけません。** あなたは「何が分かったか」と「その根拠」を正確に書くことに
集中してください。

知見メモの形式（知見が複数ある場合は`###`の見出しを知見ごとに立て、1つのコメントにまとめる。
マーカー`<!-- knowledge-candidate -->`はコメントの先頭に1つだけ）:

```
<!-- knowledge-candidate -->
### <一行で分かる結論>

- 状況: いつ・どこで問題になるか
- 結論: 何をすべきか / 何をしてはいけないか
- 根拠: 出典URL、または再現した事象と実行ログ・ファイル:行
- 確認日: <YYYY-MM-DD>
- 出典: <owner/repo>#<Issue番号>

<!-- issue-deck-source:claude-issue-dispatch -->
<!-- issue-deck-agent:implementer -->
```

- 1回の実装で残す知見は目安3件までとし、多い場合は非自明なものに絞ってください
- 残す知見が無い場合は、このコメント自体を投稿しないでください（「知見なし」の空コメントは
  不要です）
- シークレットの実値・個人情報・一時的な障害情報は、ドキュメント・知見メモのいずれにも
  記録しないでください

## 全アプリ共通の共有知識（`.shared-context/`）
ワークツリー内の`.shared-context/`に、全アプリ共通の知識リポジトリ（`guchi-apps/docs`）が
チェックアウトされています。実装の前提として、以下を必要な範囲だけ読んでください
（最初から全部読む必要はありません）。

- `.shared-context/CLAUDE.md` — 共有知識の索引・読む順序
- `.shared-context/agent-rules/implementation.md` — 実装エージェントの共通ルール
- `.shared-context/knowledge/` — 過去に他アプリ・他Issueで得た知見。今回触る領域
  （GitHub Actions・デプロイ・認証・DB等）に対応するファイルがあれば、着手前に読む
- `.shared-context/standards/coding.md` — 全アプリ共通のコーディング方針

注意事項:
- **`.shared-context/`配下は読み取り専用です。** 編集・`git add`・コミットは一切行わないで
  ください（`.gitignore`済みですが、`git add -A`等で巻き込まないよう注意してください）。
  得た知見は、後述の「実装中に得た知見の記録」に従って知見メモとして残すにとどめます
  （共有知識へ格上げするかどうかは、あなたは判定しません）。
- `.shared-context/`ディレクトリ自体が存在しない場合（checkoutに失敗した場合）は、共有知識
  なしでそのまま実装して構いません。存在しないことを理由に停止しないでください。
- 内容がこのリポジトリの`CLAUDE.md`・`docs/`と矛盾する場合は、このリポジトリ側の記述を
  優先してください（共有知識は他アプリでの既定値であり、このリポジトリ固有のルールを上書きしません）。

## 調査は往復を減らす形で行う（背景の実測値を含む全文）

実行のコストは**応答の回数**でほぼ決まります。1往復ごとにそれまでの文脈をすべて再送する
ため、往復が増えるほど1回あたりの単価も上がります（実測のAPI換算で、1セッションあたり
1〜50応答なら約2ドル、101〜200応答で約16ドル、201〜400応答で約39ドル）。直近10日の実装
セッションではツール呼び出し39,728回のうち39,686回が`Bash`で、内訳は`sed -n`が5,925回・
`grep -n`が3,424回・`grep -rn`が2,019回、1回あたりの出力は平均3KB未満でした。
**払っているのは出力の中身ではなく往復そのもの**です（#2351）。

- **ファイルを読む・探すときは`Read`・`Grep`・`Glob`を使う。** `Bash`の`sed -n`・`cat`・
  `head`・`grep -rn`・`find`で代用しないでください。`Grep`はリポジトリ全体を1回で引いて
  前後の行まで取れ、`Glob`はパターンに合うファイルを一覧でき、`Read`は読んだ範囲を
  ハーネスが覚えているため同じ場所を読み直さずに済みます。`Bash`は、これらで表現できない
  処理（`git`・`gh`・テストやLintの実行・パイプでの集計）に使ってください
- **依存の無い調査は1応答でまとめて呼ぶ。** 「3つのファイルを読む」「別々の語で2か所を
  検索する」のように前の結果を待つ必要がない呼び出しは、**1つの応答に複数のツール呼び出しを
  並べて**発行してください。前の結果で次に読む場所が決まるときだけ順に呼びます（実測では、
  ツールを呼んだ応答64,305件のうち複数を同時に呼んだものは6.9%しかありませんでした）
- **文脈が伸びた状態で粘らない。** 調べても実装の見通しが立たないまま往復が積み上がって
  きたら、**Issueが大きすぎるサイン**です。そのまま押し切っても、以降の往復すべてが膨らんだ
  文脈を運び続けるだけになります。区切りの良い範囲までを仕上げてPull Requestにし、残りは
  `gh issue create`で新しいIssueとして起票（本文に「起点: #<Issue番号>」・`70.needs-decision`
  ラベル・目安3件まで）してPR本文と完了報告からリンクしてください。区切れるところが無ければ、
  その時点で分かっている状況を`gh issue comment`で報告し、
  `gh issue edit <Issue番号> --add-label "00.check-user" --add-label "01.check-blocked"`
  を実行して止めます

## 大きいファイルの読み方

大きいファイルを丸ごと読むと、その内容が以降のやり取り全てに乗り続け、実行コストが大きく膨らみます。
目安として数万バイトを超える`.md`・`.yml`は`Read`で全体を開かず、`Grep`で該当箇所を特定してから
`Read`の`offset`・`limit`で必要な範囲だけ読んでください。特に`.github/workflows/reusable-*.yml`は
ジョブ本体を集約しているため大きく（最大のものは十万バイトを超える）、全体を開かないでください。
ファイル全体を`cat`で出力するのも同じ理由で避けます。
