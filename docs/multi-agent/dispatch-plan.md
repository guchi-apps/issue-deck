# 計画フェーズの信頼性と実装runへの引き継ぎ

`21.plan-required`が付いたIssueの計画提示ステップが確実に完了するための仕組みと、計画runの調査結果を実装runへ渡す仕組み。

索引: [Issueごとの複数Claude Codeエージェント運用 設計](../multi-agent-workflow.md)

## 計画提示ステップの信頼性確保

許可コマンドを広げても、より調査対象が広いIssueでは未許可の操作（他のBashコマンド・ツール）に
突き当たり、同様にコメント投稿まで到達できない失敗が再発する可能性は構造的に残る。これを個別の
許可コマンド追加だけで塞ぎ続けるのではなく、二段構えで対処する。

1. **プロンプト側の回避策**: 計画提示ステップのプロンプトに「調査に行き詰まった場合はそれ以上粘らず、
   分かっている範囲の情報で計画をまとめてコメント投稿を最優先する」「実装範囲が広く一度の計画に
   まとめきれない場合は、Issueの分割を計画コメントの中で提案してよい（分割作業自体はこのステップでは
   行わない）」という指示を追加した。調査を早めに切り上げさせることでターン数の消費を抑える狙い。
   ただし「何回失敗したら諦めるか」はモデルの裁量に委ねられるため、これだけでは失敗確率を下げる
   だけで、到達を保証するものではない。
2. **機械的な検証・フォールバック（本命）**: 計画提示ステップの前後でIssueのコメント数を記録・比較し、
   新規コメントが増えていなければ「計画提示ステップ実行後、コメント投稿を検証する」ステップが
   `gh issue comment`でフォールバック通知を投稿し`00.check-user`を付与する。この検証ステップは
   `gh issue view`/`gh issue comment`/`gh issue edit`のみを使う単純なシェルスクリプトであり、
   Claude Code自体の許可コマンドの問題から独立しているため、1で防ぎきれなかったケースでも
   「Issueに何も反映されないまま無言で終わる」事態を確実に防げる。
3. **設定回数までの自動リトライ（#497）**: 2のフォールバック検証ステップが「新規コメント（計画提示
   ステップ）・新規コメントとPRのいずれも（実装ステップ）が確認できない」と判断した時点で、即座に
   `00.check-user`を付けて止めるのではなく、まず全リポジトリ共通の自動リトライ上限（`GET
   /api/settings/auto-retry`から取得する`autoRetryLimit`。#496で追加した読み取り専用APIを、
   リポジトリ単位ではなくアプリ全体で共通の設定に置き換えたもの）と現在のリトライ回数を比較する。
   上限未満であれば「自動リトライします」という
   趣旨のコメントを投稿したうえで`gh workflow run claude-issue-dispatch.yml -f
   issue_number=<n> -f retry_attempt=<n+1>`で`claude-issue-dispatch.yml`自身を`workflow_dispatch`
   経由で再起動し、`00.check-user`は付与せず終了する。上限に達した場合（`autoRetryLimit`が未設定・
   API到達不可の場合は常に上限0扱いとし安全側にフォールバックする）は従来どおりのフォールバック
   通知＋`00.check-user`を行う。
   - `workflow_dispatch`による自己再起動は、`GITHUB_TOKEN`によるAPI呼び出しが新たなワークフロー
     実行を誘発しないGitHubの仕様上の制約（[docs/actions-token-model.md](../actions-token-model.md)
     参照）のため、`secrets.WORKFLOW_PAT`を使う。
   - `workflow_dispatch`トリガー自体は、`workflow_dispatch`のAPI呼び出しがリポジトリへのwrite
     権限を要求するGitHub側の仕様により、`issue_comment`向けの実行者パーミッション確認と同等の
     信頼レベルが既に担保されているとみなし、Bot判定・実行者パーミッション確認をスキップする。
   - 自動リトライ発火時のコメントには、フォールバック通知の`<!-- issue-deck-fallback-notice -->`
     マーカーを付けない（`00.check-user`も付けないため、issue-deck画面の「続きを実装・調査を依頼」
     ボタンは表示されず、UIの継続依頼導線と自動リトライが二重に走ることはない）。
   - `gh workflow run`は起動したrunのIDを返さないため、当初は「自動的に再実行します」の
     実行ログURLに（新しいrunではなく）このステップ自身が走っているrun自身のURLを使っており、
     直前に投稿した通知と実行ログURLが重複する不具合があった（#1113）。`claude-issue-dispatch.yml`
     の`run-name`を`Issue #<番号>`に固定し、`gh run list --event workflow_dispatch`をこの
     表示名で絞り込みつつ最大20秒（2秒×10回）ポーリングして新しいrunのIDを特定する方式に
     修正した。見つからない場合は従来どおり自分自身のrun URLにフォールバックする。
4. **エラー原因（一過性/恒常的）に応じたフォールバック文言・リトライ挙動の出し分け（#621）**:
   上記のフォールバック通知は、当初「ツール権限拒否等の恒常的な障害」を前提にした固定文言だったが、
   実際には計画提示・実装ステップに使う`anthropics/claude-code-action@v1`ステップ自体が、Claude
   起動前後のGitHub API呼び出し（実行者の権限チェック等、アクション内部の処理）が一時的に失敗した
   ことでステップごと`failure`終了するケースがあり（Issue #610で実際に観測: 権限チェックAPIの
   一時的な503エラー）、その場合も同じ「ツール権限拒否」文言のフォールバック通知が投稿されて
   ユーザーに誤った原因認識を与えていた。そこで、`Claude Code（計画提示）`・
   `Claude Code（実装・PR作成）`の各ステップに`id`（`claude_plan`・`claude_implement`）を付け、
   後続のフォールバック検証ステップから`steps.<id>.outcome`を参照して次のように区別する。
   - ステップの終了状態が`failure`（アクション自体がエラー終了した）→ 一過性のインフラ障害
     （`ERROR_TYPE=transient`）とみなし、「GitHub API呼び出しが一時的に失敗した可能性があり、
     再実行すれば解消する場合がある」という趣旨の文言を投稿する。
   - ステップの終了状態が`failure`以外でも、5の`execution_file`から抽出した`result`ターンの
     `subtype`が`error_max_turns`（ターン数上限に到達し、投稿前に力尽きた）の場合は
     `ERROR_TYPE=transient`とみなす（#769, #777）。Issue #769で、計画コメント投稿前にターン数
     上限へ到達したケースがステップ自体は`success`終了するため`persistent`判定になり、
     `autoRetryLimit`が0の環境では自動リトライされずユーザーの手動`@claude`コメントを待つ
     ことになっていた。ターン切れは権限拒否のような恒常的障害と異なり再実行すれば解消する
     見込みが高いため、この場合だけ例外的に`transient`側へ倒す。この判定に使う`RESULT_SUBTYPE`
     の抽出は、5で説明する理由抽出用の`jq`呼び出しとは別に、ERROR_TYPE判定の直前で先に行う
     （5の理由抽出処理は、この時点で抽出済みの`RESULT_SUBTYPE`を再利用する）。
   - 上記いずれにも該当しない場合（Claude自体は完走したが、新規コメント・PRが確認できず、
     ターン切れでもない）→ 従来どおり、ツール権限拒否等の恒常的な障害（`ERROR_TYPE=persistent`）
     とみなし、既存の文言を投稿する。`error_during_execution`（実行時エラー）はコード側の実バグに
     起因する可能性を否定できないため、今回は対象に含めず`persistent`のまま据え置く。
   - リトライ判定にも同じ区別を用いる。3の自動リトライ上限（`autoRetryLimit`）は`APP_BASE_URL`
     未設定・API到達不可の場合は常に上限0扱いになり自動リトライが働かない仕様だが、一過性障害と
     判定した場合に限り、`autoRetryLimit`が取得できない/低すぎる環境でも最低限のリトライ回数
     （ワークフロー内の`TRANSIENT_FALLBACK_RETRY_LIMIT`、現在は2回）を保証する。恒常的な障害と
     判定した場合はリトライしても解消しない可能性が高いため、この下駄は適用せず`APP_BASE_URL`
     未設定時は従来どおりリトライしない。
   - このエラー種別判定は、アクションステップ自体の終了状態という機械的に取得できる情報のみに
     基づく簡易な推定であり、HTTPステータスコード等アクション内部のエラー詳細までは判別しない
     （ジョブログからの詳細抽出はアクション実行中のログ取得の信頼性が不確かなため見送った）。
5. **`execution_file`出力からの失敗理由推定（#716）**: 上記のフォールバック通知は`ERROR_TYPE`
   （一過性/恒常的）に応じた定型文言のみで、実際にClaude Codeが何をしていて止まったのかまでは
   記録されていなかった。`anthropics/claude-code-action@v1`は`outputs.execution_file`（Claude
   Codeの実行内容をSDKのメッセージ列としてJSONファイルへ書き出したパス。ステップが`failure`
   終了した場合でもSDK内部の`catch`節で書き出し済みなら出力される）を公開しており、これを使うと
   完了報告コメントの投稿に至らず終了した場合でも、そのステップが最後に何をしていたかを事後的に
   読み取れる。これは4の「ジョブログからの詳細抽出は見送った」判断（実行中のログをリアルタイムに
   追う方式）とは前提が異なる。今回はアクションが実行後に書き出す構造化データを事後的に読む方式
   であり、信頼性の懸念が当てはまらないため別途採用した。
   - `Claude Code（計画提示）`・`Claude Code（実装・PR作成）`の各フォールバック検証ステップは、
     `steps.<id>.outputs.execution_file`を`EXECUTION_FILE`として受け取る。`jq`での抽出は2回に
     分かれている。まず`RESULT_SUBTYPE`（最後の`result`ターンの`subtype`）を、ERROR_TYPE判定の
     直前という早いタイミングで抽出する（4の`error_max_turns`判定に使うため、#777で前倒しした）。
     残りの理由テキストは、従来どおり自動リトライを使い切って諦める最終的なフォールバックコメント
     を投稿する直前に抽出する。優先順位は「先に抽出済みの`RESULT_SUBTYPE`と対になる`result`ターン
     の`result`」→「無ければ最後の`assistant`ターンのテキスト」→「どちらも無ければ理由なし」。
     `RESULT_SUBTYPE`が`error_max_turns`等の既知の値であれば、対応する日本語の定型理由を添える。
   - 抽出できた場合のみ、フォールバックコメント本文に理由セクションを追記する（改行除去・
     500文字での切り詰めのうえ`<details>`で折りたたむ）。抽出に失敗しても既存の定型フォールバック
     文言自体は従来どおり必ず投稿される（理由抽出の失敗が通知自体を壊さないようにする）。
   - `execution_file`のJSON構造は`claude-code-action`側の内部実装詳細であり、将来のマイナー
     アップデートでスキーマが変わりうる。`jq`抽出は全て`// empty`等でフォールバックする。
   - 抽出した理由（Claude自身の最終発言やSDKのエラーテキストの一部）は、Actionsのステップ
     サマリ（`show_full_output: true`で既に出力されている）よりも到達性の高いIssueコメントとして
     投稿されるため、コード片や内部パスが混ざる可能性がある。`<details>`での折りたたみ・文字数
     制限は行うが、この可視性の変化自体は許容している。
6. **サブエージェント起動によるターン打ち切りの防止・検知（#780）**: 5の`execution_file`から
   実際の失敗事例（#773で4回連続発生）を調べたところ、計画提示ステップの本体エージェントが
   `Explore`サブエージェントをバックグラウンドで起動し、その完了を待つために自作の`echo`コマンドを
   実行したあと「結果を待ちます」と述べてターンを終了していたことが判明した。無人実行には次の
   ユーザーターンが存在しないためターン終了＝セッション終了となり、調査中のサブエージェントごと
   打ち切られ、`gh issue comment`が一度も呼ばれないままフォールバックに落ちていた。最終`result`
   ターンは`stop_reason: "end_turn"`・`permission_denials`空で、クラッシュでもツール権限拒否でも
   なくモデルが自発的にターンを終えたことが確認できた。
   - **予防**: 計画提示ステップの`claude_args`に`--disallowedTools "Task,Agent"`を追加した
     （現行のClaude Codeではサブエージェント起動ツール名は`Agent`だが、`Task`は旧称でバンドル
     バージョン依存のため両方指定する）。計画提示ステップは`Read`/`Grep`/`Glob`のみで自力調査が
     成立する見込みのため、まずこのステップにのみ適用する（実装ステップはサブエージェントの
     有用性が高いため対象外とし、段階的に適用する）。
   - **検知**: サブエージェントを封じてもなお「調査が終わっていない」と判断してコメントを
     投稿せずターンを終える経路自体は残るため、4の`ERROR_TYPE`判定に`persistent_subagent`を
     追加した。`execution_file`中の各メッセージが持つSDK側のフィールド（モデルが自作した`echo`
     出力等の不確かな手がかりではない）から判定する。
     - `subagent_type`フィールドを持つメッセージが1件でもあれば、サブエージェントを起動した
       まま終了したとみなし`ERROR_TYPE=persistent_subagent`とする。この場合は決定論的な失敗
       （同じ条件で再実行しても再現する）であるため、3の自動リトライ上限設定にかかわらず
       リトライを行わずフォールバック通知に切り替える。フォールバック本文にも
       「サブエージェントの完了を待ったまま終了した」旨と、再実行しても再現する可能性が高い
       ことを明示し、再実行を促さない。
     - 上記に該当しない場合、最後の`result`ターンの`permission_denials`が非空であれば、拒否
       された実際のツール名をフォールバック本文に表示する（従来の「許可されていない操作が
       拒否される」という固定文言では、今回のように実態（権限拒否ではなくターン自発終了）と
       食い違い調査を誤誘導したため、機械的に取得できる情報がある場合はそれを優先する）。
     - いずれにも該当しない場合は、従来どおりの汎用文言にフォールバックする。
   - **原因調査の容易化**: 上記の事例究明には2900行規模の`execution_file`をログから追う必要が
     あり、Issueコメントに埋め込める分量ではなかった。フォールバック検証ステップの直前に
     `actions/upload-artifact@v4`で`execution_file`をArtifactとして保存するステップ
     （`continue-on-error: true`。保存失敗がフォールバック通知自体を止めないため）を追加し、
     保存できた場合はダウンロードURLをフォールバック本文に含める。

## 計画runの調査結果を実装runへ引き継ぐ（#909）

`21.plan-required`が付いたIssueは「計画run」と「実装run」の2回のワークフロー実行に分かれる。
GitHub Actionsのrunは毎回コンテキストが空のため、対策をしないと**実装runは計画runが行った調査を
ゼロからやり直す**。実測（#901の調査時、run 31267977826）では計画立案だけでRead 14回・grep相当
10回の調査を行っており、これがそのまま二重になっていた。

これを避けるため、計画コメントに`### 調査済みの事実`という固定の見出しで、変更対象ファイル・
確認済みの既存実装・対象外と判断した箇所を残させる（`.github/prompts/plan.md`）。実装側は
その節があれば、そこに書かれた事実の再調査をしない（`.github/prompts/implement.md`）。

運用上の歯止めを2つ入れている。

- **分量** — 計画コメント自体が実装runの読み込み対象になるため、結論のみ・ファイル一覧は目安10件
  までとしている。10件を超えるならIssueとして大きすぎるサインで、サブIssueへの分割を検討させる
- **陳腐化** — 承認までに時間が空くと、その間に他のPRがマージされて計画と実際のコードが食い違う。
  食い違う場合はコードを優先させ、その旨を完了報告コメントに残させる

節が無い場合（`21.plan-required`が付いていないIssue、`additional`モード、この仕組みの導入前の
古い計画コメント）は従来どおり実装側が自分で調査する。

効果は事前に見積もれないため、#903のJob Summaryで計画run・実装runのキャッシュ読み出しトークンを
前後比較して評価する。分量と陳腐化の兼ね合いによっては悪化する可能性もあり、その場合は戻す。
