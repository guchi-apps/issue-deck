# Issueの進捗管理とラベルによるトグル

ラベルの番号帯の設計、進捗（Project Status）の状態遷移、各種の要否トグル（計画フェーズ・プレビュー・スクリーンショット・マージ前確認）、サブIssue分割、質問セッションからのIssue起票、自動マージ可否の判定、ユーザーの手作業のIssue化。

索引: [Issueごとの複数Claude Codeエージェント運用 設計](../multi-agent-workflow.md)

## ラベルの番号帯の設計（#1702）

**ラベル名の先頭2桁は帯を表し、意味を持つのは十の位だけ。一の位は同じ帯の中での並び順でしかない。**
`30.bug`と`31.security`は同じ「不具合」の帯であり、`31`が`30`より重いとか後続だという意味は無い。

判定に番号帯を使っているコードは`src/lib/issue-status.ts`の3つの正規表現（`ATTENTION_PATTERN`・
`STATUS_STEP_PATTERN`・`NUMBER_BAND_PATTERN`）だけで、それ以外はすべて`MANUAL_STEP_LABEL`
（`src/lib/github/approval-labels.ts`）のような完全一致の定数を通る。**番号を動かすと、コードより
先にdocs・プロンプト・ワークフロー・各リポジトリのラベル定義が壊れる**ことを前提に設計を決める。

### 一覧のカードに出すラベル（#1915）

**Issue一覧のカードは、`00.`・`01.check-*`（要対応とその理由）と実装オプションのラベルを出さない**
（`isProgressLabel`・`isStartImplementationOptionLabel`。`src/components/dashboard/issue-list.tsx`の
`listCardLabels`）。前者はカード右上の`WorkflowStepBadge`が同じことを言っており、後者は
「実装を開始」ダイアログで選んだ**走らせ方**で、盤面を眺めるときの手掛かりにならない。
**実装オプションかどうかの正は`START_IMPLEMENTATION_OPTIONS`**（`src/lib/github/start-implementation.ts`）で、
番号帯の正規表現で別に判定を作らない——オプションを増やしたときに片方だけ増えて食い違う。

出さない理由はもう一つあり、**ラベル行の右端がRemote Controlを開くボタンの場所**になっている。
オプションを並べていた頃はラベル行が2行へ折り返し、置く場所が無かった。
**新しいラベルの帯を足すときは、一覧に出すかどうかもここで決める**（付いているものをすべて
見るのはIssue詳細の役割で、そちらからは除外しない）。なお`22.merge-confirm-required`・
`23.preview-required`・`24.screenshot-required`は、バッジなど他の表示に置き換えが無いため
**一覧からは読み取れなくなる**（#1915でそれを承知のうえ決めた）。

### 空き番号は詰めない

帯の中は**追加順に採番し、関連するものを後から隣へ挿せるよう間を空けておく**（`62`と`65`の
あいだが空いているのはそのため）。**空いた番号を詰め直すことはしない。** 番号を動かすことは
ラベル名を変えることであり、既に付いているIssue・docs・プロンプト・全リポジトリのラベル定義を
追随させる話になる。見た目の連番のために払うコストではない。

新しいラベルを足すときは、**性質が既存のどの帯に属するかだけを決め、番号はその帯の空きから採る**。
帯をまたぐ新設（新しい十の位を使う）は、上の表のどの行にも当てはまらないと言い切れるときに限る。

### `71.manual-step`は70番台に据え置く（#1702で確認）

`70.confirm`（実施するかが**未決**）と`71.manual-step`（やることは**決定済み**で実行者が人）は
性質が違うため、`71`を`11.local`の隣——実行状態の帯——へ移す案を検討したが、**移さないと決めた。**

移設に必要なのは、リテラル`71.manual-step`の約70か所の書き換え（コード・docs・プロンプト・
ワークフロー）、ラベル定義を持つ8リポジトリでの改名、`manual-step-label`ジョブを含む
`reusable-issue-labels.yml`の`@workflows/vN`の14リポジトリへの再配布、そして**配布が行き渡るまで
手作業Issueへラベルが自動付与されない期間**を許容すること。対して得られるのは、
`isAutoAssignableLabelName`から3行の例外を消すことだけで、割に合わない。

したがって**「自動付与の対象は30〜89番台、ただし71番台を除く」を恒久的な仕様として据え置く**
（後掲「Claudeによるラベル自動付与の対象は30〜89番台に限る（#1662）」）。除外を名前一致では
なく番号帯で行っているのは、配布先のリポジトリでラベル名が違い得るため。

### 優先度（`80.` / `89.`）は自動付与の対象に残す（#1702で確認）

優先度はバックログ全体との相対で決まる予定判断で、1件の本文だけを読むClaudeには本来決められない。
また`mergeSuggestedLabels`（`src/components/dashboard/create-issue-dialog.tsx`）は自動生成のたびに
自動付与対象のラベル選択をリセットするため、**人が先に`80.Priority: High`を選んでから「自動生成」を
押すと消える**。それでも対象に残すのは、本文へ緊急性が書かれているときに拾える利便を優先したため。
外すと自動付与の範囲が30〜70番台の連続した帯になり`71`の例外も消えるが、その整理のために
機能を削らない、という判断。

### 似た名前のラベルの使い分け

- **`40.unexpected`（種別）と`90.Close: invalid`（closeの理由）** — `40.unexpected`は「期待と違う挙動で、
  不具合か仕様かの切り分けが要る」ものに着手前から付ける種別。`90.Close: invalid`は「正しくない・
  再現しない」と結論が出てcloseするときの理由。**着手前に付けるか、closeするときに付けるかで分かれる。**
  もとは`40.invalid`という名前で`90.Close: invalid`と紛らわしかったため、#1702で改名した（実績は
  `40.`が48件に対し`90.Close: invalid`は1件で、役割が競合していたわけではなく名前だけが衝突していた）。
- **`60.chore`（その他・軽微な修正）と`61.ops`（運用基盤の整備）** — `61.ops`は他リポジトリへの
  ワークフロー配布、各アプリのマルチエージェント運用への載せ替え、サブPC・メインPCのホスト設定
  といった、**アプリの機能ではなく運用基盤を動かす作業**。#1702の時点で`60.chore`47件のうち
  約20件がこれに当たっており、「軽微」でも「その他」でもないため分けた。
  **既存Issueの付け替えは行っていない**（遡って付け替えても盤面の見え方は変わらず、通知だけが飛ぶ）
  ので、`60.chore`には過去の運用基盤Issueが残っている。今後の起票から使い分ける。

## Issueの進捗の状態遷移

**進捗はGitHub ProjectsのStatusで管理する。唯一の正はStatusで、進捗ラベルは存在しない。** #991 Phase 5（#1010）で`01.planning`〜`09.main`を廃止した。設計の一次情報源は[progress-status-architecture.md](../progress-status-architecture.md)。

マルチエージェント運用で進めるIssueは、原則として以下の順でStatusが遷移する。

1. `Ready` — 未着手
2. `Planning` — 実装エージェントが計画検討中（`21.plan-required`選択時のみ経由）
3. `Implementation` — 実装エージェントがコード実装中
4. `Develop PR` — developへPR作成・マージ中
5. `Develop` — developへマージ完了（main未反映）
6. `Release` — mainへPR作成・マージ中
7. `Done` — mainへマージ完了。この時点でissueをcloseする

`00.check-user`（ユーザーのチェックが必要）は上記のどの段階でもラベルとして併用して付与する。Status = 今どこにいるか、Label = どんな性質・条件があるか、という役割分担にしている。

`Done`を経由せずにIssueがクローズされた場合（`21.plan-required`の計画を拒否して直接クローズした場合など）、`.github/workflows/issue-labels.yml`の`cleanup-on-close`ジョブが`00.check-user`を除去する（#464）。**進捗そのものは巻き戻さない** — `Done`のIssueを人が閉じ直しただけで盤面が`Ready`へ戻るのを避けるため。

develop→mainのリリースフロー（バージョンアップコミット・PR作成）は、`.github/workflows/release-develop-to-main.yml`によりバージョンbump PR・develop→mainのPR作成までを自動化済み（Phase 6参照。release-to-mainスキルが定める手順の1〜3に相当）。ただし人間の確認なしにPRが作成されることを避けるため、起動は`workflow_dispatch`による手動実行のみとしている（developへのPRマージやscheduleでの自動起動はしない）。実際のマージ（手順4）はこれまでどおり人間が手動で行う（Phase2の`start-reviewer.sh`は`Develop`までを扱う）。上記の状態遷移自体は、`.github/workflows/issue-labels.yml`によりGitHub Actions上でイベント駆動に自動化済み（次項参照）。

### GitHub Actionsによる進捗遷移の自動化

`.github/workflows/issue-labels.yml`が、上記の状態遷移をGitHubイベント（ブランチpush・PR作成・PRマージ）をトリガーに自動的に進める。実際に行うのはissue-deckの進捗報告API（`POST /api/progress`）への報告で、Projectを書くのはissue-deckのGitHub Appだけである。

このワークフローは**トリガー定義のみ**を持ち、ジョブ本体は`.github/workflows/reusable-issue-labels.yml`（`on: workflow_call`）へ切り出してある（#940）。他リポジトリへ展開する際は、ワークフローをコピーするのではなく**issue-deck側のこの実体をタグ固定で参照する薄いcallerを置く**（[docs/cross-repo-setup-guide.md](../cross-repo-setup-guide.md)「再利用可能ワークフローの参照」を参照）。issue-deck自身はローカルパス参照で常に最新の内容を使うため、変更が最初に自分へ跳ね返るカナリアとして機能する。

呼ばれる側でも`github`コンテキストはcaller（呼び出し元リポジトリ）のものになるため、ジョブ定義は呼び出し元を意識した書き換えを必要としない（#939で実測）。

- `Planning`〜`Develop`: エージェントが自分で進捗を動かす運用は**Phase 5で廃止した**。`gh issue edit`で進捗を進める手段がもう無いため、遷移はすべてワークフローのシェルステップが担う（着手時は`reusable-issue-dispatch.yml`、PR作成・マージ時は`reusable-issue-labels.yml`）。ローカル実行の場合は`scripts/start-issue.sh`が起動時に着手（`Planning`／`Implementation`）を報告する（#1096。既に進捗が始まっているIssueには触らないため、再開時に巻き戻らない）。
- `Release`・`Done`: 対応するエージェント運用が存在しないため、Actionsが唯一の遷移手段となる。develop→mainのPRが開いている間は`Develop`のissueを`Release`へ、PRがマージされた時点で`Develop`/`Release`のissueを`Done`へ一括遷移し、あわせてissueをcloseする。**対象のissueはissue-deckの進捗問い合わせAPI（`GET /api/progress`）から引く**（Phase 4まではラベルで探していた）。

issue番号の特定は、Issue専用ブランチの命名規約`issue-<番号>`（`scripts/start-issue.sh`が作成）から行う。この規約に従わないブランチ・PRは対象外（何もしない）。

`develop-pr-opened`（`Develop PR`遷移時）・`develop-pr-merged`（`Develop`遷移時）は、進捗の報告と
同時に`gh issue comment`でIssueへ完了報告のコメントも投稿する。盤面だけでは気付きにくいため、
PRオープン・マージという確実なイベントに紐づけて通知している。

**`develop`を持たないリポジトリ（`guchi-apps/docs`）では、`main-direct-pr-opened`・
`main-direct-merged`が同じ役割を担う**（#1901。`workflows/v23`以降）。`issue-<番号>` → `main`の
PRを拾い、オープンで`Develop PR`＋`00.check-user`・`01.check-merge`、マージで`Done`＋issueのclose
まで進める。develop運用のリポジトリでは`base.ref`の条件に一致しないため発火しない。

`develop-pr-merged`は、`claude-review-develop.yml`の`auto-merge`ジョブが有効化するGitHub Auto-merge
機能による実際のマージ（必須ステータスチェック通過後にGitHub側が非同期に実行）では発火しないことが
ある（Issue #112。GITHUB_TOKEN起点のイベントは他のワークフローを起動しないというGitHub仕様の影響を
受けるため）。`auto-merge`ジョブ自体はWORKFLOW_PATでAuto-mergeを有効化するよう対応済みだが、
根本解消したか確証が持てないため、`develop-merge-sweep`ジョブが`schedule`（15分おき）・
`workflow_dispatch`をトリガーに、`Develop PR`・`Implementation`にいる全issueを走査し、対応ブランチ
（`issue-<番号>`）からのdevelop向けPRが既にマージ済みであれば`Develop`へ進める安全網を
別途設けている。走査対象はissue-deckの進捗問い合わせAPIから引くため、**issue-deckへ疎通
できない間このジョブは何も見つけられない**（ラベルという代替の判断材料はもう無い）。

`Implementation`も走査するのは、`develop-pr-opened`の進捗報告が一時的なAPI不調で失敗すると
`Develop PR`へ一度も到達せず、`Develop PR`だけを見ていた頃はどの安全網でも拾えなかったため
（#1861・#1583）。ただしマージ後の追加対応（`mode=additional`）で`Implementation`へ戻るのは
正規の遷移なので、**マージ済みPRの先端と現在のブランチの先端が一致するときだけ**進める。
`00.check-user`と理由ラベルの除去も同じ経路で行われるため、この安全網は残留ラベルの後始末も兼ねる。

#### 取り残されたコミットは見送らず人へ渡す（#1999）

先端が一致しないときに黙って見送ると、**PRのマージとほぼ同時にpushされたコミット**が
どのPRにも載らないままdevelopへ入らず、15分おきに見送られ続けるだけで誰にも伝わらない
（`guchi-apps/subscription-lists#99`で実測。本番の画面が404のまま残った）。そこで
`develop-merge-sweep`は見送る前に`compare/develop...issue-<番号>`を引き、

- developへ入っていないコミットが**無ければ**、先端が違ってもそのまま`Develop`へ進める
- **あって**、develop向けPRが開いておらず、最後のコミットから猶予時間（既定120分）が過ぎて
  いれば、`00.check-user`＋`01.check-blocked`とIssueコメントで人へ渡す

コメント末尾の`<!-- issue-deck-stranded:issue-<番号>@<SHA> -->`で冪等にしているため、同じ先端に
対して通知は1回だけで、新しいコミットがpushされれば改めて通知される。設計理由は
[progress-status-architecture.md](../progress-status-architecture.md)「PRマージとほぼ同時のpushは、
どのPRにも載らないまま取り残される」を参照。

## `00.check-user`が付く・外れるタイミング（#1417）

`00.check-user`は「ユーザーの確認・指示が要る」ことを表す唯一のラベルで、**付け外しをする実行体が
無人実行のワークフロー・issue-deckの画面・ローカルセッションのフックの3経路に分かれている**。
個々の理由はそれぞれのコードのコメントにあるが、全体を見渡せる場所が無いとどこかが欠けていても
気付けないため、ここを一覧の正とする。個別の設計理由は各項目のリンク先を参照。

### 付くタイミング

| 契機 | 無人実行（GitHub Actions） | ローカル・サブPC実行 |
| --- | --- | --- |
| エージェントがユーザーに質問した | `reusable-issue-dispatch.yml`が回答コメントの投稿後に`00.check-user`＋`00.qa-answered`を付与（#887） | `Notification / permission_prompt`フックが`POST /api/dispatch/sessions/activity`へ`checkUserRequested`を報告し、`requestSessionCheckUser`が付与（#1417） |
| 計画を提示した | 計画コメントの投稿後に付与（`.github/prompts/plan.md`） | `PreToolUse(ExitPlanMode)`フックが計画をIssueへ投稿して付与（#1342） |
| PRを作成し、自動マージされなかった | `reusable-claude-review-develop.yml`の`auto-merge`が、`risk-check`（機械的判定・`22.merge-confirm-required`・`23.preview-required`・`24.screenshot-required`）と`claude-review`（意味的判定）の結果をまとめて付与（後述「自動マージ可否の判定方法」。**判定したジョブ自身は付けない**。#1406・#2136） | 同じ（PR作成後はレビュー・統合側の担当） |
| PRを作成したが、そのリポジトリに自動マージ判定の経路が無い | `reusable-issue-labels.yml`の`develop-pr-opened`が付与（#1470。後述「判定経路を持たないリポジトリではPR作成時に付ける」） | 同じ（判定はリポジトリ単位で、起動元を問わない） |
| 開発環境のリンクを提示した | 無人実行からプレビューURLを出す経路は無い。`23.preview-required`があれば`risk-check`がPR時に付与（#813） | 提示は入力待ちになるため、質問と同じ経路で付く。プロンプトが`AskUserQuestion`で承認を尋ねるよう指示している（#1417） |
| スクリーンショットを提示した | `24.screenshot-required`があれば`risk-check`がPR時に付与（#567。撮影より前に付く） | 同上 |
| ユーザー自身にコマンドを実行してもらう必要が出た | `.github/prompts/implement.md`がコマンドを書いたコメントとあわせて`00.check-user`＋`01.check-blocked`を付与（人の操作を待てないため停止する。#2002） | `AskUserQuestion`で尋ねるため質問と同じ経路で付く（フックが`01.check-input`）。**コマンドはIssueコメントにも投稿する**（端末の表示は通知にならないため。#2002） |
| 依存関係の追加・行き詰まりで停止した | 各プロンプト（`implement.md`・`ci-fix.md`・`conflict-resolve.md`）と`reusable-claude-ci-fix.yml`が付与 | セッションが異常終了した場合は`session-escalation.ts`が付与（#1256） |
| すでに実装済み・対応不要と判断して停止した | `.github/prompts/implement.md`・`plan.md`が根拠付きの報告コメントとあわせて付与（#1601） | 端末でユーザーに確認するため、質問と同じ経路で付く（フックが`01.check-input`を付ける）。判断の根拠はIssueコメントにも残す |
| Claude Codeが起動確認（フォルダの信頼確認）で止まった | 該当なし（無人実行はセッションを持たない） | pollerの報告を受けて`escalateNotStartedSession`が付与（#1465。**フックが1つも飛ばない状態なので、ホスト側の印ではなくpollerの計器で判定する**） |
| PRマージとほぼ同時のpushでdevelopへ入らないコミットが取り残された | `reusable-issue-labels.yml`の`develop-merge-sweep`が`00.check-user`＋`01.check-blocked`を付与（#1999。後述「取り残されたコミットは見送らず人へ渡す」） | 同じ（15分おきのcronでの検知なので、コミットの起点を問わない） |

### マージを求める`00.check-user`は、実装側から付けない（#1709）

上の表のとおり、**「PRをマージしてください」（`00.check-user`＋`01.check-merge`）を付けるのは
レビュー経路だけ**で、実装エージェントは付けない。`reusable-claude-review-develop.yml`は
`wait-for-ci`ジョブでCI（`ci.yml`）の完了を待ってから`auto-merge`（両判定の反映とマージ有効化を
行うジョブ）を動かすため、この経路で付く限り「マージしてください」と言われた時点で押せる状態に
なっている（意味的判定の分も`auto-merge`が付ける。#2136）。

実装エージェントがPR作成の直後に自分で付けると、この待ちを飛び越える。#1709で実際に起きたのは
次の形で、**通知そのものが不要だった**。

1. 実装エージェントがPRを作り、その51秒後に自分で`00.check-user`＋`01.check-merge`を付けた
2. issue-deckが「確認待ち（PRのマージ）」を通知した。開くとPRは「CI実行中」で、
   「自動マージされなかった理由」も*理由の記録が見つかりませんでした*（レビューがまだ理由
   コメントを投稿していないため）
3. 10分後、レビューが「自動マージ可」と判定してマージし、ラベルも外れた

そこで実装側の各プロンプト（`.github/prompts/implement.md`・`scripts/prompts/implementation-agent.md`・
`scripts/prompts/generic-implementation-agent.md`）の禁止事項に自己付与の禁止を明記している。
作業を止めて相談するための`00.check-user`＋`01.check-blocked`は従来どおり付けてよい。

**画面の側でも、通知はCIの完了を待つ**（`src/lib/check-user-notification.ts`）。ラベルを付ける
実行体は上記のとおり複数あり、レビュー経路を持たないリポジトリでは`develop-pr-opened`が
PRのopen時点で付ける（#1470）ため、付与のタイミングを揃えきることはできない。issue-deckは
確認待ちのトースト（#852）とベル（#1614）で、理由が`merge`の確認待ちについて対応PRの`ciState`を
見て、実行中の間はトーストを保留し、ベルのバッジを「CI実行中」に落とす。判定材料はPR一覧が既に
持っている値なので、GitHub APIの消費は増えない。保留中のものは、確認待ちが解ければ表示せずに
捨てる（上の3の形）。

### ユーザーにコマンドを実行してもらうときは、Issueコメントにも書く（#2002）

エージェントが権限や実行環境の都合で実行できないコマンドに当たり、**ユーザーに実行して
もらってから作業を続けたい**ことがある。guchi-apps/myroom#167（本番デプロイの再実行）では、
auto modeのクラシファイアが`gh workflow run deploy.yml --ref main`をブロックし、実装エージェントが
端末にコマンドを出したままユーザーを待ち続けた。**端末の表示は通知にならない**ため、ユーザーが
端末を見に来るまで誰も気付かなかった。

この状況は既存のどのルールにも当てはまらなかった。作業を続けるつもりなので**中断ではなく**、
まだ終わっていないので**完了報告でもない**。`71.manual-step`はPRマージ後も残る手作業を追跡する
ためのもので、セッションの中で今すぐ実行してほしい1コマンドには重すぎる。

そこで各実装プロンプトに「ユーザー自身にコマンドを実行してもらう場合」の節を置き、**端末や
ログに出すだけで終わらせず、Issueコメントとして投稿する**ことを求めている。コメントには
「なぜエージェントが実行できないか」「コピペで実行できるコマンド」「実行後にエージェントが
何をするか」を書く。

| 経路 | ラベル | 付け方 |
| --- | --- | --- |
| ローカルセッション（`scripts/prompts/implementation-agent.md`・`generic-implementation-agent.md`） | `00.check-user`＋`01.check-input` | `AskUserQuestion`で尋ねればフックが自動で付ける（#1417）。付いていなければ手で付け、再開時に外す |
| 無人実行（`.github/prompts/implement.md`） | `00.check-user`＋`01.check-blocked` | バッチ実行は人の操作を待てず、その場で停止するため理由は「待機」ではなく「停止」 |

**ブロックされること自体は直さない。** 本番へ出る操作をエージェントに自動実行させないのは
妥当な挙動で、直すべきなのはブロックされた後の伝え方である。

### ローカルセッションで守っている約束（#1342・#1417）

- **外すのは自分で付けたときだけ。** `Stop`はturnごとに飛ぶため、無条件に外すと人が別の理由で
  付けた`00.check-user`まで落とす。付けた事実はホスト側の状態ファイル
  （`scripts/lib/session-state.sh`の`<セッション名>.check-user`）に印として残し、印があるときしか
  外しに行かない。
- **印はセッションが終わっても消さず、同じIssueの次のセッションが引き継ぐ**（#1905）。
  以前は`session_state_remove`（セッションの終了・回収）が他の状態ファイルと一緒に消していた。
  すると**入力待ちのまま終わったセッションの`00.check-user`が、誰にも外せないまま残る** —
  ラベルはGitHubに残るのに、外す権利を表す印だけがホストから消えるため。#1893では計画の
  承認待ちで終わったセッションを同じIssueで起こし直したあと、実装が終わってPRができても
  `00.check-user`が付いたままで、画面には「実行中なのに確認待ち」とだけ出ていた。
  セッション名はIssueごとに一定（`<リポジトリ名>-issue-<番号>`）なので、残した印は次の
  セッションが引き継ぎ、最初の`Stop`でラベルごと消える。
- **引き継いだ印で、他の実行体が付けた`00.check-user`は落とさない**（#1905）。印を置いた後に
  レビュー・統合が`01.check-merge`へ、無人実行が`01.check-answered`へ付け替えていることが
  あるため、外す直前にいまの理由を読み、セッション自身が付ける理由
  （`01.check-plan`・`01.check-input`・`01.check-blocked`、または理由ラベル未配布）のときだけ
  外す（`src/lib/dispatch/check-user-labels.ts`）。ラベルを読めなかったときは外す側に倒す
  （確認待ちが解けない方が、画面から見て困る）。
- **計画の承認待ちを質問への回答待ちで上書きしない**（#1905）。計画を出すと、その承認
  プロンプトで`Notification / permission_prompt`も必ず飛ぶ（#1893では9秒後）。理由を
  `01.check-input`へ落とすと画面の見出しが「計画の承認が必要です」から「質問への回答が
  必要です」へ変わり、待たれているものが読めなくなるため、`01.check-plan`が付いている間は
  付け替えない（`requestSessionCheckUser`の`keepExistingReasons`）。
- **外れるのは「答えた瞬間」で、応答終了（`Stop`）を待たない**（#1357・#1438）。承認した直後の
  `PostToolUse`が合図で、そのために計画を出した時点（`ExitPlanMode`の`PreToolUse`）で状態を
  「入力待ち」として記録しておく。記録が無いと`PostToolUse`が間引きで捨てられ、承認しても
  実装が一区切りつくまでラベルが残る。**承認と同時に外れることが、画面から見て「承認が効いた」
  ことの唯一の合図**なので、`Stop`の保険に頼らない。
- **フックの版はセッションを起こした時点で決まる。** 承認で外れるかどうかは、起動時に読まれた
  `run-issue-session.sh`・`session-notify.sh`の版に依存する（#1438で、本体の作業ツリーが古い
  ホストではフック設定に`PostToolUse`が入らず、承認しても外れなかった）。これは
  [session-notify.md](session-notify.md)「セッション側のスクリプトは`origin/develop`の同期コピー
  から走らせる」で手当てしている。
- **入力待ちではコメントを投稿しない。** 承認プロンプトや質問はturnの途中で何度も起きるもので、
  そのたびにIssueへ書くとノイズにしかならない。何を聞かれているかはRemote Controlで見る。
  計画の提示（`ExitPlanMode`）だけは本文をコメントとして残す。
- **入力待ちの間は画面の承認・修正ボタンを出さない。** `11.local`が付いている間、押しても
  コメントが残るだけで走っているセッションには届かない（`LocalSessionWaitingInputNotice`）。
  セッションが落ちていれば従来どおりボタンを出す — 画面から`00.check-user`を外す手段を残すため。
- **入力待ちでなくても、ローカルが担当している間の承認欄には「承認」「修正」を出さない**（#1903）。
  届かないのは入力待ちのときだけではない。従来はここで塗りつぶしの「承認」を主導線として出し、
  上部の帯は「回答を書いて『承認』を押すと、内容がエージェントへ渡ります」、すぐ下の案内は
  「承認してもコメントが残るだけで、走っているセッションは動きません」と正反対のことを言っていた。
  さらに「承認」が投稿する`@claude`コメントは無人実行を起こし、`11.local`が付いている以上は
  「このIssueには`11.local`が付いているため対応しません」という案内を足して終わっていた。
  ここでできることの名前に置き換える。
  - ボタンは**「コメント」「質問する」「確認待ちを外す」「取り下げ」**（`comment-thread.tsx`）。
    塗りつぶし（主導線）は案内の中の「Remote Controlで答える」だけが持つ
  - **「確認待ちを外す」は承認ではない。** `00.check-user`と理由ラベルだけを外し、`21.plan-required`は
    残す（`labelsAfterCheckUserDismissal`）。投稿するコメントに`@claude`を付けない
    （`dismissCheckUserCommentBody`）ので、無人実行は起動しない
  - **「質問する」だけは実際に答えが返る。** 読み取り専用の質問応答（`mode=ask`）は`11.local`が
    付いていても唯一許可されている経路のため
  - 上部の帯の文言も実行先を見る（`resolveCheckUserGuidance`の`localSession`）。セッションが
    終了している場合は、届かないのではなく「終了しているので復旧が要る」と言い分ける

### 理由を表す`01.check-*`ラベル（#1469・#1490）

`00.check-user`は上の7契機すべてに同じラベルが付くため、画面は理由を周辺情報から推測していた
（`isMergeApprovalPending`が進捗Status＋直近botコメントの発信元まで見ているのがその典型で、
#728のとおり進捗が一時的に巻き戻るケースを埋めるための後付け）。#1469の計画レビューで理由を
表すラベルを併用する方針を決め、#1490で実装した。

- **`00.`帯 … 人の対応が要ることを表すゲート。** `00.check-user`だけが入る
- **`01.`帯 … `00.check-user`に併用する補助ラベル。** 単独では意味を持たない

| ラベル | ユーザーがやること | エージェントの状態 | 付ける契機 |
| --- | --- | --- | --- |
| `01.check-plan` | 計画を承認する／修正を依頼する | 待機 | 計画を提示した |
| `01.check-input` | 質問・確認に答える | 待機 | 質問した／開発環境・スクリーンショットを提示した |
| `01.check-merge` | PRをマージする | 待機 | 自動マージされなかった／判定経路が無いリポジトリのPR |
| `01.check-blocked` | 続け方を指示する | **停止** | 依存追加・行き詰まり・セッション異常終了・起動確認で停止／すでに実装済みで実装不要と判断して停止 |
| `01.check-answered` | 回答を読む | **待っていない** | ユーザーの質問へエージェントが回答した（既存`00.qa-answered`のリネーム） |

- **`01.check-input`と`01.check-answered`は向きが逆で、統合しない。** 前者は「エージェントが
  質問して、ユーザーが答える番」、後者は「ユーザーが質問して、エージェントが回答済み。読むだけで
  実装は再開しない」。この違いが承認ボタンの文言の出し分け（`isQaOnlyApprovalPending` →
  `approveCommentBody`。#887）の実体になっている。
- **置換型（`00.check-user`自体を理由別に分割する）は採らない。** 全ワークフローが
  `grep -qx "00.check-user"`でゲートしており、画面の`isApprovalPending`・確認待ちビュー・
  `Issue.checkUserLabeledAt`・ローカルセッションのフックまで巻き込むため、16リポジトリの
  ラベル配布が終わるまで壊れた状態が続く。併用型には`00.qa-answered`という前例がある。
- **理由ラベルは`00.check-user`とのANDでしか読まない。** `00.check-user`が無い状態で理由ラベルが
  残っていても画面は無視する。外し忘れが誤表示にならないようにするため。
- **理由ラベルが無くても従来どおり動く。** 画面は「あればそれを使い、無ければ現行の推測へ
  フォールバック」する。既存の`gh label list | grep -qx`ガード（#975）と同じく、ラベル未配布の
  リポジトリでは付与が黙ってスキップされるだけ。
- **理由は常に1枚。** 付け替えのときは他の理由ラベルを外す。判定は
  `src/lib/github/approval-labels.ts`に寄せ、画面・API・ローカル経路はそこだけを通す。
- **外すのは`00.check-user`を外すのと同じ場所**（`labelsAfterApproval`／`labelsAfterRejection`、
  `develop-pr-merged`・`develop-merge-sweep`・`main-pr-merged`・`main-direct-merged`・`cleanup-on-close`）。
- リネームは`gh label edit "00.qa-answered" --name "01.check-answered"`（付いているIssueから
  外れずにその場で名前が変わる）。移行期間は**読む側が新旧どちらの名前も受け付ける**。
  書く側は「`01.check-answered`があればそれ、無ければ`00.qa-answered`」の順に解決する
  （どちらか片方に固定すると、配布の前後どちらかで理由が付かない期間が生まれるため）。

導入は「issue-deck側 → 無人実行ワークフロー → 各リポジトリへのラベル配布」の順に段階を分けた。
前2つは#1490で入っている。**最後のラベル配布まではどのリポジトリでも理由ラベルが付かず、
画面は従来の推測で動く。**

#### どこが何を付けるか（#1490）

| 契機 | 理由 | 付ける実行体 |
| --- | --- | --- |
| 計画を提示した | `01.check-plan` | `.github/prompts/plan.md`（無人実行）／`session-plan.ts`の`postSessionPlan`（ローカル） |
| 質問・確認の入力待ちに入った | `01.check-input` | `session-plan.ts`の`requestSessionCheckUser`（ローカル。無人実行に入力待ちは無い） |
| ユーザー自身にコマンドを実行してもらう必要が出た | `01.check-input`（ローカル）／`01.check-blocked`（無人実行） | `scripts/prompts/implementation-agent.md`・`generic-implementation-agent.md`（ローカル。実体はフックの`requestSessionCheckUser`）、`.github/prompts/implement.md`（無人実行。#2002） |
| ユーザーの質問へ回答した | `01.check-answered` | `.github/prompts/plan.md`・`implement.md`（無人実行） |
| PRが自動マージされなかった／判定経路が無い | `01.check-merge` | `reusable-claude-review-develop.yml`の`auto-merge`・`auto-merge-fallback`、`reusable-issue-labels.yml`の`develop-pr-opened`（`.github/prompts/review-develop.md`＝意味的判定は**自分では付けず**、判定マーカーを`auto-merge`へ渡す。#2136） |
| 行き詰まり・依存追加・異常終了で停止した／すでに実装済みで実装不要と判断して停止した | `01.check-blocked` | `.github/prompts/implement.md`・`plan.md`（実装済み判断。#1601）、`reusable-issue-dispatch.yml`のフォールバック3か所、`reusable-claude-ci-fix.yml`・`reusable-claude-conflict-resolve.yml`・`reusable-claude-review-develop.yml`のレビュー失敗、`reusable-release-develop-to-main.yml`、`session-escalation.ts`（ローカル） |

**未配布のリポジトリで壊れないようにする作法は、付ける側の経路で違う。**

- **ワークフロー・プロンプト（`gh`）** … `gh label list --json name --jq '.[].name' --limit 200`
  と突き合わせ、実在するものだけを`gh issue edit`へ渡す（#975と同じ）。ラベル定義が無いまま
  `--add-label`／`--remove-label`を呼ぶと`exit 1`でジョブごと落ちるため。
- **issue-deck本体（GitHub REST）** … `src/lib/dispatch/check-user-labels.ts`。付与エンドポイント
  （`POST /issues/{n}/labels`）は**存在しないラベル名を渡すとその場で作ってしまう**ので、
  `fetchRepositoryLabelNames`で定義済みか確かめてから付ける。`00.check-user`は先に単独で付け、
  理由ラベルの付与が失敗しても巻き添えにしない。

**`01.`帯は廃止済みの進捗ステップラベル（`01.planning`など）と番号の形が同じ。**
`src/lib/issue-status.ts`の`matchStatusStep`が理由ラベルを除外していないと、Issue詳細の
ラベル欄に「ステップ1/9」の進捗バーが誤って描画される。

#### `01.check-merge`の「なぜ」はコメントにしか無い（#1631）

理由ラベルが表すのは**ユーザーに何を求めているか**（＝PRをマージすること）までで、
**なぜ自動マージされなかったか**は表さない。その「なぜ」の記録は、`claude-review-develop`発の
Issueコメント（末尾に`<!-- issue-deck-source:claude-review-develop -->`）**だけ**にある。

issue-deckのIssue詳細は、マージ待ちのときこのコメントを読んでマージボタンと同じ枠の中へ理由を
出す（`src/lib/merge-check-reasons.ts`の`resolveMergeCheckReasons`と
`src/components/dashboard/merge-check-reason-notice.tsx`）。**判定をやり直しているのではなく、
既にある判定結果を読んでいるだけ。** issue-deckはPRの差分を持っていないため、パスパターンに
よるリスク判定をクライアントで再現するとワークフローの判定と食い違う表示ができてしまう。

**書き手は5つある。全員が同じ定型で書き、読む側は文面ではなく「形」を当てにする**（#2062）。

| 書き手 | いつ書くか |
| --- | --- |
| `reusable-claude-review-develop.yml`の`auto-merge` | 一次判定（パスパターン）に該当した |
| 同`claude-review-fallback` | 自動レビューが実行できなかった |
| 同`auto-merge-fallback` | 自動マージの有効化に失敗した |
| 無人実行のレビュー（`.github/prompts/review-develop.md`） | 二次判定（意味的）で該当した |
| ローカルのレビュー・統合セッション（`scripts/prompts/review-agent.md`） | 同上 |

- **定型は「⚠️ 以下の理由により、developへのマージ前にユーザーの確認が必要と判定しました。」
  → 空行 → `- `の箇条書き」。** 箇条書きには**理由だけ**を並べ、補足はその後に段落で書く。
  混ぜるとそのまま画面の理由に並ぶ（Issue #2042の自由文コメントは、1つ目が「変更内容自体は
  挙動を変えていません」という該当しない側の補足だった）
- 読み側（`resolveMergeCheckReasons`）は**定型文を全件見てから、1件も無いときだけ**自由文
  （`自動マージ不可`を含む行）へ落ちる。箇条書きは**次の見出し（`##`）の手前まで**を読む。
  この打ち切りが、レビュー本文（「### 総評」「### 気になった点」…）の箇条書きを理由として
  誤表示しないための歯止め。判定より先にマージされていた場合の文面（#1968）も定型に含む
- **Issueへ書く。** 画面が読むのはIssueコメントだけで、PRコメントに書いても理由は出ない
- **ローカルセッションは`<!-- issue-deck-source:claude-review-develop -->`と
  `<!-- issue-deck-agent:reviewer -->`を両方付ける**（前者が理由の読み取り、後者が発言者の
  表示。#1346）。読み側は`extractCommentSourceId`でsourceマーカーを直接見る——
  `resolveCommentSource`はagentマーカーを先に読むため、両方付いたコメントを弾いてしまう
- **文面や形を変えるとこの表示が黙って落ちる。** ワークフロー・プロンプトのどちらを変える
  ときも、`src/lib/merge-check-reasons.test.ts`が持つ実文面の固定値をあわせて更新する
- 一次判定の理由コメントは、そのpush開始時点で既に`00.check-user`が付いていると投稿されない
  （#594）。その場合は`22.merge-confirm-required`・`23.preview-required`・
  `24.screenshot-required`から理由を組み立て、どれも無ければ「理由の記録が見つかりません
  でした」と出す。**理由を推測で埋めない。**

#### 画面は理由ごとに「次に押すもの」まで出す（#1663）

理由ラベルの導入（#1490）で画面に出たのは、**求められている行為の名前**（「ユーザー確認待ち・
計画の承認」というバッジと、承認カードの見出し）までだった。**Remote Controlを開くのか・対応PRを
マージするのか・コメント欄の「承認」を押すのかは画面のどこにも無く**、理由と実行先の組み合わせから
毎回思い出す必要があった。#1663でここを埋めている。

- 組み立ては`src/lib/github/check-user-guidance.ts`の`resolveCheckUserGuidance`に寄せ、
  表示は`src/components/dashboard/check-user-reason-notice.tsx`が受け持つ。
  文言（説明・押すボタン・エージェントの状態）の正は上の表で、**ボタン名は画面の表記
  （「承認」「修正」「取り下げ」「マージ」「修正を依頼する」）をそのまま書く。**
- 置き場所は2か所で、**PC・スマホ共通**（どちらも同じコンポーネントを通る）。
  - Issue詳細の上部（`IssueStatusCard`）… 開いた直後に見える。承認カードはコメント欄の末尾に
    あり、この案内が無いと画面に入っていない
  - コメント欄の承認カード（`CommentThread`の`ApprovalActions`）… 押す直前に読める位置
- **行き先ボタンは1つだけ出す。** 判定は次の順で、`01.check-merge`の「なぜ」（上記#1631）は
  この案内の内側へ入れる。
  - セッションが入力待ち（`isSessionWaitingInput`）で理由が`merge`以外 … 「Remote Controlで開く」。
    画面のボタンは`11.local`の間どこにも届かないため（`LocalSessionWaitingInputNotice`と同じ理由）。
    **マージだけ例外なのは、GitHub側の操作でセッションの状態に関係なく効くため**
  - 理由が`merge` … 「対応PRへ移動」。対応PRのセクションが描かれていないIssueでは承認欄へ送る
    （押しても何も起きない移動ボタンを出さない）
  - それ以外 … 「承認欄へ移動」
- 移動先は`src/lib/check-user-focus.ts`の目印（`data-check-user-target`）で指し、着いた枠を
  一瞬ハイライトする（`globals.css`の`check-user-flash`）。**idではなくdata属性なのは、
  PC版とスマホ版が同時にDOMへ乗るため**（`md:hidden`／`hidden md:flex`によるCSSの出し分けで、
  `IssueDetail`と`MobileIssueDetail`の両方が描かれている状態が普通にある）。同じidを2つ置くと
  HTMLとして不正なうえ、先に来る非表示側が選ばれて押しても何も起きない。
- **理由ラベルが読めなければ（`checkUserReason`が`null`）案内ごと出さない。** 行き先を推測で
  決めないため。ラベル未配布のリポジトリでは従来どおりバッジと見出しだけになる。

## 画面のオプション5つの使い分け（#1317）

issue-deckの「実装を開始」ダイアログには、下記5つのラベルをアイコン付きのチップとして出している（定義は`src/lib/github/start-implementation.ts`の`START_IMPLEMENTATION_OPTIONS`）。どれも**エージェントを止める場所が違うだけ**で、迷ったら「どこで自分が見たいか」で選ぶ。

**選んだIssueをまとめて実行するとき（#1993）も、同じチップを同じ`START_IMPLEMENTATION_OPTIONS`から出す**（`bulk-dispatch-bar.tsx`）。1回選んだ条件が選んだIssueすべてに付き、出るのは**選んだIssueで共通して選べるもの**だけ（実行先がサブPC固定なので撮影は出ず、選んだIssueのリポジトリすべてに定義があるラベルだけが残る）。詳細は[subpc-dispatch.md](subpc-dispatch.md#まとめて積むときのオプションは1回だけ選ぶ1993)。

**ダイアログは上が実行先、下がオプション**（#1623）。実行先はアイコン中心のタイルを4つ横に並べ、オプションは2列のチップにしている。オプションの説明は**ONにしたものだけ**グリッドの下に出る（全部を常に出すとスマホで開始ボタンまで届かないため）。表示順は`START_IMPLEMENTATION_OPTIONS`の並びで、実装着手前に承認をもらう「計画が必要」「アーティファクトで見た目を出す」が1行目に並ぶ。

**選ぶのは実装を始めるときだけで、「新しいIssueを作成」ダイアログには出さない**（#1580）。5つのうち撮影は無人実行専用・アーティファクトはローカル実行専用で、**実行先が決まって初めて意味が決まる**ものが混ざっている。起票の時点では実行先も実施時期も未定なため、起票のたびに5項目を読ませても選びようがない。作成画面の「作成+実装開始」からも、続けて開く「実装を開始」ダイアログで選ぶ（`src/components/dashboard/create-issue-dialog.tsx`）。ラベル選択欄からも除外している（`isSelectableLabelName`）ので、作成時にこの5つが付くことはない。

| 選択肢 | ラベル | 止まる場所 | 選ぶ基準 |
|---|---|---|---|
| 計画が必要 | `21.plan-required` | 実装前 | 作り方に選択の余地がある。**新機能・改善・デザインの種別では既定でON**（後述） |
| マージ前に確認が必要 | `22.merge-confirm-required` | developへのマージ前 | 出来上がった差分を自分で読んでから入れたい |
| 開発環境を起動する | `23.preview-required` | PR作成前 | 動いている画面を触って確かめたい |
| スクリーンショットが必要 | `24.screenshot-required` | PR作成前 | **無人実行（GitHub Actions）で**画面の見た目を確認したい |
| アーティファクトで見た目を出す | `25.artifact-required` | **実装着手前** | **ローカル実行で**、作り始める前に見た目を決めたい（#1473・#1540）。**デザインの種別では既定でON**（後述） |

- **「作る前に方向を合わせる」ものと「出来上がったものを確認する」ものに割れる。** 前者が「計画が必要」（作り方）と「アーティファクトで見た目を出す」（見た目。#1540）、後者が残り3つ。バグ修正のように直す場所が決まっているIssueで計画を挟んでも、承認待ちの往復が増えるだけで判断は変わらない。
- **「開発環境を起動する」と「スクリーンショットが必要」は択一で、実行先で決まる。** サブPC実行・ローカル実行は`tailscale serve`で開発サーバーそのものをtailnetへ出せる（#1265）ため、外出先のスマホからでも実物を触れる。撮影が要るのは、ワークフロー終了と同時にdevサーバーが消える無人実行だけ（Fly.ioのプレビュー環境は#1308で廃止済み）。このため「実装を開始」ダイアログでは、**実行先にGitHub Actionsを選んでいるときだけ撮影のチップを出す**（`visibleStartImplementationOptions`）。既にラベルが付いている場合は、外せなくならないよう実行先によらず出す。
- **「アーティファクトで見た目を出す」は、撮影とちょうど逆でローカル実行専用**（#1473）。アーティファクトの公開はローカルセッションのツールで無人実行からは作れないため、実行先にGitHub Actionsを選んでいるときだけ隠す。**止まるのは実装着手前**で、`23`/`24`とは時間軸が違うため択一ではない（#1540）。`25`が効くのは**実データが無くて実画面が空になる場合**・複数案を見比べたい場合・作り始める前に見た目を固めたい場合で、**「計画が必要」と併用すると計画と見た目を1回のやり取りで承認できる**。3つの使い分けは後述の表を参照。
- **「マージ前に確認が必要」は、自動では止まらない変更を止めるためのもの。** 認証・認可、DBスキーマ・マイグレーション、本番環境の設定、GitHub Actions・デプロイ設定、Secrets・環境変数、課金・決済、大規模な依存更新は、このラベルが無くても自動レビューが常に該当と判定し、`00.check-user`を付けて自動マージを止める（「自動マージ可否の判定方法」参照）。したがってこのラベルを選ぶ意味があるのは、**そこに当てはまらないのに自分の目で通したい**場合に限られる。典型的には、影響範囲が読みにくいリファクタリング、共通コンポーネント・共通関数の書き換え、Issueの文面だけでは仕様が決まりきっていない実装、他リポジトリへ配る雛形の変更。一度きりの`00.check-user`の手動付与と違い、**PRが何度pushされても毎回止まる**のが実務上の違い。

各ラベルの詳しい挙動は以下の各節を参照する。

## 実装前の「計画フェーズ」要否をIssueラベルでトグルする

Issueによっては実装前に設計・アプローチのすり合わせ（Claude CodeのPlan mode相当）が必要だが、単純なIssueでは不要。これをIssue単位でオン/オフする。

- ラベル `21.plan-required`（新規作成予定）の有無で実装エージェントが分岐する。
  - **ラベルなし（デフォルト）**: 実装エージェントはそのまま実装に入る。
  - **ラベルあり**: 実装エージェントは実装前に計画（アプローチ・変更範囲・懸念点）をまとめて提示し、承認を得てから実装に入る。
- **チップの初期値はIssueの種別ラベルから決める**（#1317・`planRequiredDefaultForLabels`）。`50.feature`・`51.improvement`・`62.design`が付いていれば既定でON、それ以外（`30.bug`・`60.chore`・`65.docs`や種別未選択）は従来どおりOFF。判定は「実装を開始」ダイアログを開いた時点のIssueのラベルに対して行う（`startImplementationOptionsFromLabels`）ため、**起票時に`21.plan-required`を付けておく必要は無い**（#1580）。**あくまで初期値で、自分で押した後は上書きしない。**
  - 「実装を開始」ダイアログを通らない起動経路（カンバンのドラッグ・一括投入バー）では、この既定は効かない。ドラッグは`Ready`→`Planning`へ落とせば計画になり、そのときWebhook側が`21.plan-required`を付ける（`src/app/api/webhooks/github/route.ts`）。一括投入バー（「まとめて実行」）はオプションを選べるが、**種別ラベルからの既定は当てない**（#1993。Issueごとに違うため、押したものだけが付く）。
  - 既定を変えたいときは`START_IMPLEMENTATION_OPTIONS`と同じファイルの`PLAN_REQUIRED_DEFAULT_TYPE_LABELS`に種別ラベル名を足し引きする。判定はラベル名の完全一致で、他リポジトリの種別ラベルが同じ命名でなければ既定はOFFのまま（誤って計画ゲートを掛けるより、掛からない方が軽い）。
- 「承認待ち」を表す専用ラベル `00.check-user`（ユーザーの確認・指示が必要）を計画承認待ちの合図としても使う。
- 実行形態による承認方法の違い:
  - **ローカル実行（人間が横にいる）**: Claude Code本来のPlan mode（`EnterPlanMode`→提示→`ExitPlanMode`で承認）がそのまま使える。起動スクリプトは「`21.plan-required`が付いているので実装前に必ずPlan modeで計画提示すること」という一文をプロンプトに含めるだけでよい。
  - **GitHub Actions実行（無人）**: 対話的な承認者がその場にいないため二段階に分ける。①エージェントが計画をPRドラフト or Issueコメントとして投稿し`00.check-user`を付与して停止 → ②人間がコメント/ラベル操作で承認 → ③再起動されたエージェントが実装を再開する。②→③の具体的な再起動トリガーはPhase5で確定した（`00.check-user`ラベルを人間が外すことを承認とみなす。詳細は「Phase 5」節を参照）。

## 実装範囲が広いIssueをサブIssueに分割する（GitHub Actions実行のみ）

大きなIssueをそのまま単一のGitHub Actionsジョブに渡すと、実装が長時間化して適切に処理しきれない懸念がある（issue #144）。これを避けるため、`21.plan-required`の計画提示ステップ（上記）に、実装範囲が広いと判断した場合はサブIssueへの分割を提案する仕組みを組み込んでいる。

- 計画提示ステップは、計画コメントの末尾に判断結果を示すマーカー（`<!-- issue-deck-plan-type:implement -->` または `<!-- issue-deck-plan-type:split -->`）を必ず埋め込む。分割を提案する場合は、計画コメント本文に分割後の各サブIssue案（タイトル・スコープ・依存関係）を明記する。
- 人間が計画を確認し`00.check-user`を外す（＝承認）と、別のワークフロー実行がこのマーカーを読み取り、`implement`（そのまま実装）または`split`（サブIssue作成）に自動的に分岐する。
- `split`の場合、計画コメントの分割案に沿って`gh issue create`でサブIssueを実際に作成し（本文に「分割元: #<元Issue番号>」を含め、単独で着手できる情報を持たせる）、元IssueにサブIssue一覧をコメントしたうえで、元Issueを`not planned`理由でクローズする。
- サブIssueへの実際の着手（`@claude`コメントによる起動）は自動連鎖させず、これまでどおり人間が個別に行う。分割はあくまで「大きな作業を、無人実行で扱える単位に事前に切り分ける」ところまでを自動化するもので、着手の判断は人間に残す。
- クローズ済みのIssueに対する`@claude`コメントやラベル操作では、計画・実装・分割のいずれも再始動しない（分割で元Issueがクローズされた後の誤爆防止。通常の本番反映（`Done`）によるクローズ後のIssueにも同様に適用される）。

ローカル実行（`scripts/start-issue.sh`）では、分割の判断・提案自体はPlan mode内で人間に提示できるが、実際のサブIssue作成や元Issueのクローズを自動化する仕組みは今のところ用意していない（人間が`gh issue create`等で手動対応する）。

### 親子関係の正はGitHubネイティブのサブIssue（#1246）

分割で作ったIssueも、手で切り出したIssueも、**GitHubネイティブのサブIssueとして親へ紐付ける**。

```bash
# 子の数値ID（URLに出るIssue番号ではない）を取り、それを親へ紐付ける
CHILD_ID=$(gh api repos/guchi-apps/issue-deck/issues/<子の番号> --jq .id)
gh api repos/guchi-apps/issue-deck/issues/<親の番号>/sub_issues --method POST -F sub_issue_id="$CHILD_ID"
# 外すとき
gh api repos/guchi-apps/issue-deck/issues/<親の番号>/sub_issue --method DELETE -F sub_issue_id="$CHILD_ID"
```

本文に書く「分割元: #番号」「親: #番号」といったテキストは、**人が読む補助でしかない**。
機械的な集計はネイティブの関係だけを見る。テキストは表記が既に3種類に割れており（`親: #N（子A）`・
`分割元: #N`・フェーズ表の`#N`）、本文編集でも壊れるため、正として使えない。

紐付けておくと次の2つが同時に成立する。

- **GitHub.com側**: 親Issueと一覧にネイティブの進捗バーが出る
- **issue-deck側**: Issue詳細に「子Issue」セクションが出て、**Project Statusごとの内訳**が見える
  （`未着手 1 / 実装中 2 / 本番反映済 3`）。ネイティブの集計はclose済み件数しか数えないため、
  残りが未着手なのか実装中なのかまでは分からない。判定は`src/lib/sub-issue-progress.ts`で、
  **closeされた子はStatusが何であってもdone**として数える（`not planned`でのcloseも「もう残っていない」ため）

親子関係はDBへキャッシュせず、Issue詳細を開いたときだけ`GET /api/issues/sub-issues`が取りに行く
（[../code-map.md](../code-map.md)「データの流れ」）。一覧にはバッジを出していない（Issueごとに
1クエリ増えてN+1になるため）。

分割とは別に、計画提示ステップは調査中に見つかった元Issueのスコープ外の関連事項（追加対応すべき別件・副作用や懸念点など）を、承認フローを経ずにその場で新規Issueとして起票してよい（元Issue自体の実装承認とは独立。#735）。分割が「元Issueのスコープを割る」ものであるのに対し、これは「元Issueとは別の関連事項を独立Issueとして提案する」もので、本文に「起点: #<元Issue番号>」を含め、`70.confirm`ラベルを付与したうえで1回あたり目安3件までに留める。

## 質問セッションは実装しないが、Issueの起票はしてよい

**質問セッションでも新規Issueの起票だけは認める**（#1528）。対象は無人実行の質問応答（`mode=ask`）と、
ローカルの横断質問セッション（[subpc-dispatch.md](subpc-dispatch.md)）の両方。

質問セッションは実装を行わない。しかし、答えた結果「これは対応が必要だ」と分かったことを回答
コメントに書くだけで終わらせると、**どのカンバンにも残らず追跡できなくなる**。実装しないことと、
やるべきことを残せないことは別なので、起票だけを切り出して認める。

ルールは上記の計画提示ステップからの起票（#735）と同じにしてある。

- 本文に「起点: #<質問Issue番号>」を含め、質問Issueを読み返さなくても単独で伝わるように書く
- `70.confirm`を付ける（人が着手要否を判断するまで実装フローへ自動で乗せない）
- 1回あたり目安3件まで。超える分は回答コメントに箇条書きで残す
- 起票したら回答コメント本文にも番号の一覧を書く
- **起票してもそのセッションでは実装しない**（実装は別セッションを起こす）

質問セッションだけの追加事項は2つ。

- **既存Issueのラベル・状態は変更しない。** 許可ツールにも`gh issue edit`・`gh issue close`を
  含めていない（[dispatch.md](dispatch.md)「無人実行時の権限モード（許可ツールリスト）」）。
  質問された側のIssueの進行を、質問への回答が動かしてしまわないようにするため
- **横断質問セッションでは起票先が質問Issueの記録先リポジトリとは限らない。**
  `gh issue create --repo <owner/repo>`で起票先を明示させる

## 開発環境プレビュー要否をIssueラベルでトグルする

開発サーバー（`pnpm dev`）のポート割り当て自体はコストがないため、ラベルの有無に関わらず常に`.env.local`に`PORT=4000 + Issue番号`を設定する。ラベルは「画面確認をPR作成前の承認ゲートにするかどうか」を制御する。

- ラベル `23.preview-required` の有無で`start-issue.sh`が生成するプロンプトの文言が分岐する。
  - **ラベルなし（デフォルト）**: 実装エージェントは、画面に関わる変更を行った場合PR本文の「確認方法」に開発サーバーのURL（`http://localhost:<ポート>`）とアクセス手順を記載するだけで、承認待ちなしにそのままPR作成まで進める。
  - **ラベルあり**: PRを作成する**前**に、実際に開発サーバーを起動してURLをユーザーに提示し、画面を確認してもらったうえで明示的な承認を得てからPRを作成する（`21.plan-required`と同様の承認ゲート）。
- 承認の得方は実行形態により異なる。
  - **サブPC実行**: ラベルが付いているセッションだけ開発サーバーを起動し、`tailscale serve`で
    tailnetへ出す（#1265）。**提示するURLは`localhost`ではなく`http://<ホスト名>.<tailnet>.ts.net:<ポート>`**
    （主な用途が外出先のスマホで、`localhost`では届かない）。URLはプロンプト・Signalyの通知・
    issue-deckのIssue詳細の3か所に出る。詳細は[local-quick-start.md](local-quick-start.md)
    「Tailscale経由でスマホから画面を見る」
  - **ローカル実行**: 実際に到達可能な開発サーバーが起動しているため、`21.plan-required`と同じ考え方で
    PRを作成する**前**に提示・応答待ちのゲートとして機能する。提示後にそのまま応答を止めて、
    ユーザーからの返信（承認）を待つ。
  - **GitHub Actions実行（無人）**: ワークフロー終了と同時にdevサーバーも消えるため、実装エージェント
    自身が確認物を用意することはできない。この制約により、以前はPR作成自体をブロックして
    `00.check-user`を付与し停止していたが、`24.screenshot-required`と同様の理由（確認ゲートをPR作成前
    ではなくdevelopへのマージ前に移す）で#813にてPR作成をブロックしない方式に変更した。一時期は#832でFly.io Machines上のプレビュー環境（#826・#830・#831）へ接続し、
    無人実行から実際に開けるプレビューURLを通知していたが、#1265でサブPC上のローカルセッションが
    `tailscale serve`でtailnetへ開発環境を出す方式へ移行したため、Fly.io側は#1308で廃止した。
    現在は無人実行からプレビューURLを発行する経路は無い。developへの
    マージ前確認は後述の「developへのマージ前確認要否をIssueラベルでトグルする」の`risk-check`
    ジョブがゲートする。

## スクリーンショット取得要否をIssueラベルでトグルする

グローバルCLAUDE.mdの方針（Playwright等のブラウザ自動操作はトークン消費が大きいため明示指示がある場合のみ実施）に合わせ、実装エージェントによるスクリーンショットの自動取得はデフォルトで行わない。視覚的な確認と承認をPR作成前のゲートにしたいIssueにはラベルで個別に有効化する。

**このラベルは無人実行（GitHub Actions）専用と考えてよい**（#1317）。サブPC実行・ローカル実行では`tailscale serve`で開発サーバーそのものをスマホから開けるため（#1265）、撮影しても実物を触るより得られるものは少ない。「実装を開始」ダイアログも、実行先にGitHub Actionsを選んでいるときだけこのチップを出す（既にラベルが付いている場合は、外せなくならないよう実行先によらず出す）。

- ラベル `24.screenshot-required` の有無で分岐する。
  - **ラベルなし（デフォルト）**: スクリーンショットの自動取得は行わない。
  - **ラベルあり**: PRを作成する**前**に、実装エージェントが`run`スキル等を使って開発サーバー上で変更箇所のスクリーンショットを取得してユーザーに提示し、明示的な承認を得てからPRを作成する（承認の得方は上記`23.preview-required`と同じ）。Playwright等の新規依存関係の追加が必要な場合は、追加前に必ずユーザーに確認する（依存関係の追加はCLAUDE.mdの方針により無断で行えないため）。

## 見た目のアーティファクト要否をIssueラベルでトグルする（#1473・#1540）

Claude Codeのアーティファクト（claude.aiにホストされる自己完結HTMLのページ）で、これから作る画面の
見た目を出す。**出すのは実装着手前で、承認を得てからコードを書き始める**（#1540）。
**開発サーバーのURLと違い、セッションが終了した後も残る**のも効きどころで、issue-deckの画面に出る
`previewUrl`はセッションが`ALIVE`の間しか表示されない（`src/lib/dispatch/issue-session.ts`）ため、
後から見返せる形で見た目を残せる。

**このラベルはローカル実行専用**（`24.screenshot-required`のちょうど逆）。アーティファクトの公開は
ローカルセッションのツールで、無人実行（GitHub Actions）からは作れない。「実装を開始」ダイアログは
**実行先にGitHub Actions以外を選んでいるときだけ**このチップを出す（既にラベルが付いている
場合は、外せなくならないよう実行先によらず出す。`visibleStartImplementationOptions`）。

- ラベル `25.artifact-required` の有無で分岐する。
  - **ラベルなし（デフォルト）**: アーティファクトは作らない。
  - **ラベルあり**: コードを書き始める前に見た目をアーティファクトとして公開し、URLを提示して
    見た目の承認を得てから実装に入る。
- **チップの初期値はIssueの種別ラベルから決める**（#1956・`artifactRequiredDefaultForLabels`）。
  `62.design`が付いていれば既定でONで、それ以外の種別（未選択も含む）はOFF。判定は
  「実装を開始」ダイアログを開いた時点のラベルに対して行う（`startImplementationOptionsFromLabels`）
  ため、**起票時に`25.artifact-required`を付けておく必要は無い**。**あくまで初期値で、
  自分で押した後は上書きしない。** `21.plan-required`の既定（`62.design`を含む）と重なるので、
  デザインのIssueは計画とアーティファクトの2つにチェックが入った状態で開き、上述の「併用するのが
  基本形」がそのまま既定になる。
  - 対象は`62.design`だけにしている。このラベルの効きどころは見た目そのものが成果物になるIssueで、
    画面を触らない`50.feature`・`51.improvement`まで広げると外す手間の方が増える。既定を変えたいときは
    `START_IMPLEMENTATION_OPTIONS`と同じファイルの`ARTIFACT_REQUIRED_DEFAULT_TYPE_LABELS`を足し引きする。
  - **そのリポジトリに`25.artifact-required`が定義されていることも既定ONの条件**（#1956）。
    ラベルの付与エンドポイントは存在しないラベル名を渡すと**その場で作ってしまう**
    （`fetchRepositoryLabelNames`の注記・#1490）ため、条件を付けないと`62.design`だけがある
    リポジトリで、色も説明も無いラベルが押した覚えのないまま増える。ダイアログは開いている間だけ
    `/api/issues/meta`でラベル一覧を取り（`useIssueRepoMeta`）、届いた時点で既定を当てる。
    **未取得のうちは当てない**（付け損ねる方が、配っていないラベルを作るより軽い）。
    手で押した場合は従来どおり付くので、これは既定が勝手にONになる経路だけのガード。
  - **実行先にGitHub Actionsを選んだ場合も、既定でONになったチップは出たまま**になる
    （`visibleStartImplementationOptions`は「ONなら実行先によらず出す」ため）。無人実行では
    アーティファクトを作れないので、Actionsで走らせるデザインIssueはここで外す。
    既定の実行先は**ローカル起動の対象表にあるリポジトリならサブPC、無ければGitHub Actions**で
    （`resolveDefaultDispatchHost`が`null`を返すとActionsへ落ちる）、ホストがオフライン・
    実行中のジョブがある場合もActionsへ落ちる。実行先に応じて既定を切り替える作りにはしていない
    ——上のラベル定義の条件で「配っていないリポジトリに勝手に作る」方は塞がっており、残るのは
    読まれないラベルが1枚付くだけで、外す導線は画面に出ているため。
  - ダイアログを通らない起動経路（カンバンのドラッグ・一括投入バー）ではこの既定は効かない。一括投入バーで手で押したときは付く（#1993。ただし**そのリポジトリにラベルが定義されていない場合はチップ自体を出さない**）。
- **タイミングは「実装着手前」で、PR作成前ではない**（#1540）。実装・テストが済んでから見せる形だと、
  見た目がNGだったときに実装がまるごとやり直しになる。アーティファクトの効きどころは
  **作る前に見た目を合意すること**なので、承認ゲートを前倒しした。出来上がった画面の確認は
  `23.preview-required`（実物）が受け持つ。
- **`21.plan-required`と併用するのが基本形。** 併用時は**Plan modeに入る前に**公開し、URLを計画本文へ
  含める（Plan modeではファイルを書けず、アーティファクトを作れない）。計画と見た目を1回の
  やり取りで承認でき、承認済みの計画コメントにURLが残るのでIssue側の記録にもなる。
  `21`が付いていない場合はアーティファクトの提示そのものが承認ゲートで、承認可否は
  `AskUserQuestion`で尋ね（#1417）、URLはIssueコメントにも残す。
  - **計画のやり取りで見た目の直しを求められても、Plan modeの中では差し替えられない**（#1745）。
    Plan modeで書けるのは計画ファイルだけで、アーティファクトのHTMLは書けないため、
    公開済みのURLは古い見た目のまま残る。**計画本文に「公開済みの版は修正前であること」と
    反映する内容を書いて承認を取り、承認直後・コードを書く前に同じURLへ差し替える**のが順序。
    再公開はファイルのパスを変えなければ同じURLになるので、計画コメントに残ったリンクは
    そのまま新しい見た目を指す。見た目の直しだけを再承認させるゲートは足さない
    （承認の往復が2回になるうえ、直す内容は計画に書いてあるため判断材料が増えない）。
  - **この手順はこのドキュメントではなく、プロンプト（`{{ARTIFACT_INSTRUCTIONS}}`）の側に
    書いて初めて届く**（#2110）。汎用ランチャー（`generic-start-issue.sh`）で起動した
    他リポジトリのworktreeからissue-deckの`docs/`は読めず、実際にguchi-apps/myroom#109で
    手順が届かないまま「古いURLの計画を承認させるか、Plan modeを抜けるか」の二択で止まった。
    アーティファクトの運用を決めたときは、3か所のプロンプト文面（`build-implementation-prompt.ts`・
    `start-issue.sh`・`generic-start-issue.sh`）へ必ず写す。
  - **計画本文にURLを載せるときは、差し替えがあり得ることも一緒に書く。** 定型文は
    `アーティファクト: <URL>（計画のやり取りで見た目が変わった場合は、承認後・コードを書く前に
    同じURLへ差し替えます）`。断りが無いと、承認済みの計画コメントに古い版のURLだけが残る。
- **画面デザインはPC・スマホの2画面を並べて出す**（#1632）。1つのアーティファクトの中に、
  PC（デスクトップ幅）と**スマホ（iPhone 15 = 幅393px × 高さ852px）**の両方を並べる。
  issue-deckは外出先のスマホから使う場面が多く、PCの見た目だけを承認しても、
  スマホ幅での崩れは実装後の実画面で初めて分かる。それでは「作る前に見た目を合意する」という
  このラベルの効きどころが半分失われる。どちらか一方だけにする場合は理由をアーティファクト本文に書く。
  **この原則はラベルの有無によらない**ため、`25.artifact-required`が付いていないときの文面
  （「作成は不要です」）にも、それでもデザインを出す場合の但し書きとして同じ指示を入れている。
- **アーティファクトは実装前の見た目案であって実物ではない。** 承認の意味は「この見た目で作ってよい」
  までで、実装が正しいことの確認にはならない。実装後の見た目は開発サーバーの実画面で確かめる。
  この但し書きはプロンプト（`{{ARTIFACT_INSTRUCTIONS}}`）とアーティファクト本文の先頭の両方に置いている。
- **公開したアーティファクトはissue-deckの画面の中で開ける**（#2154）。公開した時点で
  `PostToolUse(Artifact)`のフックがHTMLの原本をissue-deckへ送り、Issue詳細の
  「アーティファクト」セクションと、計画コメントなどに載ったclaude.aiリンクの両方から、
  **claude.aiへ遷移せずに**その場で開ける（claude.aiのページは`frame-ancestors 'self'`で
  iframeに入らないため、URLではなく中身を運んでいる。仕組みは
  [session-notify.md](session-notify.md)「公開したアーティファクトはissue-deckへ取り込む」）。
  - **出るのは近似**で、claude.aiが足しているmermaidの描画とランタイム機能は再現しない。
    そこまで確かめたいときは各カードの「claude.aiで開く」から本物を開く
  - **取り込めるのは今後公開する分だけ。** 過去に公開したものは原本が手元に残っていないため、
    画面には出ない（claude.aiのURLからは従来どおり見られる）
  - 計画本文へURLを載せる運用（上の定型文）は変えない。**リンクの見た目は同じまま、
    押したときの行き先だけがアプリ内へ変わる**（修飾キー付きのクリックは従来どおりclaude.ai）
- **PR本文にはURLを貼らない**（#1540）。実装後の姿とは限らないものをPRの「確認方法」に置くと、
  レビューする側が実物と取り違える。記録はIssue側（計画コメント・提示時のコメント）に残す。
  `POST /api/dispatch/sessions/activity`の`previewUrl`も拡張していない（コード変更なしで
  記録がIssueに残るため）。
- `risk-check`（`reusable-issue-dispatch.yml`）には足していない。無人実行では作れず、ローカルの
  承認ゲートはプロンプトで完結するため。

### `23` / `24` / `25` の使い分け

| | `23.preview-required` | `24.screenshot-required` | `25.artifact-required` |
| --- | --- | --- | --- |
| 止まる場所 | PR作成前 | PR作成前 | **実装着手前** |
| 使える実行先 | ローカル・サブPC実行 | 無人実行（GitHub Actions） | ローカル・サブPC実行 |
| 見せるもの | 動いている実物 | 実画面の静止画 | 手で書いた見た目案HTML |
| 忠実度 | 実物そのもの | 実物そのもの | 近似（実装とずれ得る） |
| 操作できるか | できる | できない | 限定的（自己完結HTMLの範囲） |
| セッション終了後 | 消える | Issueに残る | 残る（claude.ai） |
| コスト | 低（起動済み） | 高（Playwright） | 低 |

**`25`と`23`/`24`は競合しない。時間軸が違う**（#1540）。`25`は「作る前に見た目を決める」ためのもので、
`23`/`24`は「出来上がったものを確かめる」ためのもの。見た目を決めてから作り、出来たものを実物で
確認したいなら`21`＋`25`＋`23`を同時に付けてよい。

**出来上がったものを見るなら`23`が最良。** `25`が効くのは、実データが無くて実画面が空になる場合や、
複数案を並べて見比べたい場合、実装を始める前に見た目を固めたい場合。

## developへのマージ前確認要否をIssueラベルでトグルする（#366）

「自動マージ可否の判定方法」（後述）は、変更内容（パスパターン・依存関係の変更内容）に基づく
機械的・意味的判定のみで自動マージ可否を決めており、Issue単位で「この変更は内容によらず必ず
人間の確認を経てからマージしたい」と明示的に指定する手段が無かった。これをIssueラベルで
トグルできるようにする。

**いつ選ぶか**（#1317）。認証・認可、DBスキーマ・マイグレーション、本番環境の設定、GitHub Actions・
デプロイ設定、Secrets・環境変数、課金・決済、大規模な依存更新は、このラベルが無くても機械的判定が
止める。**選ぶ意味があるのは、そのどれにも当てはまらないのに自分の目で通したい変更**（影響範囲が
読みにくいリファクタリング、共通コンポーネント・共通関数の書き換え、Issueの文面だけでは仕様が
決まりきっていない実装、他リポジトリへ配る雛形の変更など）に限られる。

- ラベル `22.merge-confirm-required` の有無で分岐する。
  - **ラベルなし（デフォルト）**: 従来どおり、`risk-check`（機械的判定）・`claude-review`
    （意味的判定）の結果のみで自動マージ可否を判断する。
  - **ラベルあり**: 対応Issueに付いている限り、develop向けPRへのpushのたびに`risk-check`
    ジョブが判定し、変更内容によらず常に該当扱いにして自動マージをスキップする
    （`00.check-user`を実際に付けるのは`auto-merge`ジョブ。詳細は「自動マージ可否の判定方法」参照）。他の`21.plan-required`等と異なり、実装
    エージェントの挙動（Plan mode・画面確認等）を分岐させるものではなく、レビュー・統合側の
    自動マージ判定にのみ影響する。
  - `24.screenshot-required`が付いている場合も同様に`risk-check`ジョブが常に該当と判定する
    （#567）。無人実行では撮影自体は完結できてもスクリーンショットの内容を人間が
    確認する前にdevelopへマージされてしまう問題があったため、`22.merge-confirm-required`と
    同じ仕組みに乗せている。詳細は「自動マージ可否の判定方法」・Phase7参照。
    このコメントはPR作成・push直後（実装エージェントがスクリーンショットを撮影する前）に
    自動投稿されるため、投稿時点ではスクリーンショットがまだ添付されていない。ユーザーが
    このコメントだけを見てスクリーンショット未添付だと誤解し、再度添付を催促してしまう
    事象が起きたため（#859）、コメント文言自体に「撮影完了後に別コメントとして画像が
    追加投稿される」旨を明記した（#862）。
  - `23.preview-required`が付いている場合も同様に`risk-check`ジョブが常に該当と判定する
    （#813）。無人実行ではPR作成前にプレビュー画面を提示できないため、確認ゲートを
    develop向けPRのマージ前に移した（詳細は「開発環境プレビュー要否をIssueラベルでトグルする」参照）。
  - 一度きりの`00.check-user`の手動付与と異なり、PRが複数回pushされる場合（追加修正・
    コンフリクト解消の自動push等）でも、そのPRが存在する間はIssueにラベルを付けたままにして
    おけば毎回のpushで確実に確認ゲートがかかる。
  - 「実装を開始」ダイアログのオプション（`src/lib/github/start-implementation.ts`の
    `START_IMPLEMENTATION_OPTIONS`）にも「マージ前に確認が必要」として追加済みで、`21.plan-required`
    等と同様にダイアログから選択して付与できる（#366）。

## Claude Reviewの実行要否を`risk-check`でゲートする（#992）

`claude-review`ジョブ（Claude Codeによる意味的レビュー）は、当初はdevelop向けPRの作成・更新の
たびに無条件で実行していた。しかし実際のdevelop向けPRは2〜5ファイル・数十〜200行程度の小規模で
低リスクな変更が大半を占めており（本Issue検討時点の直近18件では14件・約78%がパスパターンに
一切該当しない小規模変更だった）、そのすべてにClaude Codeの実行コストをかけるのは費用対効果が
低い。そこで`risk-check`ジョブが`needs-review`出力を返し、`claude-review`はそれが`true`のときだけ
実行する形に変更した。

`needs-review`が`true`になる条件は以下のいずれかを満たす場合。

| 条件 | 理由 |
|---|---|
| 一次判定（機械的リスク判定）に該当した | 変更内容そのものがリスクカテゴリに触れている。人間が確認する際の判断材料としてレビュー結果が要る |
| 差分が大きい（10ファイル以上 **または** 500行以上） | 複数領域にまたがる変更は、パスパターンに引っかからなくても影響範囲の読解が要る |
| 対応Issueに既に`00.check-user`が付いている | ユーザーが確認待ちの状態であり、判断材料としてレビュー結果が役立つ |
| 対応Issue番号を特定できない（ブランチ名が`issue-<番号>`規約外） | この場合`auto-merge`自体もスキップされる。安全側に倒してレビューを実行する |

差分規模の算出では`pnpm-lock.yaml`・`package-lock.json`をファイル数・行数の双方から除外する。
自動生成されるlockファイルは依存を1つ追加しただけでも数百行動くため、除外しないと
「依存を1つ足しただけの小さなPR」が常に差分規模の閾値を超えてしまう。

設計上の注意点は次の3つ。

- **差分規模は`00.check-user`の判定には影響させない。** 差分が大きいことは「レビューを読みたい」
  理由にはなるが「マージを止める」理由ではないため、`risk-check`内では機械的リスク判定の
  フラグ（`RISKY`）とレビュー実行ゲートのフラグ（`NEEDS_REVIEW`）を別々に持っている。
  閾値超過だけでは`00.check-user`は付かず、レビュー結果が問題なければそのまま自動マージされる。
- **`auto-merge`ジョブは`claude-review`がskipされても進む必要がある。** `needs`の既定動作では
  依存ジョブがskipされると後続もskipされるため、`auto-merge`の`if`で
  「`claude-review`が`success`または`skipped`」を明示的に許容している。`failure`のときは
  従来どおり自動マージしない。
- **`always()`ではなく`!cancelled()`を使う。** `always()`はワークフローのキャンセル時にも
  ジョブを実行してしまう。本ワークフローは新しいpushが来ると古い実行をconcurrencyで丸ごと
  キャンセルする（#818）ため、`always()`にするとsupersededになった古い実行がauto-mergeを
  有効化してしまう。

判定結果（実行するかスキップするか、その理由、差分規模と閾値）は`risk-check`ジョブの
Job Summaryに出力される。スキップした旨をPRやIssueへコメント投稿はしない。低リスクPRは
そのまま自動マージされるため、毎回コメントが増えるとノイズになるだけだからである。

なお、この閾値（10ファイル / 500行）は呼び出し元（`claude-review-develop.yml`）が
`review-file-threshold`・`review-line-threshold`入力で指定する（#1078でジョブ本体を
`reusable-claude-review-develop.yml`へ切り出した際に、`env`から入力へ移した）。
リポジトリごとにPRの粒度が違うため、他リポジトリへ展開する際はここを調整する。
差分規模から除外する自動生成ファイルも`lock-files`入力で指定する。


## ワークフローファイルを変更するPRではclaude-reviewが必ずスキップされる

`claude-code-action`には、**ワークフローファイルの内容がリポジトリのデフォルトブランチ
（issue-deckでは`develop`）の同ファイルと完全一致していなければ、Claudeの実行だけを
スキップする**という検証機構がある。ワークフローファイルを書き換えたPRから、そのPR自身の
内容でClaudeを動かせてしまうと任意のプロンプト・任意の権限で実行できてしまうため、
それを防ぐためのもの。

そのため`.github/workflows/`配下を変更するPRでは、`claude-review`ジョブのClaudeステップが
次の警告を出して必ずスキップされる。

```
##[warning]Skipping action due to workflow validation: Workflow validation failed.
The workflow file must exist and have identical content to the version on the
repository's default branch.
```

**注意すべきなのは、このときステップもジョブも`success`で終わることである。** `claude-review`
ジョブが成功していても、レビューが実際に行われたとは限らない。実際に行われたかどうかは、
PRにレビューコメントが投稿されているか、あるいは「Claude使用量をJob Summaryに出力する」
ステップが`execution_file`が空でskipされていないかで判別する。

この挙動による運用上の帰結は次の2つ。

- **ワークフロー変更はマージ前に完全には検証できない。** ワークフローファイルへの変更が
  実際にClaudeの挙動へどう効くかは、デフォルトブランチへマージされて初めて確認できる。
  ワークフロー変更PRでは、Claudeを介さない部分（シェルスクリプトによる判定ロジック・
  ジョブ間の`needs`/`if`の依存関係など）をローカルで検証しておき、Claude側の挙動は
  マージ後の次のPRで確認する、という二段構えになる。判定ロジックのローカル検証方法は
  ステップの`run`を抽出して`gh`をスタブ化する形が使えるが、`env`の定義漏れはこの方法では
  捕まらないため、`env`にキーが存在することは別途確認する（#929で実際に見逃した）。
- **安全網は`risk-check`側が担保している。** `risk-check`は`.github/workflows/**`の変更を
  機械的リスク判定の対象にしており、ワークフロー変更PRには必ず`00.check-user`が付いて
  自動マージがスキップされる。したがって「レビューが行われないまま自動マージされる」
  事態にはならない。ワークフロー変更PRでレビュー結果が無いのは想定どおりの状態であり、
  人間の確認で代替する。

実例: PR #1048（本ゲート機構の導入PR）の
[run 31477646748](https://github.com/guchi-apps/issue-deck/actions/runs/31477646748)。
`risk-check`が`.github/workflows/**`の変更を検知して`00.check-user`を付与し、ゲート判定は
`claude-review`を実行する側に倒れ、ジョブ自体も`success`で終わったが、Claudeの実行は
上記の検証機構でスキップされており、PRへのレビューコメントは投稿されていない。


## デプロイ後などに残るユーザーの手作業はIssueとして起票する（#1240）

実装の結果として、エージェントが代行できないユーザー自身の操作が残ることがある
（VPS上の`.env`の書き換え、GitHub Appの権限追加、1Passwordでのトークン発行、
外部サービスの管理画面での設定など）。

**これをPR本文の「注意点」やIssueコメントに書くだけで終わらせない。** PRがマージされ
元のIssueが`Done`でcloseされた時点で、その手順はどのカンバンにも残らず、やり残しとして
追跡できなくなる。**必ず単独の新規Issueとして起票する。**

### 判断基準

次のいずれかに当てはまるものが対象。

- エージェントの権限・実行環境では実施できない（本番サーバー上の操作、GUIしか無い管理画面、
  1Password等のシークレット発行）
- 実施はできるが、無断で行ってはいけない（Secrets・環境変数の設定変更、本番設定の変更。
  「自動マージ不可カテゴリ」と同じ理由）
- 変更をマージしただけでは効かず、別リポジトリ・別ホストでの追随操作が要る
  （他リポジトリへのラベル配布・再利用可能ワークフローのタグ更新など）

逆に、**エージェントが実施できることを手作業Issueへ逃がさない。** 起票は追跡のための手段で、
作業を人へ移す口実ではない。

### 起票しない条件（#2009）

上の判断基準に当てはまっていても、次のどれかなら**起票しない**。追跡したいのは「まだ誰も
やっていない作業」であって、押せば済む操作や、放っておいても次回また発生する作業ではない。

- **issue-deckの画面から実行できる操作。** サブPCのチェックアウト更新とpollerの再起動は、
  ホストの行に出る「更新して再起動」で済む
  （[subpc-dispatch.md](subpc-dispatch.md#画面から更新して再起動する1875)）。起票せず、
  PR本文の「注意点」と起点Issueのコメントに「マージ後に画面から更新して再起動する」と書く。
  **書くだけで終わらせてよい数少ない例外**で、理由は追跡すべき作業が残らないため。押すのは
  遅くとも次にその画面を見たときで、押し忘れはホストの行の「◯コミット遅れ」に出続ける
- **同じ作業が繰り返し発生するもの。** 発生のたびに起票しない。2回目以降だと気付いた時点で
  起票するのは、**その作業を追跡するIssueではなく、その作業をなくすIssue**（自動化するか、
  画面の操作へ寄せる）にする
- **openな同内容の手作業Issueが既にあるもの。** 起票の前に必ず確認する（後述）

そう決めたのは、この判断が無かった期間に同じ内容のIssueが並んだため。「サブPCの
`~/apps/issue-deck`をpullしてpollerを再起動する」だけの手作業Issueは、2026-08-14から08-19までの
5日間で**17件**起票されている（#1295・#1463・#1581・#1584・#1592・#1609・#1634・#1694・#1747・
#1760・#1823・#1844・#1858・#1867・#1887・#1900・#1934）。実装セッションは互いの存在を知らない
ため、openな同内容があっても新しく立つ。#1858と#1867は3秒差でまとめてcloseされており、
**実際には1回の作業**だった。「ユーザーの作業待ち」ビューを開いた人からは、同じ作業が2〜5件
並んで見えていたことになる。

**#1875で「更新して再起動」を入れた後も#1887・#1900・#1934が同じ形で立ち続けた。** 代替手段を
作っただけでは止まらず、起票する側の基準に書いて初めて止まる（作った側と起票する側は別の
セッションで、互いの成果を知らない）。

#### 起票の前にopenな同内容を探す

タイトルの`<やること>`から名詞を1〜2語取り、**同じリポジトリのopenな手作業Issue**を引く。

```bash
gh issue list --repo guchi-apps/issue-deck --state open \
  --label "71.manual-step" --search "poller 再起動" --json number,title
```

- **見つかったら起票しない。** 起点Issueとの紐付けが要るなら、既存の手作業Issueへ
  「#<起点Issue番号>でも同じ作業が必要になった」とコメントし、サブIssueとして紐付ける先も
  既存の方にする。PR本文の「注意点」にもそのIssueへのリンクを書く
- 内容が同じでも**前提条件（対象ホスト・先に要るPR）が違うなら別の作業**なので起票してよい。
  その場合はタイトルで違いが分かるようにする（`[手作業] VPS: ...`と`[手作業] サブPC: ...`）
- 探すのはopenだけでよい（`--state open`）。closedは過去に同じ作業をした履歴が出るだけで、
  いま追跡すべきものではない。ただし**closedが何件も出てきたら「繰り返し発生するもの」の
  合図**なので、起票ではなく作業をなくすIssueを立てる

### 実機の設定ファイル変更は、管理リポジトリのIssueへ切り出す（#2021）

VPS・サブPCの設定ファイルは**Gitで管理されていて、`main`へマージすれば実機へ自動で反映される**。

- `guchi-apps/vps`: `main`へのpushで`.github/workflows/deploy.yml`がVPSへrsyncし、
  `scripts/apply.sh`が`/etc`配下へ配る
- `guchi-apps/subpc`: `main`へのpushでサブPC上のself-hostedランナーが
  `scripts/setup-apply.sh`（＝`setup.sh`）を実行する

**ただしマージは2回ある。** どちらのリポジトリも日常の開発ブランチは`develop`で、Issueブランチが
向くのも`develop`。`deploy.yml`が起動するのは`main`へのpushなので、実機へ出るには
`develop`→`main`のリリースPR（`release-develop-to-main.yml`）のマージがもう1段要る。
そのマージは自動マージ不可カテゴリ（[../../CLAUDE.md](../../CLAUDE.md)）なので人が行う。

にもかかわらず、手作業Issueには`sudo nano /etc/apache2/sites-available/...`のように**実機を
直接書き換える手順**が書かれることがある。そうすると変更がGitに残らず、両リポジトリが毎日回して
いるドリフト検知で後から差分としてだけ出てくる（直した本人はもうその作業を覚えていない）。

**そこで、実機のファイル変更は手作業Issueの手順にせず、管理リポジトリのIssueへ切り出す。**

| 実機のパス | 管理リポジトリ | リポジトリ内の置き場所 |
| --- | --- | --- |
| `/etc/apache2/sites-available/`・`conf-available/`・`mods-available/` | `guchi-apps/vps` | `apache/` |
| `/etc/systemd/system/`・`~/.config/systemd/user/` | `guchi-apps/vps` | `systemd/` |
| `/usr/local/bin/`・`/etc/profile.d/signaly_login_notify.sh` | `guchi-apps/vps` | `scripts/` |
| `crontab -e` | `guchi-apps/vps` | `cron/crontab.txt` |
| `/etc/fail2ban/jail.local` | `guchi-apps/vps` | `fail2ban/jail.local` |
| `/etc/netplan/`・`/etc/ssh/sshd_config.d/`・`/etc/default/grub` | `guchi-apps/subpc` | `configs/` |
| `~/.bashrc`・`~/.bashrc.local`・`~/.profile.local` | `guchi-apps/subpc` | `configs/bash/` |

**載せるのは`deploy.yml`の`paths`に入っている受け口だけ**（vpsは`apache/**`・`systemd/**`・
`cron/**`・`scripts/**`・`fail2ban/**`、subpcは`setup.sh`・`configs/**`・`scripts/**`）。
vpsの`mysql/`は記録用で`scripts/apply.sh`が配らないため対応表に載せていない——マージしても実機が
変わらない置き場を載せると、切り出したPRをマージしても実機は元のままなのに「対応済み」に見える。
Git管理外の領域は従来どおり手作業のまま残すのが正しい。

**対応表の正は[`src/lib/infra-config-repos.ts`](../../src/lib/infra-config-repos.ts)**。上の表は
読むためのもので、画面もそちらを見る。各リポジトリの反映スクリプト（`scripts/apply.sh`・
`setup.sh`）が変わったら、まずそこを直す。**`mysql/`（vps）と`netplan`（subpc）はマージしても
自動では反映されない**——前者は`apply.sh`の対象外、後者は`netplan apply`と再起動を自動化して
いない（失敗すると到達できなくなるため）。この2つは対応表側に但し書きを持たせてある。

切り出しの流れは次のとおり。

1. 対象リポジトリへIssueを起票する（`gh issue create --repo guchi-apps/vps ...`）。
   **そのリポジトリでの実装（ファイルの変更・PR作成）は起票したセッションで行わない**——
   担当Issue以外の実装にあたる（[branching.md](branching.md)）。PRは対象リポジトリの
   セッションが作る
2. 起点Issueのサブissueとして紐付け、PR本文と完了報告コメントにリンクを書く
3. 手作業Issueは残す。ただし本文に書くのは実機のコマンドではなく、**マージと確認の3手順**にする
   （(1) 切り出したPRを`develop`へマージ (2) `develop`→`main`のリリースPRを作成・マージ
   (3) `deploy.yml`の成功を確認）。実機へ出るまでのマージが2回あり、2段目は自動マージ不可
   カテゴリで人が行うため、追跡の対象として残る
4. その手作業Issueの`## 前提条件`の「先に完了している必要があるIssue・PR」へ
   `guchi-apps/vps#<番号>`と書いて順序を残す（後述「実施順序は`## 前提条件`に書く」）

#### 取りこぼしは画面が拾う

すでに立っている手作業Issueや、上の判断を知らないセッションが書いた手順のために、
**手作業パネル（`ManualStepPanel`）が本文を見て「リポジトリ経由で反映できます」を出す**。
押すと新規作成ダイアログが対象リポジトリ・タイトル・本文を埋めた状態で開き、作成すると
起点の手作業Issueの`## 前提条件`へ`guchi-apps/vps#<番号>`が自動で書き足される。

- **画面が黙って他リポジトリへ起票することはない。** 埋めるところまでで、作るかどうかは
  中身を読んだ人が決める
- **判定はパスの文字列一致と書き換えを表す語だけで、推定を挟まない。** 読み取るだけの手順
  （`cat`・`systemctl status`）には出ない。デバイス（手順の文頭の`（VPS）`、無ければ
  `## 前提条件`の「実行するデバイス」）が読めず、VPS・サブPCの両方に当たるパス
  （`/etc/systemd/system/`）は、どちらの実機か決められない
  ので出さない。**取りこぼす側へ倒してある**——当たっていない手順に出すと、実機に反映されない
  PRだけが残る
- 出ていても手作業は止まらない。「順番に進める」も「完了してクローズ」もそのまま押せる

### ラベル

`71.manual-step`（ユーザー自身の手作業が必要）を付ける。

- **`00.check-user`とは併用しない。** 併用するとissue-deckのIssue詳細に「承認」「修正」
  ボタンが出るが、手作業Issueには承認して再開させる実装フローが無く、押しても宛先が無い。
  「ユーザーの確認待ち」ビューにも混ざり、承認待ちの優先順位付けが崩れる。
- **00番台にしない。** `^00\.`のラベルは`isAttentionLabel`により一覧カードのラベル表示から
  除外される（`src/lib/issue-status.ts`・`src/components/dashboard/issue-list.tsx`）ため、
  盤面で手作業Issueだと見分けられなくなる。
- `70.confirm`（実施するか検討必要）とも役割が違う。`70.confirm`は**やるかどうかが未決**、
  `71.manual-step`は**やることは決まっていて実行者が人**である。
- 他リポジトリには`guchi-apps/docs`の`label-sync/`でissue-deckから配る
  （[../cross-repo-setup-guide.md](../cross-repo-setup-guide.md)「2. ラベル体系」）。

#### 付け忘れはワークフローが埋める（#1492）

**タイトルが`[手作業]`で始まるIssueには、`71.manual-step`が自動で付く。**
`reusable-issue-labels.yml`の`manual-step-label`ジョブが、Issueのopen・タイトル編集を
きっかけに付与し、**取りこぼしは`schedule`の定期巡回が埋め直す**（#2010）。

ラベルの付与を担保するものが以前はどこにも無かった。実装エージェントはプロンプトの指示に
従って`gh issue create --label`を書くだけで、忘れても誰も気付かない。issue-deckの作成
ダイアログやGitHubから人が直接起票する経路には、その指示すら届かない。**ラベルの無い
手作業Issueは「ユーザーの作業待ち」ビューに現れず、Issue詳細でも案内パネルではなく「実装を開始」が
出るため、エージェントへ送れる普通のIssueに見える**（#1492で実際にこの疑問が出た）。

- 判定材料をタイトルにしたのは、プレフィックスが規約で決まっており、3つの起票経路
  （エージェントの`gh issue create`・issue-deckの作成ダイアログ・GitHubから直接）すべてで
  同じ形になるため。ラベルと違い、リポジトリにラベル定義が無くても書ける。
- **付けるだけで、外しはしない。** タイトルからプレフィックスを消したときにラベルまで剥がすと、
  人が意図して付けたラベルをワークフローが取り消すことになる。埋めるのは付け忘れだけ。
- ラベル定義が無いリポジトリでは警告を出してスキップする（`gh issue edit --add-label`は
  ラベル未定義だとexit 1になる・#975）。ラベル体系そのものを配る話は上記のとおり別経路。
- **`--label`を書く運用は変えない。** 自動付与は最後の網であって、起票時点でラベルが付いて
  いれば「ユーザーの作業待ち」ビューへ即座に並ぶ。ワークフロー経由だと数秒遅れる。
- **他リポジトリではcallerの更新が要る。** トリガー定義（`on: issues: types:`）は各リポジトリの
  `issue-labels.yml`にしか無いため、`@workflows/vN`のタグを上げるだけでは`opened`・`edited`が
  届かない（[../cross-repo-setup-guide.md](../cross-repo-setup-guide.md)「再利用可能ワークフローの参照」）。

##### イベントで取りこぼしたものはscheduleが埋め直す（#2010）

**イベント駆動だけでは、一度取りこぼすと永久に埋まらない。** `on:`はcaller側にしか無いため、
そのリポジトリが`opened`・`edited`を拾っていない時期（あるいは`manual-step-label`ジョブを
含まないタグを指していた時期）に起票されたIssueは、後からタグを上げてもIssueのイベントが
再発火せず、ラベルが付かないまま残り続ける。

実例が`guchi-apps/signaly#148`で、`manual-step-label`ジョブがまだ無い`workflows/v21`を
指していた時期に起票され、タイトルは規約どおり`[手作業]`で始まるのに**ラベルが1つも付かないまま
2日以上openだった**。「ユーザーの作業待ち」ビューにも通知にも一度も出ておらず、
重複や完了漏れを見分ける以前に管理対象へ入っていなかった。

そこで`manual-step-label`ジョブは`schedule`・`workflow_dispatch`でも動く。

- 対象は**タイトルが`[手作業]`で始まるopenなIssueのうち`71.manual-step`が無いもの**。
  `gh issue list --search 'in:title "[手作業]" -label:"71.manual-step"'`で引く
- **検索は絞り込みにしか使わない。** GitHubの検索は`手作業`を含むだけの別Issueも返すため、
  プレフィックスの一致は取得後にもう一度確かめる（判定規則はイベント経路と同じ）
- **付けるだけで外さないのも、ラベル未定義のリポジトリで警告に留めるのも変わらない**
- **`schedule`を持つcallerでは、このジョブぶんのActions実行が1回増える**（課金はジョブ単位で
  1分に切り上げ。対象0件でも起動はする）。`develop-merge-sweep`と別ジョブのままにしてあるのは、
  あちらが進捗報告APIへ依存するのに対しこちらはGitHubだけで完結し、片方が落ちても
  もう片方が動くようにするため
- **`schedule`を持たないcallerには届かない**（`guchi-apps/question`。手作業Issueも
  `71.manual-step`の定義も無いリポジトリなので、現状は問題にならない）

### タイトル

`[手作業] <実行する場所>: <やること>` の形にする。

```
[手作業] VPS: issue-deckの.envにPROGRESS_REPORT_SECRETを追加する
[手作業] GitHub App: sub_issuesイベントの購読を追加する
[手作業] 1Password: docs用のサービスアカウントトークンを発行する
```

プレフィックスを付けるのは、盤面でラベルチップを見なくても判別でき、GitHub側でも
`in:title "[手作業]"`で引けるようにするため。場所を先頭に置くのは、同じホスト・同じ
管理画面の作業をまとめて片付けられるようにするため。

### 本文

次の見出しをすべて埋める。**「やること」はコピーしてそのまま実行できるコマンド**にする
（手順の要約ではなく、実際のコマンド。GUI操作なら押す場所を順に書く）。
**手順が2つ以上あるときは`- [ ]`のチェックリストにする**（後述）。

**本文の雛形。この形をそのままコピーして埋めてください。**

<!-- manual-step-body-template:start -->
````markdown

- できるようになること: （実行すると何が使える・動くようになるか）
- 実行するまでできないこと: （それまで何が止まる・使えないか）
- 急ぎ具合: （いつまでに必要か。急がないなら「急がない」）

## 前提条件

- 実行するデバイス: （手順の大半を実行する端末。サブPC / メインPC / VPS / ブラウザ のどれか1つ。SSHが要るなら接続コマンドも）
- カレントディレクトリ: （`cd`する場所。リポジトリでの作業でなければ「不要」）
- Gitブランチ: （原則`develop`。リポジトリでの作業でなければ「不要」）
- 先に完了している必要があるIssue・PR: （`#<番号>`がdevelopへマージ済み、など。無ければ「なし」）
- その他の前提: （必要な権限・トークン、起動しておくサービスなど。無ければ「なし」）

## やること

- [ ] （サブPC）1手順目。何をするかを1行で

  ```bash

  ```

- [ ] （ブラウザ）2手順目

## 完了の確認方法

（実行後に何を見れば効いたと分かるか。確認用のコマンドと期待する出力、または画面のどこに
何が出ていれば完了かを書く）

## なぜエージェントが実施しないか

（権限が無い・無断で変更できない設定である、など）

## 関連

- 起点Issue: #<番号>
- 対応PR: #<番号>
````

**埋めるときに守る点。** issue-deck画面（手作業アシスタント）がこの書式を読んで手順・チップ・
代行実行を組み立てるため、崩すとその機能が黙って落ちる。

- `## 前提条件`の各項目は**1行に収める**。折り返した続きの行は項目として読まれず、値が途中で切れる
- **手順の文頭に`（サブPC）`のように端末を書く。** 書けるのは`サブPC`・`メインPC`・`VPS`・
  `ブラウザ`の4つで、書いた手順はその端末で扱われる（代行実行の可否も手順ごとに決まる）。
  「サブPCで〜する」のような散文からは読み取らないので、括弧書きで書くこと
- **「実行するデバイス」は1つだけ書く。** これは**デバイスを書かなかった手順の既定値**で、
  そのまま画面のチップにも出る。端末が複数書かれていると既定値が決まらず、デバイスを
  書いていない手順は代行実行の対象から外れる
- `## 関連`の起点Issue・対応PRは**`#<番号>`**（別リポジトリなら`owner/repo#<番号>`）で書く。
  URLで書くと前提条件の状況表示から落ちる
- **1つの手順に置くコードブロックはちょうど1つにする。** 2つ以上ある手順は「どれを実行したのか」が
  チェック1つに対応しないため、代行実行の対象から外れる
- コマンドのコードブロックは、その`- [ ]`項目の**2スペース下げ**で置く
- **人が値を埋めてから実行するコマンドは、埋める箇所を`<控えたkey>`のように`<…>`で書く。**
  プレースホルダを含む手順は代行実行の対象から外れ、「あなたが実行」として並ぶ（#2051）。
  `$HOME`のような**実在の環境変数参照は埋める箇所として扱われない**ので、値を埋めてほしい
  ところは必ず`<…>`にする

#### 雛形の正は1か所で、起票側のプロンプトへ差し込む（#2048）

上の雛形の実体は[docs/multi-agent/manual-step-body-template.md](manual-step-body-template.md)にあり、
`scripts/generate-prompt-templates.mjs`がマーカー（`<!-- manual-step-body-template:start -->`〜`:end`）
で囲った区間へ差し込む。差し込み先はこの文書と、起票する3経路のプロンプト
（`scripts/prompts/implementation-agent.md`・`generic-implementation-agent.md`・
`.github/prompts/implement.md`）。**雛形を直したら`node scripts/generate-prompt-templates.mjs`を
実行する**（ずれはCIの`Prompt shared template sync check`が落とす）。

**なぜプロンプトへ埋め込むのか。** 以前はリテラルな骨組みがこの文書にしか無く、実際に起票する
エージェントが読むプロンプト側には**散文の要件リストしか無かった**。そのため毎回モデルが要件から
文面を再構成し、太字の有無・コードブロックのインデント・参照の書き方が揃わなかった
（2026-08-22時点でopenだった3件が3通りに割れていた）。プロンプトは他リポジトリでも使うため、
「この文書を読め」という形にはできない（そのリポジトリには存在しない）。

#### 本文の書式は起票時に機械検査する（#2048）

雛形を配っただけでは揃わない（`71.manual-step`の付け忘れを#1492で埋めたのと同じ理由で、
**起票する側と作った側は別のセッションで、互いの成果を知らない**）。そこで
`reusable-issue-labels.yml`の`manual-step-body-check`ジョブが、タイトルが`[手作業]`で始まる
Issueのopen・editedで本文を検査し、指摘があればマーカー付きのコメントを1件だけ貼る
（本文を直すと更新され、指摘が無くなれば消える）。

- **判定の正はissue-deck側**（`src/lib/manual-step-body-check.ts`、受け口は
  `POST /api/manual-steps/body-check`）。検査するのは画面のパーサーが読む書式そのものなので、
  規則をワークフローへ写すと「検査は通るが画面は読めない」食い違いが必ず出る。判定は
  `parseManualStepGuide`・`splitManualStepSections`・`collectShellBlocks`を通す
- **検査するのは画面が実際に使う項目だけ。** 「テンプレートと文字が違う」を全部指摘すると
  読まれなくなる。規則を1つ足すときは、**崩れたときにどの機能が落ちるかを言えること**を条件にする
- **ラベルは付けず、起票も止めない。** 手作業Issueに`00.check-user`を付けない規約に従う。
  ここは書式の助言であってゲートではない
- **issue-deckが落ちていてもワークフローを失敗させない**（進捗報告と同じ取り決め）。
  `APP_BASE_URL`・`PROGRESS_REPORT_SECRET`が無いリポジトリでは黙ってスキップされる
- **「指摘なし」の判定はファイルサイズではなく中身で行う**（#2106）。指摘が1件も無いとき
  APIは`comment: null`を返し、ワークフローは`jq -r '.comment // ""' > comment.md`で受ける。
  **`jq`は末尾に改行を付けるため、この`comment.md`は0バイトではなく改行1バイトになる。**
  `[ ! -s comment.md ]`はサイズしか見ないのでここを素通りし、空本文の投稿が
  `GraphQL: Body cannot be blank (addComment)`で落ちて、**書式どおりの手作業Issueを起票する
  たびに赤い失敗が1本残っていた**（#2105で実測。前回の指摘コメントを消す経路も同じ`if`の
  中にあるため、指摘を直しても古いコメントが残り続けていた）。判定は
  `[ -z "$(tr -d '[:space:]' < comment.md)" ]`で行う
- この4経路（指摘なし／指摘なし＋前回のコメント／指摘あり／前回のコメントの更新）は
  `scripts/reusable-issue-labels.test.mjs`が`run:`本文をそのまま実行して押さえている。
  **スタブの`gh issue comment`は、本文が空の`--body-file`をGitHubと同じように拒否する**——
  黙って成功させると#2106の失敗経路をテストで踏めないため

いま見ている規則は次の7つ。

| 規則 | 重さ | 崩れると落ちるもの |
| --- | --- | --- |
| 6つの見出しが規定の順で揃っているか | `error`（不足）／`warning`（順） | 見出しで節に割るため、無い節はそのまま欠ける |
| `## 前提条件`の5項目が「ラベル: 値」の1行として読めるか | `error`（デバイス・ディレクトリ・ブランチ）／`warning`（残り2つ） | チップと代行実行の可否 |
| 「実行するデバイス」に端末が複数書かれていて、デバイスの無い手順が残っていないか | `error` | 既定値が決まらず、デバイスを書いていない手順が代行実行の対象から外れる（#2052） |
| `## 前提条件`の項目が折り返していないか | `warning` | 続きの行は項目として読まれず、値が途中で切れる |
| `## やること`がチェックリストで割れているか | `warning` | 割れていないと節まるごとが1ステップになる（#1486） |
| 1手順のコードブロックがちょうど1つか | `error` | 2つ以上ある手順は代行実行の対象から外れる（`extractShellBlock`） |
| `## 関連`の参照が`#番号`形式か | `error` | `REFERENCE_PATTERN`はURLに一致せず、実施順序の表示から落ちる |


#### 「やること」はチェックリストで書く（#1486）

手順が2つ以上ある手作業では、**1手順＝1つの`- [ ]`**にする。コマンドはその項目の下に
インデントしたコードブロックで置く（インデントを揃えないと、コードブロックが項目から外れて
チェックリストが途切れる）。

これは見た目の都合ではなく、**チェックボックスがそのまま実行状態の記録になる**ため。

- GitHub上ではチェックボックスをクリックするとIssue本文が書き換わり、Issue一覧に
  「3 of 5」の進捗が出る（GitHubのタスクリスト機能）
- issue-deckのIssue詳細でも同じようにクリックでき、「説明」の右に「タスク 2 / 3 完了」が
  出る。チェックの実体はIssue本文なので、GitHubで付けても画面で付けても同じ状態になる
  （`src/hooks/use-issue-task-list.ts`・`src/lib/markdown-task-list.ts`）
- 手作業は途中で中断されることがある（SSH先が落ちている、先にリリースが要る、など）。
  1本のコマンド列で書かれていると、再開する人はどこまで実行したかを思い出せない

手順が1つしか無い場合はチェックリストにしなくてよい。**コードブロックの中に書いた`- [ ]`は
チェックボックスにならない**（テンプレートの例示をタスクとして数えないため）。

**`op signin`のような対話が要るコマンドは、その手順まるごとが人の実行になる**（#2025）。
サインインしたセッションは実行したシェルの環境変数にしか残らないため、`op signin`と、その
セッションを使う後続のコマンドは**同じコードブロックにまとめて書く**。手作業アシスタントは
その項目を「あなたが実行」として並べ、自動実行はそこで止まって人へ返す（実行し終えて
「実行した・次へ」を押すと、残りの手順は自動で流れる）。分けて書くと、人が`op signin`だけを
実行したところで続きの代行実行はそのセッションを引き継げず、必ず失敗する。

#### 「この作業でできるようになること」を先頭に置く理由（#1730）

**本文の最初に来るのは手順でも前提条件でもなく、「この作業をやると何ができるようになるか」
「やるまで何ができないか」である。** 手作業Issueを開く人は、実装したエージェントとは別の時点・
別の端末にいて、その作業がどの機能を止めているのかを覚えていない。先頭に効果が書かれていないと、
`## やること`のコマンドを読んでも「いま急いでやるべきか、後回しでよいか」を判断できない。
「ユーザーの作業待ち」ビューに複数溜まったときの優先順位付けも、ここを読み比べて決める。

- **旧テンプレートの`## 放置するとどうなるか`はこの見出しへ統合した。** 「これをするまで
  何ができないか」と「放置するとどうなるか」はほぼ同じ内容で、見出しを分けると同じことを
  2か所に書くことになり片方が古くなる（`## 実行する場所`を`## 前提条件`へ統合した#1458と同じ判断）。
  期限（いつまでに必要か）は「実行するまでできないこと」に含めて書く。
- **`## 完了の確認方法`は`## やること`の直後に置く。** 実行する人は「手順を実行する→効いたことを
  確かめる」を続けて読むため。`## なぜエージェントが実施しないか`は実行時には要らない背景情報なので、
  その後ろへ回した。
- 既存の手作業Issueを書き直す必要は無く、これから起票するものに適用する。

#### 「前提条件」を独立した見出しにする理由（#1458）

手作業Issueを開くのは、実装から日が空いた人（多くは別の端末の前にいる）である。**そのとき
最初に判断するのは「いま実行してよいか」「どこで実行するのか」であって、コマンドの中身では
ない。** これを本文のあちこちに散らすと、`cd`だけコマンドブロックに埋もれていて実行するデバイスは
どこにも書いていない、という状態になる（実際、#1463のように「`# サブPC上で実行する`」という
コメント頼みで書かれていた）。見出しとして固定し、埋める項目を列挙しておくことで、書く側が
落としたことに気付ける。

なお、**旧テンプレートの`## 実行する場所`はこの「実行するデバイス」に統合した**（同じことを
2か所に書くと片方が古くなる）。タイトルの`[手作業] <実行する場所>: <やること>`は変更しない。
既存の手作業Issueを書き直す必要は無く、これから起票するものに適用する。

#### Gitブランチは原則`develop`（#1458）

リポジトリの作業ツリーでコマンドを実行する手作業では、**既定を`develop`とする。** サブPC上の
各リポジトリの本体チェックアウトは`develop`に置いてあり（issue-deckの`~/apps/issue-deck`は
レビュー・統合エージェント用のdevelop最新チェックアウト。[branching.md](branching.md)）、
手作業の大半は「developへマージ済みの変更をそのホストへ取り込む」ものであるため。

例外は次の2つで、この場合だけ`main`と書く。

- **`develop`を持たないリポジトリ**（`guchi-apps/docs`・`claude-config`など、`main`だけで
  運用しているもの）
- **本番（VPS）へデプロイ済みのコードを対象にする作業**（デプロイは`main`へのpushで走るため、
  本番に載っているのは`main`）

「いつから実行してよいか」はブランチではなく**「先に完了している必要があるIssue・PR」**に書く。
`develop`にマージされれば実行できるのか、`main`へのリリースまで待つ必要があるのかで、実行可能に
なる時点が変わる（例: 「#1461がdevelopへマージされた後」）。

### 起点Issueとの紐付け

起点のIssueへ**GitHubネイティブのサブIssueとして紐付ける**（本文の「起点: #番号」は
人が読む補助でしかない。前掲「親子関係の正はGitHubネイティブのサブIssue」参照）。
起点Issueが`Done`でcloseされても、手作業Issueはopenのまま残る。

あわせて、起点のIssueとPRに手作業Issueへのリンクをコメントで残す。PR本文の「注意点」にも
書いてよいが、**書くのは起票したIssueへのリンクであって手順そのものではない**（手順を
二重に持つと片方が古くなる）。

### issue-deckでの表示

サイドメニュー・スマホのクイックビューに**「ユーザーの作業待ち」ビュー**（`view=manual-step`）が
あり、`71.manual-step`が付いたopenなIssueを横断で一覧できる。件数バッジも他のビューと
同じく出る（`LABEL_FILTER_PRESETS`・`labelNavViews`）。

**件数に出るのは「いま実行できる手作業」だけ**（#1763）。前提待ちのものは数に入らないため、
メニューの数と一覧に並ぶ行数はわざと食い違う。その差は次の2つで読む。

- **一覧のヘッダー**: `2件・前提待ち2件`（メニューと同じ数を先に出し、差を添える）
- **一覧の各行のアイコン**: 緑のチェック＝いま実行できる、橙の時計＝前提待ち。PCではカーソルを
  合わせると「まだ実行できません。#1690 がmainへ反映されるのを待ってください。」が出る
  （Issue詳細の「前提条件の状況」と同じ1行）

判定は下記の「前提条件に書いた番号は、画面で状況まで出る」と同じ計算で、**番号を書いていない
手作業Issueは「いま実行できる」に数える**（見落とすより強調しすぎる方へ倒す）。実行できる
ものが1件も無ければ数は0になり、橙色の強調も消える。

**ヘッダーの通知ベル（「対応が必要なもの」）にも、いま実行できる手作業だけが並ぶ**（#1801）。
判定は上と同じで、前提待ちのものはベルに出ない。ベルは「いま人が動けば盤面が進むもの」を横断で
集める場所のため、実行できない手作業を並べても押せる操作が無い。前提待ちの存在は
「ユーザーの作業待ち」ビュー（一覧ヘッダーの`2件・前提待ち2件`と橙の時計アイコン）で読む。

**ただし、ベルの件数バッジには手作業を1件も数えない**（#1936）。手作業Issueは実行できる状態に
なってからも人の都合で数日〜数週間openのまま残るため、数えるとバッジが常時点灯し、確認待ち・
マージ待ちPRの増減に気づけない。**ベルを開いた一覧には従来どおり並び**（横断で手作業待ちを
見られる場所は他に無い）、差は見出しの`1件・手作業待ち1件`で読む。

**手作業Issueは「未着手」ビューからは除外している。** エージェントが着手することが無く、
ユーザーが実行するまで`Ready`に留まり続けるため、除外しないと「次にどれへ着手させるか」を
選ぶビューに恒久的に溜まる。

Issue詳細では、**エージェントへ送る導線を出さず、代わりに手作業用の案内パネルを出す**
（#1280。`ManualStepPanel`・`canCompleteManualStep`）。

- 「〈起動先〉で開始」（`canStartImplementation`）とサブPCへの起動ボタン
  （`StartLocalSessionButton`）は、`71.manual-step`が付いている間は**表示しない**。
  手作業Issueは進捗が`Ready`のまま留まるため、ラベルで除外しないと「まだ誰も着手して
  いないIssue」と区別が付かず、押しても実装対象が無い主ボタンが出続ける。
- 代わりに本文の直前へ、**「前提条件の状況」と「手作業を完了してクローズ」「実施せずクローズ」
  だけ**を並べたパネルを出す。**説明文はパネルに置かない**（#1732）。以前は手順（前提条件を
  確かめる→「やること」を実行する→…→クローズ）と進捗Statusの補足も並べていたが、手順は本文
  テンプレートの見出しをなぞっただけで、すぐ下に出る本文と重複していた。毎回同じ文面が縦に積まれ、
  実行してよいかの判断材料と出口が押し下げられる方が損が大きい。手作業の進め方は後述の
  「完了時の扱い」を正とする。
- パネルの配色にamberを使わないのは、amberが`00.check-user`（ユーザーの確認待ち）の色
  だから。violetは`71.manual-step`ラベル自体の色（`d876e3`）に合わせている。
- **手順そのものはパネルに戻さず、「順番に進める」（手作業アシスタント・#1826）へ渡す。**
  後述のとおり、テンプレートに沿って書いた本文はそのまま1手順ずつの案内になる。

#### テンプレートに沿って書くと、画面が手順に割って案内する（#1826）

「ユーザーの作業待ち」の一覧と手作業Issueの詳細に**「順番に進める」**があり、押すと
手作業アシスタントが開く。**いま実行できる手作業だけ**を更新の古い順に1件ずつ、
「この作業でできるようになること → 手順1 → 手順2 → … → 完了の確認方法」の順に出す。

このテンプレートの見出しは、そのまま画面の割り方になる。

| 本文の見出し | 画面での使われ方 |
| --- | --- |
| `## この作業でできるようになること` | 最初のステップ（実行してよいか・急ぐかの判断材料） |
| `## 前提条件` の「実行するデバイス」「カレントディレクトリ」「Gitブランチ」 | **全ステップに出したままのチップ**。末尾の括弧書き（補足）は落とす。デバイスは手順に書かれていればそちらが出る（#2052） |
| `## 前提条件` の「先に完了している必要があるIssue・PR」 | 従来どおり「前提条件の状況」（#1705） |
| `## やること` の `- [ ]` 1項目 | 1ステップ。項目の下のコードブロックがそのまま出て、コピーボタンも付く |
| `## やること` の項目の文頭の `（サブPC）` | **その手順を実行する端末**（#2052）。チップと代行実行の可否が手順ごとに切り替わる |
| `## 完了の確認方法` | 最後のステップ。クローズの2ボタンと並ぶ |

したがって、**書き方が崩れると案内も崩れる**。とくに次の2点は画面に直接効く。

- **コマンドはチェック項目の下にインデントして置く**（前掲「『やること』はチェックリストで書く」）。
  インデントが揃っていないとコードブロックが項目から外れ、手順に付かない
- **`## 前提条件`は「ラベル: 値」の箇条書きで書く**。「実行するデバイス」「カレントディレクトリ」
  「Gitブランチ」の3つはチップになるので、書いていなければそのチップは出ない（省略しても
  画面は壊れないが、実行する人はどこで打つのかを本文から探し直すことになる）

`## やること`にチェックリストが1つも無い本文は節ごと1ステップになり、見出しが1つも無い
古い本文は手順に割らず本文をそのまま出す。**案内できないというだけでIssueを隠さない。**
既存の手作業Issueを書き直す必要は無い。

#### サブPCで実行する手順は、承認だけで代行できる（#1828）

手順にコマンドが書かれていて、**その手順を実行する端末がサブPC**なら、
アシスタントの手順画面に**「承認して実行」**が出る。押すとサブPCのpollerがそのコマンドを実行し、
終了コードと出力が画面に返る。終了コードが`0`なら、その手順のチェックまで自動で付く。

- **代行するのは「権限・実行環境の都合で実施できない」に当たらない手作業だけ。** 起票基準の
  もう一方（「実施はできるが、無断で行ってはいけない」）は**承認が入ることで解ける**——
  これが代行してよい範囲そのものになっている（前掲「判断基準」）
- **実行するのは本文に書かれたコマンドだけ。** 画面が送るのは「どの手順か」と「承認した
  コマンド」で、実行に使われるのはサーバーが本文から抽出し直したもの。サブPC側でもpollerが
  GitHubの本文を読み直して同じ照合を行う（仕組みは
  [subpc-dispatch.md](subpc-dispatch.md#手作業アシスタントからの代行実行1828)）
- **代行できるのは、シェルのコードブロックが手順の中にちょうど1つある場合だけ。** 0個・2個以上の
  手順はボタンが出ない（どのコマンドを実行したのかがチェック1つに対応しないため）。
  **代行したい手順は1手順＝1コマンドで書く**——書き方がそのまま代行できるかどうかを決める
- サブPC以外（VPS・1Password・GitHub App・ブラウザ）の手順では、ボタンの代わりに理由が出る。
  **判定は手順ごと**なので（#2052）、「手順1はブラウザで人が実行し、手順2はサブPCで代行する」が
  同じ手作業の中で混在できる。端末をまたぐ作業は各手順の文頭に`（サブPC）`のように書く。
  書かれていない手順は`## 前提条件`の「実行するデバイス」を既定値として使い、そこに端末が
  複数書かれている本文では**既定値が決まらないので代行しない**（読み取れないものは止める側へ倒す）
- 出力は**画面にだけ**出す（GitHubのIssueにも通知にも載せない）。手作業のコマンドの出力には
  シークレットが混ざりうるうえ、このリポジトリはPUBLICでIssueは誰でも読める

#### 前提条件に書いた番号は、画面で状況まで出る（#1705）

パネルの中に**「前提条件の状況」**が並ぶ。本文の`## 前提条件`と`## 関連`に書かれた`#番号`を
拾い、それぞれが**いまどこまで進んだか**（`mainへ反映済み` / `developへマージ済み・本番未反映` /
`実装中`・`マージ待ち` / `クローズ済み`）と、先頭に「いま実行できます」「#1690 がmainへ反映される
のを待ってください」の1行を出す。実行する人が番号を1つずつ開いて確かめる必要がなくなる。

- **番号は`#1690`の形で書く。** 「前のIssueがマージされた後」のように番号を書かないと拾えず、
  待っている相手として出てこない。別リポジトリを指すときは`guchi-apps/vps#88`と書く
  （そのリポジトリがissue-deckに連携されていれば同じように状況が出る）。
- **前提が揃っていなくても「手作業を完了してクローズ」は押せる。** 判定は本文の記載からの
  推定なので、外したときに完了できなくなる方が損が大きい。
- 状態を取得できなかった参照（連携外のリポジトリなど）は「状態不明」として出し、**待ちには
  数えない**。左メニューの「ユーザーの作業待ち」の数え方と同じ向きに倒している。
- 参照が1件も無ければ（「なし」と書いた場合を含む）ブロックごと出さない。

#### 逆向き——この手作業を待っている相手も出る（#2003）

「前提条件の状況」のすぐ下に**「このIssueの完了を待っているIssue」**が並ぶ。他のIssueの
`## 前提条件`にこの番号が書かれていれば、そのIssueが**自分が終わるまで先へ進めない相手**として
出る。実行者は「後回しにしてよい手作業か」をここだけで判断できる。

- **相手の`## 前提条件`に書かれているものだけ**を辿る。`## 関連`の起点は辿らない
  （起点は「子Issue」がすでに出しており、親が待っているとは限らない）
- **クローズ済みのIssueは出さない。** もう待っていない
- 手作業Issue以外のIssueでも同じものが出る（次節）

### 実施順序は`## 前提条件`に書く（#2003）

`guchi-apps/subpc`の#38/#39/#40のように**実施順序が決まっている**組み合わせがある
（「#39の手作業を実施 → #40をマージ → #38が閉じる」）。この順序を画面へ出したければ、
**待つ側のIssueの本文に`## 前提条件`を足して番号を書く。**

```markdown
## 前提条件

- 先に完了している必要があるIssue・PR: #39（ランナーを起こす手作業）
```

これだけで次の3か所に出る。ラベルは足さない。

| どこ | 何が出るか |
| --- | --- |
| 待つ側（#38）のIssue詳細 | 「実施順序」セクションに「前提条件の状況」。前提が残っている間は畳めない |
| 待たれる側（#39）のIssue詳細 | 「このIssueの完了を待っているIssue」（手作業Issueなら手作業パネルの中） |
| Issue一覧の行 | 前提待ちなら橙の時計、そろっていれば緑のチェック（手作業Issueと同じ印） |

- **書くのは待つ側だけでよい。** 逆向きは書かれたものから自動で出る。両方に書くと二重管理になる
- **PR本文に書いても画面には出ない。** PRの本文は読んでいないので、順序はIssueの本文へ書く
- **左メニュー「ユーザーの作業待ち」の件数は変わらない。** あの数は`71.manual-step`のうち
  いま実行できるものを指しており、一般のIssueは混ざらない
- **自動マージは止まらない。** 前提が残っていても、対応PRは`claude-review-develop.yml`の判定で
  マージされる。マージ前に人の確認を挟みたい場合は`22.merge-confirm-required`を併用する

### 完了時の扱い

**手作業Issueをエージェントへ送り直す必要はない。** 実行するのは人で、実行後にコードが
変わるわけでもないため、`@claude`コメントも「実装を開始」も要らない。**やることは
「実行してcloseする」だけ。**

1. Issue本文の「やること」を、書かれている場所（VPS・GitHub・1Password等）で実行する。
2. 実行結果や気づいた点があれば、closeする前にIssueコメントへ残す（任意。
   手順が本文と違っていた場合は特に書く）。
3. issue-deckのIssue詳細で**「手作業を完了してクローズ」**を押す（`completed`でclose）。
   GitHub側から直接closeしてもよい。

進捗（Project Status）は`Ready`のままでよい。手作業Issueは`Develop`→`Done`のリリース
フローに乗らないため、**closeしたことが完了の記録になる**。closeすると「ユーザーの作業待ち」
ビューからも消える（このビューはopenのみが対象）。

実施しないと決めた場合は「実施せずクローズ」（`not_planned`でclose）を押し、見送った
理由をコメントに残す。判断が付かない場合はopenのまま残してよい。手作業Issueは
起点Issueが`Done`でcloseされても道連れにならないため、残っていても他の進行を止めない。

#### 実施済みかもしれないものは画面が拾う（#2008）

**closeを押し忘れると誰も気づけない**、というのがこの手順の弱点だった（#1994は本文の完了条件を
満たしているのに数日openのまま残っていた実例）。そこでissue-deckが、openな手作業Issueの
`## 完了の確認方法`を**1日1回サブPCで実行し、全部が終了コード0で終わったものへ
「完了済みの可能性」の印**を付ける。

- 印はIssue一覧の行（violetのチェック）とIssue詳細の手作業パネルに出る。詳細では
  「手作業を完了してクローズ」が主ボタンになる
- **自動でcloseはしない。** 巡回が見ているのは終了コードだけで、本文の「期待する出力」との
  照合はしていない。押すのは人（この判断は#2011の全体実行とも共通）
- 巡回するのは**`## 前提条件`の「実行するデバイス」がサブPCに決まる**もので、**確認コマンドが読み取り
  だけだと読める**Issueに限る。VPS・1Password・ブラウザでの手作業や、確認コマンドが
  状態を変えうるものは対象外（印が出ないだけで、従来どおり人が実行できる）
- したがって**確認コマンドを読み取りだけで書くと、印が付く**。`## 完了の確認方法`に
  「実行してから確かめる」種類のコマンドを混ぜると、そのIssueは巡回されなくなる

仕組みと対象の判定は[subpc-dispatch.md](subpc-dispatch.md)「完了の確認方法を定期巡回する」を参照。

## Claudeによるラベル自動付与の対象は30〜89番台に限る（#1662）

issue-deckの「新しいIssueを作成」ダイアログには**「タイトル・ラベルを自動生成」**があり、
Issue本文からClaude（`claude-haiku-4-5`）がタイトルとラベルを推定する
（`src/components/dashboard/create-issue-dialog.tsx` → `/api/issues/suggest` →
`src/lib/claude/issue-suggest.ts`）。**Issueへラベルを推定で付ける経路はこれ1つだけ。**

**推定の対象にするのは30〜89番台のラベルだけで、71番台は除く。** 判定は
`isAutoAssignableLabelName`（`src/lib/issue-status.ts`）1か所にある。

**この「71だけを除く」は恒久的な仕様である**（#1702）。`71.manual-step`を別の帯へ移して例外を
無くす案と、優先度を対象から外して範囲を30〜70番台の連続した帯にする案をどちらも検討したうえで、
現状のまま据え置くと決めた。判断とその根拠は冒頭「ラベルの番号帯の設計（#1702）」を参照。

| 番号帯 | 例 | 自動付与 | 理由 |
| --- | --- | --- | --- |
| `00.` / `01.check-*` | `00.check-user`・`01.check-plan` | ✕ | 承認待ちの合図。人とワークフローが付け外しする |
| `11.` | `11.local` | ✕ | 「いまローカルセッションが持っている」という実行状態。起動経路が付ける |
| `21.`〜`25.` | `21.plan-required`・`24.screenshot-required` | ✕ | 「実装を開始」ダイアログのチェックボックスで選ぶゲート（「画面のオプション5つの使い分け」参照） |
| `30.`〜`70.`・`80.`/`89.` | `30.bug`・`40.unexpected`・`51.improvement`・`61.ops`・`70.confirm`・`80.Priority: High` | ○ | 種別・優先度。**本文の内容から決まる**ので推定に向く |
| `71.` | `71.manual-step` | ✕ | タイトルが`[手作業]`で始まるIssueへワークフローが付ける（上記「付け忘れはワークフローが埋める」） |
| `90.` | `90.Close: duplicate` | ✕ | closeの理由。起票の時点で決まるものではない |

- **`71`を外すのは、付け方の正がタイトルにあるから。** 推定で付くと「ユーザーの作業待ち」ビューへ
  紛れ込み、Issue詳細に「実装を開始」ではなく手作業の案内パネルが出るため、エージェントへ
  送れないIssueに見える。除外は名前一致ではなく**番号帯**で行っている（Issueの文面が「71除く」で、
  配布先で名前が違い得るため）。
- **番号プレフィックスを持たないラベルも対象外。** issue-deckのラベル体系を配っていない
  リポジトリに残るGitHub既定の`bug`・`enhancement`等は、番号帯から性質を判別できない。
  そのリポジトリでは自動生成がラベルを付けず、タイトルだけを生成する
  （[../cross-repo-setup-guide.md](../cross-repo-setup-guide.md)「2. ラベル体系」）。
- **プロンプトの候補一覧と、応答の後処理は必ず同じ集合にする。** プロンプト側だけ絞ると、
  Claudeが範囲外のラベル名を返したときに後処理が素通しする。`issue-suggest.ts`の
  `buildIssueSuggestPrompt`と`generateIssueSuggestion`の2か所が同じ関数を通る。
- **画面側でリセットする範囲も同じ集合に揃える。** `mergeSuggestedLabels`は「自動生成のたびに
  選択済みラベルを一度リセットしてから結果を反映する」実装だが、リセット対象を自動付与の対象へ
  狭めていないと、**人が手で選んだ`11.local`や`90.Close: *`が黙って消える**（生成結果には
  出てこないので復活しない）。

### 手で選ぶラベルの範囲とは別物

ラベル選択欄（作成ダイアログ・質問ダイアログ）で人が選べる範囲は
`isSelectableLabelName`（`src/lib/github/start-implementation.ts`）が決めており、
こちらは進捗管理用ラベルと実装オプション用ラベル（`21.`〜`25.`）だけを外す。
**`11.local`・`71.manual-step`・`90.Close: *`は人なら選べる。** 自動付与の対象を絞っても、
人が意図して付ける経路は塞がない。

## 自動マージ可否の判定方法

自動マージ不可カテゴリ（`00.check-user`付与対象）:
- 認証・認可
- DBスキーマ変更・マイグレーション
- 本番環境の設定
- GitHub Actionsやデプロイ設定
- Secretsや環境変数
- 課金・決済
- 大規模な依存関係の更新
- `develop`→`main`のマージ

判定方法（`.github/workflows/claude-review-develop.yml`に実装済み、Phase4）:
- **CI完了待ち（`wait-for-ci`ジョブ）**: `ci.yml`（ワークフロー名`CI`）がそのPRのhead SHAに対して`completed`になるまで待つ待機ジョブ。20秒間隔・最大60回（約20分）ポーリングし、タイムアウトした場合もジョブ自体は失敗させずそのまま後続へ進める（fail-open）。CIが`in_progress`のうちに`00.check-user`が付き、issue-deck画面上で時期尚早に「要確認」と見えてしまう問題を防ぐためのもの（#810）。**依存するのは最後の`auto-merge`ジョブだけで、`risk-check`・`claude-review`はCIと並行して走る**（#2066。後述「判定とレビューはCIと並行して走らせる」）。なお実際のマージ可否は`auto-merge`ジョブがGitHub Auto-merge機能（`develop`の`required_status_checks`でCI完了を待つ）に委ねているため、`wait-for-ci`の有無に関わらずマージの安全性自体は保たれる。
- **一次判定（機械的、`risk-check`ジョブ）**: `git diff --name-only origin/develop...HEAD` のパスを、上記カテゴリに対応するパターン（`prisma/migrations/**`, `.env*`, `.github/workflows/**`, `**/auth/**`, `.shared-context/**`）に照合する。これらは`reusable-claude-review-develop.yml`に**内蔵**されており、呼び出し元から無効化できない（#1078）。リポジトリ固有のリスクパスは`risk-paths`入力で**追加**する。入力でリスクを追加できても削減はできない設計で、宣言し忘れたリポジトリで認証やマイグレーションの変更が無確認のままマージされるのを防いでいる。`package.json`は変更前後の`dependencies`/`devDependencies`をNode.jsで比較し、メジャーバージョンが変わった依存があるかで判定する（パッチ・マイナー更新は対象外）。あわせて、共有知識リポジトリのcheckout先である`.shared-context/`（`.gitignore`済み）が差分に混入していないかも確認する。従来はこの確認を`claude-review`のプロンプトだけが担っていたが、`claude-review`は低リスクPRではskipされるようになった（#992）ため、機械判定側にも同じ確認を置いている。ヒットした場合、**このジョブは判定結果を出力（`risky`・`reasons`・`already-check-user`）に載せるだけで、`00.check-user`の付与と理由コメントの投稿は行わない**。実際に反映するのは最後の`auto-merge`ジョブ（後述「`00.check-user`はレビュー完了後に付ける」、#1406）。
- **二次判定（`claude-review`ジョブ、意味的）**: パターンに引っかからない意味的リスク（例: 認可ロジックの変更だがファイルパスに`auth`が含まれない）をレビューエージェントが読解して判断する。該当時は**対応Issueへ理由コメントを投稿するだけで、`00.check-user`は付けない**（#2136。後述「意味的判定もラベルは`auto-merge`が付ける」）。ただしこのジョブは全PRで実行されるわけではなく、`risk-check`ジョブの`needs-review`出力によってゲートされる（後述「Claude Reviewの実行要否を`risk-check`でゲートする」、#992）。
- **明示的指定（`risk-check`ジョブ、`22.merge-confirm-required`・`24.screenshot-required`ラベル）**: 変更内容によらず、対応Issueに`22.merge-confirm-required`または`24.screenshot-required`ラベルが付いている場合は常に`00.check-user`を付与する（「developへのマージ前確認要否をIssueラベルでトグルする」参照、#366・#567）。
- **`00.check-user`はレビュー完了後に付ける（#1406）**: 一次判定の結果を反映する（ラベル付与・理由コメント投稿）のは、`risk-check`ではなくワークフロー最後の`auto-merge`ジョブの先頭ステップ。`risk-check`の時点で付けていた頃は、そのあとに走る`claude-review`（数分かかる）と`auto-merge`のcheck-runが残ったままユーザーへ通知が飛び、issue-deckの画面では**head SHAの全check-runを集約したCI状態が`in_progress`のまま**（`src/lib/github/pull-request-ci.ts`）でマージボタンが押せなかった。実測（PR #1404）ではCI（`lint-and-build`）成功が17:43:23、`00.check-user`付与が17:43:51、`claude-review`完了が17:50:18で、**通知から約6分半**押せない状態が続いていた。**レビュー用ワークフローが自分自身の完了を待ってからラベルを付けることはできない**（デッドロックになる）ため、「ラベルを読む直前＝最後のジョブで書く」形にして、通知後に残るcheck-runを`auto-merge`ジョブ自身の数秒だけにしている。なお`risky`が真なら`needs-review`も必ず真になる（`add_review_reason "機械的リスク判定に該当したため"`）ので、一次判定に当たったPRでは`claude-review`が必ず走り、付与は常にレビュー完了後になる。`claude-review`が失敗して`auto-merge`ごとスキップされる経路では、`claude-review-fallback`がラベル付与と理由の伝達を肩代わりする。**なお画面側は#1799で、CI状態の集約からレビュー・自動マージ（`claude-review-develop.yml`）のcheck-runを外した**（`src/lib/github/check-rollup.ts`の`NON_CI_WORKFLOW_FILES`）ため、`auto-merge`ジョブ自身が残っていてもCI状態は`success`になる。ここでの「最後のジョブで書く」構成は通知のタイミングを揃えるために引き続き必要だが、**残るcheck-runがマージボタンを塞ぐことはなくなっている**。
- **意味的判定もラベルは`auto-merge`が付ける（#2136）**: 上の#1406で一次判定（`risk-check`）の付与は最後のジョブへ移したが、二次判定（`claude-review`）は**レビューエージェント自身が`gh issue edit`で付けていた**。#2066でレビューをCIと並行させた結果、この付与はCIの実行中に起きるようになり、しかも**ラベルが理由コメントより先に付く**（レビューはラベルを付けてから残りの読解を続け、コメントを最後に投稿する）。実測（Issue #2126 / PR #2131）ではラベルが12:06:09、CI完了が12:07:26、理由コメントが12:09:20で、**約3分間、issue-deckのIssue詳細に「⚠️ 自動マージされなかった理由: 理由の記録が見つかりませんでした」と「CI実行中」「Claudeがレビュー中」「判定中」が同時に並ぶ**状態になっていた（通知だけが飛び、押せる操作は無い）。対処として、`claude-review`はラベルを付けず、対応Issueへ投稿する理由コメントの末尾に判定マーカー`<!-- issue-deck-review-verdict:merge-blocked sha=<head SHA> -->`を残すだけにし、`auto-merge`がそれを読んでラベルを付ける。`auto-merge`は`wait-for-ci`と`claude-review`の両方を`needs`に持つ唯一のジョブで、「CIの完了とレビューの完了の両方が終わってから付く」ことを構造として保証できるのはここだけ。
  - **`sha=`で今回のhead SHAに絞る。** 追いコミットしたPRで、前のコミットに対する判定のマーカーを拾わないため。`claude-review`が`skipped`（#992のゲート）・`failure`の実行では、マーカーを読まない（前者は判定自体が無く、後者は`claude-review-fallback`が付ける）
  - **マーカーが無ければ「該当なし」に倒す（fail-open）。** レビューが判定を残せなかったときの挙動は、ラベルを自分で付けていた頃（付け忘れれば同じく自動マージされる）と変わらない。ただし文字列がプロンプトとワークフローで**ずれると黙って倒れる**ため、`scripts/check-review-verdict-marker.sh`がCI（`docs-sync-check`）で両ファイルを突き合わせる。あわせて`claude-review`の`allowedTools`から`Bash(gh issue edit:*)`を外し、道具の側でもラベルを付けられないようにしている
  - **理由コメントは重複させない。** `auto-merge`が投稿するのは一次判定（`risk-check`）の理由だけで、二次判定の理由は`claude-review`が投稿済みのものをそのまま使う（マーカーはそのコメントに付いている）
  - **`claude-review-fallback`も`wait-for-ci`を`needs`に加えた。** レビュー失敗時に`00.check-user`を付けるのはこのジョブで、待たないとCIの実行中に同じ時期尚早の通知が飛ぶ。`wait-for-ci`はタイムアウトしても成功する（fail-open）ので、レビュー失敗の通知がこの待機で失われることはない
- **判定が終わるまで画面からマージさせない（#1968）**: 上の#1799で`claude-review-develop.yml`のcheck-runをCI状態の集約から外した結果、**判定が走っている最中でも画面のCI状態は`success`になる**。issue-deckのマージボタンは`mergeWarnings`（`src/lib/pull-request-list.ts`）が空なら確認ダイアログを挟まないため、判定が下る前に**1クリック・警告なしでdevelopへマージできる状態**になっていた。実際にPR #1959（`secrets.WORKFLOW_PAT`で他リポジトリへpushする新規ワークフローの追加）は、PR作成の6分後・`auto-merge`ジョブの6分前に画面からマージされ、`00.check-user`・`01.check-merge`はマージ後に付いた（マージ前の確認として機能していない）。**ワークフロー内の順序（当時は`wait-for-ci`→`risk-check`→`claude-review`→`auto-merge`の直列。現在は後述#2066の並行構成）は壊れておらず、先行したのは画面からの手動マージの方**である。対処として、同じ`statusCheckRollup`から`claude-review-develop.yml`のcheck-runだけを取り出した`mergeJudgement`（`src/lib/github/check-rollup.ts`）を`PullRequestSummary`・`IssuePullRequest`に持たせ、`pending`の間はPR一覧・PR詳細・Issue画面のマージボタンを「判定中」で無効化する（`isMergeJudgementPending`）。
  - **警告ダイアログではなく無効化にした。** 事故は「ダイアログを読み飛ばした」ではなく「ダイアログが出なかった」ために起きているため
  - **この窓の間、人がマージを押す必要は本来ない。** 判定が「自動マージしてよい」ならワークフロー自身がマージし、「確認が必要」なら`00.check-user`が付いて`requiresUserMerge`が真になり、ボタンはまた押せるようになる
  - **判定のcheck-runが1件も無ければ`unknown`で従来どおり押せる。** `claude-review-develop.yml`を配っていないリポジトリ・起動前・チェックが100件を超えて1件ずつ見られない場合が該当する。キャンセル・スキップされたcheck-runは`completed`なので`settled`扱いで、判定が得られないまま画面を塞ぎ続けない（`wait-for-ci`のfail-openと方針を揃えている）
  - **既にマージされてしまった場合の伝え方も直した。** `auto-merge`ジョブの理由コメントと`claude-review`の二次判定コメント（`.github/prompts/review-develop.md`）は、投稿前にPRがマージ済みかを確認し、マージ済みなら「判定が終わる前にマージされている。事後の確認が必要」という文面へ切り替える。**ラベル（`00.check-user`・`01.check-merge`）は従来どおり付ける**——確認が要る変更が入ったこと自体は変わらないため
- **判定中は何を待っているかを画面に出す（#2059）**: 上の#1968で判定中のマージボタンを無効化したが、押せない理由の文言（`MERGE_JUDGEMENT_PENDING_REASON`）を置いていたのは**ボタンの`title`属性だけ**だった。`title`のツールチップはマウスを載せたときにしか出ず、**スマホでは表示手段が無い**。その結果、PR詳細に「CI通過」と灰色の「判定中」が並ぶだけの画面になり、押せない理由も、あと何分待てばよいのかも読み取れなかった（#2059はスマホのスクリーンショットで報告されている）。対処として、CI状態のピルの隣に**待っている段階のピル**（`MergeJudgementBadge`。`src/components/dashboard/pull-request-badges.tsx`）を出す。文言はジョブごとに「CIの完了待ち」（`wait-for-ci`）・「マージ可否を判定中」（`risk-check`）・「Claudeがレビュー中」（`claude-review`）・「自動マージの判定中」（`auto-merge`）で、ピルごとそのジョブの実行ログへのリンクにする。ジョブ名と実行ログURLはCI状態と同じ`statusCheckRollup`の1クエリに`name`・`detailsUrl`を足すだけで取れるので、GitHub APIの消費は増えない。
  - **「CI通過」と「判定中」が並ぶのは矛盾ではない。** `claude-review`は数分かかり、CIより長いことが多い。#2066でレビューをCIと並行させた後も、**「CI通過」が出た後に判定だけが動いている窓は残る**（実測（PR #2056）では`lint-and-build`完了が06:42:11、`claude-review`完了が06:45:03）。この窓を指しているのが判定中のピル。
  - **CI状態へ混ぜ戻す案は採らない。** それは#1799で外した状態そのもので、戻すと自動マージされるPRが一度も「CI通過」を表示できなくなる。CIとは別の軸のまま、別のピルとして並べる。
  - **ボタンは「判定中」で無効のまま。** 追いコミットしたPRでは「ユーザーのマージが必要です」（`00.check-user`）は**1つ前のコミットに対する判定結果**が残っているだけで、いま乗っている変更はまだ判定されていない（`00.check-user`は最後の`auto-merge`ジョブで付く。#1406）。押せるようにすると#1968の事故（未判定コミットの1クリックマージ）が再発する。
  - **段階を特定できないときは「マージ可否を判定中」へ縮退する。** ジョブ名が想定外（`identify-issue`など）・チェックが100件を超えて1件ずつ見られない場合（`mergeJudgement`が`unknown`になり、ピル自体が出ない）。
- **判定とレビューはCIと並行して走らせる（#2066）**: ジョブの依存は`identify-issue` → {`wait-for-ci` ‖ `risk-check` → `claude-review`} → `auto-merge`で、**CIの完了を待つのは実際にマージを有効化する`auto-merge`だけ**。直列だった頃（`wait-for-ci` → `risk-check` → `claude-review` → `auto-merge`）は、直近20実行の実測で`wait-for-ci`が中央値167秒・`claude-review`が中央値235秒（20件中16件で実行）かかり、PR作成から自動マージ有効化まで約7分あった。並行にすると律速がレビュー側だけになり、中央値で約2分半縮む（約7分→約4分）。
  - **Claude Codeの消費は増えない。** `wait-for-ci`はCIのconclusionを見ず`completed`で抜けるため、**CIが落ちたコミットにも並行化の前からレビューは走っていた**（実例: 2026-08-22 07:20のissue-2059はCI失敗・`claude-review`は382秒完走）。増えるのは「CI実行中のpushで走行中のレビューがキャンセルされる分」だけで、直近40実行のキャンセル2件はいずれもpush間隔3分半以上＝並行化の前から走行中だった
  - **マージの安全性は変わらない。** `auto-merge`が使うGitHub Auto-merge機能が`develop`の`required_status_checks`（`lint-and-build`）の通過を待ってから実際のマージを行う。`wait-for-ci`を残しているのは、上の#1406の`00.check-user`付与と理由コメントをCI完了後に揃えるためで、マージの可否のためではない
  - **`auto-merge`の`if`には`wait-for-ci`の結果を書かない。** `needs`の既定は「依存が失敗・スキップなら後続もスキップ」だが、**`if:`を書いた時点でこの既定は上書きされる**ので、`if`に結果を書かなければ待機ジョブが失敗しても後続は走る。「待つが、待てなくても止めない」（fail-open）はこの形で表現している
  - **`wait-for-ci`を完全に削除する案は採らない。** `auto-merge`の`00.check-user`付与がCI実行中に出てしまい、`required_status_checks`を持たないリポジトリでは`gh pr merge --auto`の挙動まで変わる
  - **レビューはCI結果を判定材料にしない。** 並行実行では`gh pr checks`が実行中を返すのが普通なので、`.github/prompts/review-develop.md`には「実行中ならその旨だけ書き、完了を待たない」と書いてある。CI失敗の修正は`claude-ci-fix.yml`の担当
  - **画面のピルは判定側を優先して出す。** `wait-for-ci`と`claude-review`が同時に走るため、実行順で選ぶとレビュー中でも「CIの完了待ち」と出てしまう。CIの進み具合は隣のCI状態のピルが既に出しているので、`JUDGEMENT_STEP_ORDER`（`src/lib/github/check-rollup.ts`）は`risk-check` → `claude-review` → `wait-for-ci` → `auto-merge`の順にしてある
- **`00.check-user`を両判定共通の「マージ保留」シグナルとして使う**: `auto-merge`ジョブは上記の反映を済ませたうえで、対応Issueに`00.check-user`が付いていないことだけを確認して`gh pr merge --auto --merge`（Auto-merge機能。リポジトリ設定で有効化済み）を実行する。判定ロジックとマージ可否判断を疎結合に保つことで、判定方法を追加・変更してもマージ側のロジックは変えずに済む。必須ステータスチェック（`develop`の`lint-and-build`）待ちのポーリングは自前実装せず、GitHub Auto-merge機能に任せる。
- **手動マージ時の`00.check-user`除去**: `00.check-user`が付いたPRは自動マージがスキップされ、人間がPRリンクから手動マージする運用になる。このマージ操作自体が確認完了を意味するため、`.github/workflows/issue-labels.yml`の`develop-pr-merged`・`develop-merge-sweep`・`main-pr-merged`・`main-direct-merged`の各ジョブは、状態遷移とあわせて`00.check-user`も除去する（#266・#1901）。
- **判定経路を持たないリポジトリではPR作成時に付ける（#1470）**: 上の判定は**すべて`claude-review-develop.yml`（caller）を持つリポジトリでしか走らない**。callerが無いリポジトリでは`risk-check`も`auto-merge`も一度も起動せず、自動マージされないのに`00.check-user`も付かないため、develop向けPRが誰にも気付かれないまま開いたまま残る。実測（2026-08-15）では、callerを持つのは`issue-deck`・`dayspan`・`shopping-list`の3つだけで、**他12リポジトリに判定されないままのdevelop向けPRが13本**あった（配布状況は[docs/supported-repositories.md](../supported-repositories.md)「`claude-review-develop.yml`の配布状況」）。そのため`reusable-issue-labels.yml`の`develop-pr-opened`ジョブ（展開済みの全リポジトリが呼ぶ唯一の共通経路）が、PR作成時に`.github/workflows/claude-review-develop.yml`の有無を`gh api`で確認し、**無ければその場で`00.check-user`を付ける**。理由はPR作成通知コメントの末尾に1行足す形で伝える（コメントを増やさないため）。
  - **経路を持つリポジトリでは何もしない。** ここで付けると`auto-merge`ジョブが「`00.check-user`が付いている」と読んで自動マージを常にスキップしてしまう。将来callerを配ったリポジトリでは、この保険は自動的に発火しなくなる
  - **一覧の取得に失敗したときは「経路なし」に倒す（fail-closed）。** 3回リトライしても取れなければ警告を出したうえでラベルを付ける。誤って付いた`00.check-user`は画面から外せるが、付かなかったPRは気付かれずに残り続けるため
  - 外れるタイミングは他の経路と同じで、`develop-pr-merged`・`develop-merge-sweep`・`main-pr-merged`・`main-direct-merged`がマージ時に、`cleanup-on-close`がIssue close時に外す
- **同一PRへの連続pushでのコメント重複防止**: 実装エージェントが追加修正等で同一PRに連続してpushすると、そのたびに`risk-check`ジョブが再実行される。ラベル自体はpushのたびに再付与して確認ゲートを確実に保つが、そのpush開始時点で対応Issueに既に`00.check-user`が付いていた場合はコメント投稿のみ省略する。**この「push開始時点で付いていたか」は`risk-check`が掴んで`already-check-user`出力で渡す**（#1406）。付与を行う`auto-merge`ジョブ側で読み直すと、`claude-review`が二次判定で付けたラベルを見て一次判定の理由コメントを取りこぼす。実装がまだ進行中の段階で同内容の「developへのマージ前にユーザーの確認が必要」コメントが繰り返し投稿され、作業中なのか確認待ちなのか紛らわしくなる問題を防ぐため（#594）。
