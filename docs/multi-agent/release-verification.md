# リリース前の統合検証と全体AIレビュー（#4212）

**いつ読むか**: develop→mainのリリースPR（`release-main/vX.Y.Z`）を本番へマージする前の検証・レビューの仕組みを触るとき。

個別PRのレビュー（develop向けPRの自動レビュー）に加えて、**固定したリリース内容そのもの**に対する検証を足す。
段階的に入れた（PR1＝土台 #4219、PR2＝統合検証 #4237、PR3＝全体AIレビューと画面 #4238）。**強制（`enforced`）は運用検証が済むまで全リポジトリで無効**で、画面は表示のみ。

## 3つの区分と責務

| 区分 | 何を見るか | 担当 | 状態 |
| --- | --- | --- | --- |
| 個別PRレビュー | develop向けPR単位の差分 | 既存の自動レビュー（#4092の「記録なし」判定を含む）。**置き換えない** | 既存 |
| 統合検証 | mainへ統合した状態のビルド・自動テスト | `kind=integration`（PR2） | 実行経路あり |
| リリース全体レビュー | 差分全体の矛盾・退行・設定不足 | `kind=ai_review`（PR3） | 実行経路あり |

AIレビューはテスト実行の代わりにしない。個別レビューの判定を転記して「全体レビュー済み」にもしない。

## 記録（`ReleaseVerification`）

対象キーは**リポジトリ・PR番号・baseSha・headSha・種別**。main更新・head更新・作り直しでSHAが変われば別の行になり、
古い行は現在の対象に流用されない（判定側が「対象変更による無効」にする）。同じ対象への依頼は一意制約で重複しない。

状態は`not_run / waiting / running / passed / failed / needs_check / not_applicable`。
`passed`でも`unverifiedScope`（確認できなかった範囲）が空でなければ`needs_check`として扱い、通常の準備完了にしない。

## マージ判定（`src/lib/release-merge-gate.ts`）

画面とマージAPIが同じ純関数を使う。結果は`ready`／`needs_confirmation`／`blocked`／`not_enforced`。

- **`POST /api/issues/pull-request-merge`のゲートは、base=main・head=`release-main/v*`のPRにだけ掛ける。** develop向けPR・知見昇格PR等は従来どおり。
  マージ直前にGitHubからbase/headを取り直して記録のSHAと突き合わせ、`mergePullRequest`へexpectedHeadShaを渡す
- `blocked`（失敗・未実施・実行中・古い結果）は確認済みにできない。`needs_confirmation`だけが`acknowledgeVerification: true`で通れる（サーバーログに残す）
- **判定の完了待ち（#4354）。** 統合検証・全体レビューが`waiting`／`running`のあいだは、**`enforced`に関わらず**マージAPIが409（`release_verification_pending`）で止める。
  結果（失敗・要確認・古い結果）では止めず、記録が無い（依頼されていない）ものも待たない。報告が来ず待ちのまま止まった場合は`acknowledgeVerification: true`で上書きできる（サーバーログに残す）。判断は`evaluateReleaseVerificationWait`
- **「mainへマージ待ち」は検証が揃ってから出す（#4390）。** 判定の正は`src/lib/release-candidate-status.ts`の1か所で、
  ブランチ画面（畳んだ行・束の見出し・「手が要るもの／待てば進むもの」）、マージボタン、ヘッダーのリリース状況
  （`release-button-status.ts`の`isWaitingUserMerge`）、反映待ち件数・通知ベル（`release-pending-merges`）、本番マージ待ちPush
  （`release-merge-push.ts`）が同じ判定を通す。材料はPR一覧の`releaseChecks`（`fetchReleaseChecks`。DBのみ）で、
  **`enforced`でないリポジトリのリリースPRにも載せる**（完了待ちが強制の有無に依らないため。PR一覧の2枠だけは従来どおり強制時のみ）
  - 実行中・待機中 → 「リリース検証中」「リリース検証待ち」（待てば進む）。マージボタンは「検証の完了待ち」で無効（#4354と同条件）
  - 失敗／設定不足（`describeIntegrationSetupGap`）／要確認／対象変更で無効／未実施（強制時のみ）／取得不能 → 理由付きの問題（手が要る）。
    結果ではボタンを止めない（禁止・例外確認は既存ゲートのまま）
  - 見出しはPR一覧の更新周期に従う。検証の詳細枠（5秒間隔）が状態の変化を見つけたらブランチ画面の再取得を促して揃える
- **AIのLGTMだけで自動マージはしない。** 最終承認は従来どおり人
- 結果による強制は`src/lib/release-verification-config.ts`のリポジトリ別`enforced`で切り替える（上の完了待ちは対象外）。**検証の実行経路が配布されるまで`false`**（未配布を導入済みと扱わない）

### ゲートが及ばない経路

- `deploy-recovery-series-run.ts`の復旧PR自動マージ: 通常のリリースPRではなく、#4006の機械検証が別にある。対象外
- GitHub画面での直接マージ: このAPIを通らないので止められない。**必須チェックの設定で補う**（配布の手作業Issueで追跡し、未設定のリポジトリは「未導入」と明示する）

## API（`POST /api/dispatch/release-verify`）

認証は`POST /api/progress`と同じ共有シークレット。`action`は`request`（行を作り、統合検証のジョブも積む。#4237。全体レビューは統合検証の完了後に開始し、検証中は応答の`aiReview`が`deferred`になる。#4763）・`report`（結果を記録。依頼の無い対象には書かない）・`status`（現在のSHAでのゲート判定）。

## 統合検証の実行（#4237・PR2）

- `request`を受けると`requestReleaseVerifyJob`（`src/lib/dispatch/release-verify-jobs.ts`）が`DispatchJob`（`RELEASE_VERIFY`）を積む。
  `activeKey`は`release_verify:owner/repo#PR@base:head:integration`。PR番号・base/head SHAは`PR_REVIEW`と同じ専用列で、`issueNumber`はPR番号の埋め草。
  対象が変わると古い待機中ジョブは取り消し、旧SHAの結果は`viewReleaseVerifications`が「対象変更による無効」にする
- **実行内容はサーバー設定が正。** `release-verification-config.ts`の`integrationCommands`（と`macBuildCheck`）をジョブ表示の`releaseVerify`としてpollerへ渡す。
  **コマンドの無い・対象外理由のあるリポジトリはジョブを積まず`not_applicable`（理由付き）で記録**する（他リポジトリへ`pnpm`前提を流用して誤った成功を出さない）
- サブPCのpoller（`DISPATCH_POLLER_VERSION=35`以降・`releaseVerify`を申告）が`scripts/run-release-verify.sh`をtmuxで起動する。
  mainの先端へリリースheadをマージした一時worktreeで、コマンドを順に実行する。競合・失敗は`failed`、完走は`passed`
- 既存CI（`ci.yml`のhead SHA成功）は証跡URLとして再利用するが、統合状態のビルド・テストの代わりにはしない。サマリは実施／未実施／対象外を行ごとに残す
- Mac検証: `ios/`に差分があるときだけ`ios/scripts/remote-build-check.sh`を実行する。差分なしは対象外、スクリプト無し・Mac未接続は**成功にせず`unverifiedScope`付きの`passed`（＝要確認）**
- 結果は`/api/dispatch/report`の`releaseVerification`として届き、記録先はジョブの対象で決まる（ランナーは別の対象へ書けない）。完走しても結果が無ければ`failed`
- リリースワークフロー（`reusable-release-develop-to-main.yml`）がPR作成直後に`request`を送る。ベストエフォートで、依頼できなくてもPR作成は止めない。**配布先へはタグを配るまで届かない**

## 全体AIレビューの実行（#4238・PR3）

- `request`は統合検証の後に`requestReleaseReviewAfterIntegration`（`src/lib/dispatch/release-review-start.ts`）を呼び、統合検証が終わっていれば`DispatchJob`（`RELEASE_REVIEW`）を積む（検証中は待たせる。下の「統合検証の完了後に全体レビューを開始する（#4763）」）。
  `activeKey`は`release_review:owner/repo#PR@base:head`。積めない理由（能力ホスト無し・Codex未対応）は**`ai_review`を`failed`（理由付き）で記録**する
- **担当は`resolveReleaseReviewAssignee`（`src/lib/release-review-assignee.ts`）。** 設定の「アプリ内AI：原因診断・新規アプリ相談」（`appAiModelReasoning`）に従い、
  OpenAI系ならCodex、それ以外はClaude Code。AIモデル設定画面は同じ関数で実効担当を表示する。モデルは`DispatchJob.claudeModel`／`codexModel`に載り、結果の`agent`（`claude:opus`など）として記録される
- サブPCのpoller（`DISPATCH_POLLER_VERSION=36`以降・`releaseReview`を申告→`DispatchHost.releaseReviewCapable`）が`scripts/run-release-review.sh`をtmuxで起動する。
  `base...head`の差分を読み取り専用のAI（Claudeは`Read`・`Grep`・`Glob`のみ許可）へ渡す。
  **差分は1バッチ既定300,000文字（`ISSUE_DECK_RELEASE_REVIEW_DIFF_BUDGET_BYTES`）でバッチに分けて順に確認し、容量を超えた分も黙って除外せず次のバッチで確認する**（#4615）。
  1ファイルが上限を超えるときは断片に分け、全断片の確認が揃って初めて確認済みになる。全バッチの後に、バッチをまたぐ相互作用（`pr_interaction`ほか）を別に確認し、
  バッチごとの合格の単純集計で済ませない
- **複数バッチの項目の集計（#4768）**: 以前は「全バッチ＋相互作用の確認」の`batch_count+1`件がそろって全部が確認済み・非該当でないと未確認にしており、
  1つのバッチが`host_compat`を非該当でなく未確認と書いただけで項目全体が未確認になっていた。いまは`merge_batch_results`が次の順で決める
  - **相互作用の確認が根拠つきで報告した結果を優先する**（確認済み・非該当・未確認のどれでも。バッチの結果を見たうえでリリース全体として判断したもののため）。
    バッチ側の未確認を確認済み・非該当で上書きしたときは、根拠の末尾に「／バッチ側の未確認: バッチN: 理由」を併記する（#4769）
  - 相互作用の確認が報告していない・根拠が空の項目は、バッチごとの報告から決める。全バッチが根拠つきの確認済み・非該当なら確認済み（混在は確認済み、全部が非該当なら非該当）。
    報告の無いバッチ、未確認・根拠なしと報告したバッチが残るときだけ未確認にし、根拠に「バッチN: 理由」を並べる（Nは実際のバッチ番号。途中のバッチの結果が欠けても番号はずれない。#4769。証跡待ちの文言はそのまま残るので、自動再評価の判定は変わらない）
  - 分割しない（1バッチ）ときは従来どおりそのバッチの報告で決まる。確認項目の内容は変えていないので、確認項目の版（v2・#4765）は上げていない
- **入力へ載せた数と確認した実績は別物。** ランナーは`inputFiles`（入力へ載せた数）・`targetFiles`・`fileReviews`（ファイルごとの`reviewed`＋根拠／`unreadable`＋理由）を報告し、
  `reviewedFiles`は申告しない。**サーバー（`normalizeCoverage`）が、対象に含まれ根拠のある`reviewed`だけを確認済みと数える。** 入力に載っていても根拠の無いファイルは未確認、
  差分を取得できないものは取得不能として別に数える。ファイル別の実績を持たない旧結果は件数不明（`reviewedFiles=null`・画面は「実績不明」）
- **パスの正規化と取りこぼしの補完（#4768）**: AIが`./src/a.ts`・`/src/a.ts`・`src\a.ts`・作業ディレクトリの絶対パスで報告しても、照合の前に差分のパスへ揃える
  （ランナーの`JQ_NPATH`とサーバーの`normalizeReviewPath`。作業ディレクトリの除去はランナーだけ）。それでも報告の無い・根拠が空のファイル
  （取得不能と報告されたものは除く）が残ったら、全バッチの後に**そのファイルの差分だけを載せた補完の質問を1回だけ**行う（分割したファイルは取りこぼした断片だけを載せる）。
  上限は対象`ISSUE_DECK_RELEASE_REVIEW_SUPPLEMENT_MAX_FILES`（既定40ファイル）・差分`DIFF_BUDGET_BYTES`・時間`ISSUE_DECK_RELEASE_REVIEW_SUPPLEMENT_TIMEOUT_SECONDS`（既定600秒）で、
  入らなかったファイルは聞き直さない。補完が失敗しても全体レビューは失敗にせず、**補完しても残ったファイルだけが`unverifiedScope`の未確認に入る**。
  補完の結果は`rsup.json`（聞き直した一覧は`rsup.asked`）へ保存し、同じ対象の再実行では再利用する（バッチを1つでもやり直したら補完もやり直す）。補完で確認済みになった数は`supplementedFiles`。
  補完の応答の確認項目は集計に使わず、指摘だけを合わせる
- **中断・再開**: バッチごとの結果はサブPCの作業ディレクトリ（`*.batches`、対象のbase・head・予算で一意）へ保存する。1起動の実行バッチ数の上限
  （`ISSUE_DECK_RELEASE_REVIEW_MAX_BATCHES_PER_RUN`、既定8）か、バッチ・相互作用の確認の失敗で止まったときは残りを保存し、同じ対象の再実行が続きから確認する。
  残りがある結果は`pendingBatches`が付き、確認項目は確認済みにならない。候補のSHAが変わると別の保存になり、旧SHAの結果は使わない（現在の結果へ書き換えない）
- **完走後も保存を残し、確認済みのバッチを再利用する（#4767）**: 以前は完走時に`*.batches`を消していたため、再評価（#4664）・手動の再実行（#4632）が
  全バッチと相互作用の確認を最初からやり直し、画面の「確認済みは再利用」と実装が食い違っていた。いまは完走後も`r<N>.json`・`r<N>.fp`を残し、
  掃除は起動のたびに`prune_batch_dirs`が行う（3日より古いもの＋新しい順に`ISSUE_DECK_RELEASE_REVIEW_KEEP_BATCH_DIRS`件〈既定20〉を超えた分。使用中の保存は`touch`して最新にしてから消す）。
  再実行でやり直すのは「証跡に依存し、指紋が変わった（取れない）バッチ」と「確認項目の版が今と違うバッチ」だけで、それ以外は再利用する。
  **バッチを1つでもやり直したら、相互作用の確認もやり直す**（保存済みの相互作用は古いバッチ結果に基づくため）。結果には`reusedBatches`（AIを呼ばずに再利用した数）・
  `rerunBatches`（今回確認した数）・`integrationReused`を載せ、画面の「確認した範囲」に「再利用N／再確認Mバッチ」と出す（旧ランナーの結果は記録なし＝表示しない）。
  同じ証跡・同じSHAの再実行はAIを1回も呼ばない（`scripts/run-release-review.test.mjs`の「完走後の再利用」で呼び出し回数を固定している）
- **バッチの並列実行とターン数の上限（#4769）**: 確認するバッチは`ISSUE_DECK_RELEASE_REVIEW_PARALLEL`（既定3。1で従来どおり1本ずつ）本まで同時に起動する。
  起動は番号順で、実行予算（`MAX_BATCHES_PER_RUN`）で残るのは従来どおり後ろのバッチ。各バッチは自分の作業ディレクトリ（`.parts/b<N>/`）でプロンプト・出力・ログを持ち、
  成功したものだけが`r<N>.json`（指紋`r<N>.fp`を先に書く）へ保存される。**1本でも失敗したら新しいバッチは起動せず、実行中のものの完了を待って保存してから、番号の最も小さい失敗を報告する**
  （再実行は保存済みを再利用し、失敗・未起動のバッチから続ける）。相互作用の確認・実績の補完は従来どおり全バッチの後に1本だけ走る。
  進捗の分母は全バッチ数に揃え、完了は再利用ぶんを含めて「バッチ2・3・4/5を並列で確認中・完了2/5（再利用1）」のように出す（`batch_progress_message`・`batch_running_label`。#4785）。
  1本でも失敗したあとは新しいバッチを起動しないので、文面は「失敗したバッチがあり、実行中のN本の完了を待っています」に変わる。想定外の終了では`cleanup`が起動したバッチのプロセス木（`timeout`・AI CLI）を止める。
  終了の待ち方は、bash 5.1以上なら`wait -n -p`が返す**終了したジョブのPID**で回収する（PIDの再利用の影響を受けない。#4785）。heartbeatも同じシェルの子ジョブなので、返ったPIDが起動したバッチのものでなければ無視して待ち直し、
  成否は`$jd/rc`で判定する（`&`で起動したサブシェルは親の`EXIT`トラップを実行しない）。サブPCのbashは5.2.21で使える。5.1未満では従来の方式（起動したPIDを`kill -0`で0.5秒ごとに見て、終わったものだけ`wait <pid>`で回収）に戻る。
  テストの偽claudeは、呼ばれた順ではなくプロンプトのバッチ番号で応答を決める（並列だと呼び出し順のカウンタが競合して結果が揺れるため）。
  claudeには`--max-turns`（`ISSUE_DECK_RELEASE_REVIEW_MAX_TURNS`、既定300、0で指定しない）を渡す。上限に達するとclaudeは**標準出力（最終応答）へ**`Error: Reached max turns (N)`と書いて
  終了コード1で終わる。`diag_ai_cause`は**ログ（stderr）か最終応答の最後の非空行が行頭からこの1行の形のときだけ**`turn_limit`とする（#4785。レビュー本文に引用された文字列では判定しない）。
  `turn_limit`で失敗したバッチだけ、上限を`ISSUE_DECK_RELEASE_REVIEW_RETRY_MAX_TURNS`（既定500）・時間を`ISSUE_DECK_RELEASE_REVIEW_RETRY_TIMEOUT_SECONDS`（既定3000。ターン数だけ上げても時間の上限に先に当たるため）に上げて**1回だけ自動でやり直す**。
  やり直しても同じなら失敗として報告し、診断に`turnLimitRetried`と`maxTurns`を載せる。画面は「まず再実行」ではなく、原因（バッチが大きい・上限が小さい）と次の操作（`DIFF_BUDGET_BYTES`を下げる／上限を上げる）を案内する。
  既定を300にした根拠は、時間上限1800秒に対し1ターン約6秒前後で、150では大きいバッチ（差分30万文字・ファイル一覧300件）で届きうるため。実際に使ったターン数は、claudeの`-p`の標準出力がテキストだけで取れないので残せない（やり直したことと適用した上限だけを残す）。
  デプロイはサーバー（診断の新フィールドを受ける側）が先、その後サブPCのpollerを更新・再起動する。pollerが古いままでも従来の挙動（上限150・再実行の案内）で動く。
  Codex CLIの`exec`にはターン数を指定する引数が無いので、Codexは時間（`TIMEOUT_SECONDS`）だけで止める。
  - 相互作用の確認を省く条件は従来どおり`batch_count > 1`で足りる（複数バッチになるのは差分が1バッチの予算を超えたときだけなので、差分が小さいときは必ず1バッチ）。1ファイルが予算を超えて断片に分かれた場合は、断片同士が互いを見ていないため相互作用の確認を残す
  - 毎バッチ載せ直している全ファイル一覧（最大300件）と再レビューの修正差分（最大100KB）は**絞らない**。修正差分を各バッチの担当ファイルへ絞ると、前回の指摘（`previousFindings`）のファイルを持たないバッチが修正を見ずに`unresolved`と報告し、集計が`unresolved`を優先するため解消済みの指摘が残ってしまう。全ファイル一覧は呼び出し元を探す手がかりで、差分本文（1バッチ既定300,000文字）に比べて小さい
- 結果の正規化（`src/lib/release-review-result.ts`）: **指摘が1件でもあれば`needs_check`、確認範囲が足りなければ未確認範囲つきの`passed`（判定側が理由付きの`needs_check`へ読み替える）。**
  AIが問題なしでも指摘・未確認が無い場合だけ`passed`。`failed`はレビューを完走できなかったときだけ。結果には対象SHA・担当AI・指摘・影響PR・影響ファイルを残す
- **AIのLGTMだけで自動マージはしない。** マージは従来どおり人で、`needs_confirmation`は理由付きで既存の明示確認フローへ渡る

## リリース画面の3区分

PC（リリースPR詳細）・スマホ（リリースシート）・**本番マージの確認ダイアログ**（#4277）で、同じコンポーネント
（`release-review-sections.tsx`の`ConnectedReleaseReviewSections`）が上から「全体レビュー／統合検証／個別PRレビュー」を並べる。
**並びは表示の優先順位で、実行順序や依存関係ではない。** 全体レビュー（AIによるリリース差分全体の確認）と統合検証（mainへ統合した状態の
ビルド・自動テスト。AIではない）は互いを代替せず、個別PRレビューは既存の「今回反映する内容」（`useReleaseChanges`）の集計で、
他の2区分の結果で置き換えない。凍結ブランチ（`release-main/*`）のリリースPRにだけ出す。

**PCのリリースPR詳細（本番PR詳細）だけは並べ方が違う**（#4428）。正式タイトルの後に「現在の状態と次の操作」→「現在候補の検証」
（6チェック＋3区分）→「今回リリースする変更」→修正履歴→既存のバッジ・本文・コメント（詳細・履歴）の順に置き、主操作
「本番公開へ進む」は既存の本番マージ確認を通る。部品は`release-pull-request-overview.tsx`で、要約・今回の変更・履歴は
`release-fix-panel.tsx`の`useReleaseFixOverview`と分割した部品を並べ替えて使う（判定は`describeFixOverview`のまま）。
修正→取り込み→再検証→公開の工程は修正系列があるときだけ出す。ブランチ画面は開いたリポジトリの先頭に「次のリリース」
カード（本番稼働中・次のバージョン・反映PR件数、状態・主操作・検証）を置き、束の見出しからは操作と検証を外し、作り直し履歴を流れ図の下へ移した（#4721でブランチ画面からは外した。モバイルのリリースシートには残る）。

- **形式**: どの区分も「見出し＋短い説明＋状態の1行」。閉じたままで状態・現在の工程・経過時間・指摘の有無と短い理由が読め、
  総評・指摘・実施内容・証跡・PR別の一覧は開いて読む。未実施・待機・取得失敗を緑や「問題なし」にしない
- **確認ダイアログ**: 旧「マージ前の確認」と「このリリースに含まれる変更」の独立した枠は出さず、「リリースの検証」1枚に
  まとめる。CI・コンフリクトは枠の末尾の1行（`buildCiConflictRows`）、変更一覧は個別PRレビューを開いた中。旧「Claudeのレビュー」行は
  個別PRレビューへ統合した（判定の材料は区分と同じ各PR本文）。旧世代のリリースPR（head=develop）は従来の表示のまま
- **取得**: `GET /api/repositories/release/verification`と`GET /api/repositories/release/changes`を部品自身が取り、待機・実行中は5秒間隔、
  取得に失敗しても間隔を空けて取り直す。「更新」で両方を取り直す。スマホのシートも同じ取得を使う

### 全体レビューの指摘と実行失敗の区別（#4300）

`ai_review`の**指摘（コードへの問題）**と**実行失敗（レビューを最後まで行えなかった）**は別物として扱う。

- 指摘: `findings`に重要度・概要・影響・根拠・推奨対応・ファイル／行・関連PRを持ち、画面は件数と最重要の題を閉じたまま、詳細を開いて出す。要修正は従来どおり「developへ入れて作り直す」
- 実行失敗: `state=failed`のとき、`findings.diagnostic`（`stage`・`cause`・`exitCode`・機密除去済み`excerpt`・対象base/head SHA）を持つ。画面は「レビュー未完了」と出し、失敗した工程・確認できた原因・次の操作・エラー抜粋（tmuxが無くても読める）を示す。**作り直しは勧めず、「全体レビューを再実行」が主導線**
- 原因（`cause`）は`launch_failed`（終了コード126/127・CLI無し）／`auth_failed`（ログに認証エラー表示）／`timeout`（124/137）／`turn_limit`（AI CLIがターン数の上限に達した。#4769）／`parse_failed`／`target_missing`／`no_host`／`unknown`。**観測できた事実だけで決め、決められなければ`unknown`（原因未特定）**。126だけから権限問題などと断定しない
- 診断は対象SHA付きで保存し、現在のSHAと一致するものだけを表示する（旧実行の原因を現在の結果に見せない）。機密は実行側（`scripts/run-release-review.sh`の`diag_redact`）とサーバー（`redactDiagnosticText`）の両方で伏せ、末尾30行・2000文字までしか持たない。生ログ全文は出さない
- 再実行: `POST /api/repositories/release/review-rerun`。ガードは作り直しと同じ（`previewModeGuard`→`requireUserId`→リポジトリ所有確認）。対象はサーバーが今のリリースPRから解決し、クライアントのSHAは一致確認だけに使う。`activeKey`で実行中・待機中の二重起動を防ぎ、積めたときだけ`ai_review`を`waiting`へ戻して旧診断・指摘を消す
- **未確認範囲・検証結果待ちからの再実行（#4632）**: 再実行は実行失敗（`failed`）だけでなく、確認範囲不足・検証結果待ち（`needs_check`）からも「次の操作」として詳細を開かずに見える（`release-review-rerun-view.ts`の`describeReviewRerun`が出し分け、候補詳細・本番PR詳細・スマホシートは共通欄なので揃う）。**統合検証が`waiting`・`running`の間は押せず（APIも`integration_pending`で409）、途中の証跡で再評価しない。再実行のために統合検証を起動することもしない。** 受付は「合格」ではなく、画面は待機→実行中→完了を表示する。旧結果は新テーブルを作らず`findings.previousRun`（直前1件）へ退避して履歴として見せる（完了後も引き継ぐ）。前提は「コードの確認（読み残し）」「統合検証」「運用状態の確認」に分けて出す（#4665）
- **poller更新・再起動の要否は稼働情報と照らして決める（#4665）**: 以前は`/poller|ポーラー|再起動/`の一致だけで「更新が必要・再実行では解決しない」と出していた。判定は`release-review-ops-evidence.ts`が持つ。
  - **要求か言及か**: 未確認の理由・未確認範囲・未確認の確認項目の根拠から、更新・再起動を**要求する文**だけを拾う（`findOpsRequest`）。互換性の確認・「更新済み」「更新不要」「サーバーのみで有効」の文、確認済みの項目・要約の言及は数えない。要求が無ければ運用状態の行自体を出さない
  - **issue-deck自身の候補**: 候補（main…head）にサブPCへ届くファイル（`scripts/`）が無ければ「サーバー側だけで有効・更新不要」。有れば、オンラインのホストの**起動時コミット**（`checkoutStartedCommit`＝いま走っているコード）が候補headを含むかをGitHubのcompareで照合し「更新済み／更新が必要」。pollerは`develop`を追うので公開前でも更新でき、公開後にしかできない配布を公開前の条件にする循環は起きない。公開前に必須とするのは、レビューが非互換（旧版では動かない）を根拠に書いたときだけ
  - **他リポジトリの候補**: pollerのコードは候補に含まれない。`checkoutBehind`はissue-deckの`develop`基準の遅れでこのリポジトリの公開と無関係なので使わず、そのリポジトリを申告するホストの`releaseVerifyCapable`・`releaseReviewCapable`だけで決める
  - **確認できない**: ホスト未申告・全ホストオフライン・changed filesが取れない（compareは300件で打ち切られるので上限到達も含む）・照合失敗は「状態を確認できない」にし、更新必須にも更新済みにもしない。**統合検証の成功では運用状態を確認済みにしない**
  - 稼働情報（DBのホスト申告・最後の`SELF_UPDATE`成功・GitHub API）は、全体レビューが`needs_check`かつ要求があるときだけ`loadReleaseVerificationSummary`が読む（5秒ごとのポーリングで毎回GitHubを叩かない）。次の操作は既存の「更新して再起動」・自動更新（#4118）の案内だけで、再起動処理は足していない。根拠に`#番号`があれば関連Issueとして出し、新規起票はしない
  - ランナー（`run-release-review.sh`）はpollerが公開する`POLLER_STARTED_COMMIT`から「いま走っているpollerの版」と「候補headを含むか」を検証証跡の節へ書き、`host_compat`で互換性と実機の更新を書き分けるよう指示する（同じ更新要求を再レビューで繰り返させない）。この部分はpollerの更新後に有効
- **証跡の更新に伴う再評価（#4632）**: `run-release-review.sh`は保存した各バッチ結果と、そのときの統合検証の証跡の指紋（`evidence_fingerprint`＝結果状態・終了時刻・工程数）を`r<N>.fp`へ残す。再実行時、**証跡に依存する結果だけ**、指紋が変わった・取れなかったときに捨てて再評価し（相互作用の確認も一緒に捨てる）、それ以外は再利用する。
  **「証跡に依存する」は、根拠の文言が実行結果の証跡（統合検証・テスト・型検査・ビルド・`running`など）を指す未確認の項目・未確認範囲だけ**（#4767）。
  poller更新のような運用作業の未確認・観点の読み残しは、統合検証が終わっても変わらないので依存に数えない（根拠の文言が空の未確認だけは、何に依存するか分からないので依存側へ倒す）。
  語の一覧はランナーの`EVIDENCE_TEXT_PATTERN`とサーバーの`EVIDENCE_TEXT`（`src/lib/release-review-reevaluation.ts`の`reviewDependsOnEvidence`）で同じものを持ち、**変えるときは両方を揃える**。
  - **運用（pollerの更新・再起動）の未確認は、ホストの事実で見直す**（#4799）。未確認の根拠・範囲が`HOST_TEXT_PATTERN`（TS側`HOST_TEXT`・`reviewDependsOnHost`）に当たる保存済みの結果は、保存時のホスト指紋（pollerの起動時コミット・候補を含むか。`*.hfp`）が今と違う、または指紋が無いときに捨てて、`runner_host_prompt_text`入りのプロンプトで再実行する（相互作用の確認も同時に捨てる）。統合検証の完了では変わらないので、自動再評価の契機（`reviewDependsOnEvidence`）には数えない。
  証跡に依存しない未確認は、要確認の内訳で`check_unconfirmed`（「証跡に依存しない未確認の確認項目」）として出し、統合検証の待ちと混ぜない。保存時の指紋が無い旧い保存も依存結果は再評価する。この変更はpollerの更新後に有効

### 統合検証の完了後に全体レビューを開始する（#4763）

以前は統合検証と全体レビューを同時に積んでいたため、1回目のレビューは証跡の無い状態で走って確認項目を`unconfirmed`にし、統合検証の完了後に同じSHAで全体レビューがもう1回走っていた（下の#4664の自動再評価）。**自動で全体レビューを積む経路は、同じ対象（PR・base・head）の統合検証が終わってから開始する。**

- **対象の経路は4つで、すべて`requestReleaseReviewAfterIntegration`（`src/lib/dispatch/release-review-start.ts`）を通る。** 候補作成・revision更新（`release-rc-run.ts`）、正式バンプ後の再検証（`release-finalize-run.ts`）、`release-verify`の`request`。どれも統合検証を先に依頼してから呼ぶ。画面の手動再実行（#4632）は従来どおり`rerunReleaseReviewJob`を直接呼び、統合検証の待機中は受け付けない
- **判定は純関数`decideReleaseReviewStart`（`src/lib/release-review-start.ts`）だけが持つ。** 待つのは次の2つのときだけで、それ以外は開始する（永久に待たない）。
  - 同じ対象の統合検証ジョブが動いている（`QUEUED`・`CLAIMED`・`RUNNING`）
  - 統合検証の記録は`waiting`だがジョブがまだ無く、依頼から猶予（10分）以内（依頼の直後。過ぎたら積めなかったとみなす）
  - 開始する例: 統合検証の記録が終わった（`passed`・`failed`・`needs_check`。失敗でも開始し、その結果をレビューに評価させる）／記録が無い（正式バンプで統合検証を引き継いだ・未依頼）／`not_applicable`／ジョブが報告なしで終わった（期限切れ・取り消し）／積めなかった（ホスト無し・設定不足は`failed`が記録される）
- **待つ間は、全体レビューの記録を`waiting`のまま`findings.awaitingIntegration`（`since`）の印を付ける。** 画面の段階は`awaiting_integration`（「統合検証の完了待ち」）で、候補の状態（`release-candidate-status.ts`）は開始待ちとして段階名を出す。マージの完了待ち（`evaluateReleaseVerificationWait`・#4354）は従来どおり`waiting`の全体レビューを待ちとして返すので、新しい状態と矛盾しない。統合検証の完了後に開始されるまでの短い間は「全体レビュー中」と出す
- **開始の契機は2つ。** 統合検証の完了報告（`/api/dispatch/report`の`RELEASE_VERIFY`。#4664の再評価判定より先に呼ぶ）と、pollerの`claim`ごとの巡回（`sweepDeferredReleaseReviews`。1分に1回まで・直近3日・50件まで。報告の反映失敗・再起動・猶予切れを拾う）。**50件に数えるのは印付きでcurrentな対象だけ**で、印の無い待機中の記録（候補の更新で取り残された古いSHAの記録など）と古い対象はページを読み進めて読み飛ばす（1回に読むのは2,000件まで。#4775。以前は待機中の記録を新しい順に50件取ってから絞っていたため、それらで50件が埋まると待っている対象を拾えない回があった。印はJSONの中身なのでクエリ側では絞らず、current判定もクエリでは書けないため）。印の無い記録・結果の出た記録には触れず、古い対象（`isCurrentReleaseReviewTarget`。#4664と共用）は開始しない——積むと同じPRの新しい対象の待機中ジョブを取り消してしまうため
- **ホストは統合検証を実行したホスト（そのジョブの`targetHost`）を優先する**（`requestReleaseReviewJob`の`preferredHost`）。「実行した」とみなすのはホストがジョブを取得した（`claimedAt`がある）ものだけで、ジョブの状態では判定しない——`TIMEOUT`は`QUEUED`のまま期限切れになり一度も動いていないジョブも含み、そのホストに証跡は無いため（#4775）。不適格（オフライン・未対応・Codex未対応）なら従来の選び方（名前順の先頭）へフォールバックし、それも無ければ従来どおり`ai_review`へ失敗（`no_host`）を記録する。#4664の再評価が使う`requiredHost`（不適格なら積まない）とは別の指定
- **#4664の自動再評価は残す。** 通常経路ではレビューのジョブ開始が統合検証の完了より後になるので、`decideReviewReevaluation`は`used_latest_evidence`を返して発火しない。統合検証をやり直した（新しい完了が来た）・旧サーバーで並列に積まれた対象のときだけ働く

### 統合検証の完了後の自動再評価と共通の段階（#4664）

統合検証と全体レビューは、#4763までは並列で積まれていた（現在は上の節のとおり、統合検証の完了後に開始する）。レビューが統合検証の実行中の証跡（`running`）を読んで終わると、#4632までは「全体レビューを再実行（証跡を更新）」を手で押す必要があった。**再評価を「いつ積むか」はサーバーが決め、手動の再実行は回復用に残す。**

- **判定は純関数`decideReviewReevaluation`（`src/lib/release-review-reevaluation.ts`）だけが持つ。** 積むのは次の3つがすべて揃ったとき。
  - 統合検証が終わった（`passed`・`failed`・`needs_check`）。`failed`・`needs_check`はその結果をレビューに評価させるために積み、`passed`へ読み替えない。`not_applicable`・未依頼・結果待ちでは積まない。
  - その完了より前に始まったレビューが、証跡に依存する未確認を残して完走した。依存の判定は`reviewDependsOnEvidence`で、未確認の確認項目、または実行結果を指す未確認範囲があることを条件にする。重大指摘が混在していても積む。実行失敗の診断がある結果では積まない。
  - 同じ統合検証の完了では、まだ積んでいない。
- **呼ぶ場所は3つ（`src/lib/dispatch/release-review-reevaluate.ts`）。どれが先に来ても結論は同じになる。**
  - 統合検証の完了報告: レビューが先に終わっていた場合。
  - 全体レビューの完了報告: 統合検証が先に終わり、レビューは開始時の古い証跡を読んでいた場合。
  - pollerの`claim`ごとの巡回: 1分に1回まで。直近24時間・20件まで。報告の反映の失敗や再起動で抜けた判定を拾う。
- **重複・無限再評価を止める仕組みは3つ。**
  1. ジョブの`activeKey`: 手動再実行・重複報告と同じ対象を二重に積まない。
  2. 記録の印`findings.autoReevaluation`: 契機にした統合検証の完了時刻を持ち、結果にも引き継ぐ。
  3. 「レビューのジョブ開始が統合検証の完了より後なら最新の証跡を読んでいる」という比較。
  - この3つにより、同じ証跡で指摘が残るだけなら繰り返さず、「自動再評価済み・対応／判断が必要」として残件を出す。新しい統合検証が完了したときだけ、もう一度積む。
- **積み先は、統合検証を実行したホスト（その`RELEASE_VERIFY`ジョブの`targetHost`）に限る。** 証跡はそのホストのローカルファイルで、別ホストでは読めない。
  - そのホストが不適格なときは、`ai_review`へ失敗を記録せずに見送る（`requestReleaseReviewJob`の`recordNoHost: false`）。有効な`needs_check`を「失敗」で上書きしない。見送った分は巡回で再試行する。
- **現候補の判定はDBだけで行う。** 同じPRにより新しい対象の記録があるときは積まない（候補の更新・mainの前進・正式バンプ後への移動）。新方式の候補が進行中でない（取消・本番反映後）ときも積まない。
  - 正式バンプ後の最終検証（`finalHeadSha`）も同じ対象として扱う。
- **自動で積んだ再評価が報告なしで終わったときは、`fail_stalled`で`failed`へ戻す。** 取り消し・期限切れのケースで、「確認中」のまま残さず手動の再実行へ戻すため。書き換えは状態を条件にするので、先に届いた結果は上書きしない。
- **再評価はレビュー結果を記録し直すだけ。** 修正Issue・PR・候補・版は作らず、公開承認も作らない。公開への復帰は既存の公開系列が判定する。
- **画面の共通の段階は`describeReviewEvidenceStage`が出す。** 要約の`aiReview.stage`と、PR一覧の`releaseChecks.aiReviewStage`に載る。
  - 段階は「コード確認済み・統合検証待ち」「検証結果を確認中」（自動再評価の開始待ちを含む）「全体レビュー完了」「要確認」の4つ。
  - 要確認には残件の種類を添える。種類は「指摘」「運用作業（poller更新・再起動）の証跡待ち」「統合検証の失敗・要確認」「取得不能・未実施」「実行結果待ち」「コードの未確認範囲」で、互いに区別する。
  - この段階を使う表示は、上部バッジ（`release-stage-badges.ts`）、候補の状態（`release-candidate-status.ts`・`deriveRcStatus`）、本番PR詳細の概要帯（`release-fix-overview.ts`）、全体レビュー欄、バンプ後の再検証（`describeReverifyItems`）。
  - 統合検証が完了した後は「統合検証中」と出さない。
  - 検証詳細は、段階が待ち・確認中の間もポーリングを続け、段階の変化で一覧を取り直す。
  - poller更新の必要性の根拠表示は#4665で扱う。ここでは、更新の要求を再評価の開始条件にしていない。

### 検証証跡のAIレビューへの受け渡しと失敗種別の区別（#4616）

全体レビューのAIは読み取り専用で、依存関係もテスト環境も持たない（`node_modules`が無くvitestを実行できず「要確認」を繰り返した）。**テストの実行をAIへ丸投げせず、統合検証ランナーが設定済みコマンド（`integrationCommands`。issue-deckは`pnpm install --frozen-lockfile`が先頭）を実行した結果を、AIの入力として渡す。**

- 証跡: `scripts/lib/release-evidence.sh`。`run-release-verify.sh`が、リポジトリ・PR・base/head・統合対象・コマンド・成否・終了コード・日時・失敗時のログ末尾を、対象（base/head）ごとのJSONへ残す（`ISSUE_DECK_RELEASE_EVIDENCE_ROOT`、既定は`$TMPDIR/issue-deck-release-evidence`）
- **head単体と統合状態を混ぜない。** 証跡は統合状態（main base＋release head）のものだと明記し、head単体は「未実施」と書く。合格で代用しない
- 全体レビュー（`run-release-review.sh`）は、**base/headが完全に一致する証跡だけ**をプロンプトの「検証証跡」へ入れる。候補の更新・mainの前進でファイル名が変わるため旧証跡は再利用されない。無い・実行中の場合は「未実施」として渡し、**コードの不具合の根拠にしない**（実行結果が要る項目は`unconfirmed`＋`unverifiedScope`）。AIの権限（Codexはread-only、ClaudeはRead/Grep/Glob）は変えない
- 失敗種別`failureKind`（統合検証の結果JSONに追加。旧サーバーは無視する）: `merge_conflict`（競合ファイルを併記・統合状態の検証は未実施）／`dependency_install_failed`（`pnpm install`・`npm ci`・`pip install`等の失敗）／`setup_missing`（終了コード126/127）／`timeout`（124/137）／`test_failed`（テスト・型検査・ビルドの不合格）／`duplicate_run`。**取得失敗・設定不足・時間切れを`test_failed`（コード不具合）に置き換えない**
- 二重実行: 同じ候補（base/head）の証跡に隣接するロック（PID）で、進行中の統合検証がある間は2本目を開始せず`needs_check`（`duplicate_run`）で返す。PIDが生きていなければロックを引き継ぐ
- **未対応（別Issueで扱う）**: サーバー側が`failureKind`を画面・復旧系列（#4451/#4480）へ接続すること。全体レビューを統合検証の完了まで待たせる順序制御は#4763で実装した（上の「統合検証の完了後に全体レビューを開始する」）。証跡が無い場合（統合検証を引き継いだ・積めなかった）は従来どおり「未実施」としてレビューへ渡す

### 進捗（#4277）

結果（`ReleaseVerification`）とは別に、**現在の対象（base・head）の**最新ジョブ（`DispatchJob`）から進捗を作る
（`lib/release-verification-progress.ts`・`release-verification-load.ts`）。対象の違うジョブは見ないので、作り直す前のSHAの
工程・成功を現在の進捗に見せない。**進捗はゲートの判定に使わない**（記録が`waiting`でジョブが`RUNNING`なら表示だけ「実行中」）。

- **工程**: 実行側（`run-release-verify.sh`・`run-release-review.sh`）が`running`報告に`progress: { step, plan, index, command?, files? }`を載せ、
  `/api/dispatch/report`がジョブの種別に合う工程名だけを通して`DispatchJob.progress`へ保存する。統合検証は準備→統合→検証コマンド
  （文字列からinstall＝依存関係取得・test＝テスト・build＝ビルド、他は「検証コマンド」）→Mac検証、全体レビューは準備→差分取得→AIレビュー→結果整理。
  生存報告は別プロセスなので、現在の工程はファイル（`scripts/lib/release-progress.sh`）経由で渡す
- **待機理由**: `QUEUED`は実行先の`lastSeenAt`でオフライン／順番待ち、`CLAIMED`は起動準備中。ホストの記録が無ければ「未取得」と出し推測しない
- **停止**: 最後の報告から`DISPATCH_HEARTBEAT_TIMEOUT_MS`（10分）を過ぎたら「応答なし」にしてアニメーションを止める。取り消し・
  結果なしの終了は「中断」
- **出さないもの**: 百分率・残り時間（総量が分からない工程に経過時間から割合を当てない）、出力・ログ。終了後の「確認した範囲」は実行中の進捗と別に出す

**修正導線**: リリースブランチは直接書き換えない。指摘が出たら、developへ修正を入れてから既存の「修正を入れて作り直す」（`release-rebuild`・#3014）へ進み、
作り直しで変わったbase/head SHAに対して統合検証・全体レビューをやり直す（古いSHAの結果は「古い結果」になり流用されない）。CI失敗・コンフリクトは従来どおり`reusable-claude-pr-repair`の修復ボタン。
**手動で作り直す代わりに、画面から修正Issueを起案して作り直しまで自動で進める経路が次節の修正系列（#4317）。**

## 全体レビューの確認契約と再レビューへの引き継ぎ（#4559）

全体レビューが「何を確認すれば合格か」と「再レビューへ何を渡すか」を固定する。**個別PRレビュー・統合検証・候補管理・修正系列（#4317・#4410・#4478）は再実装せず、それらの記録を読む。**

### 確認項目（`src/lib/release-review-checklist.ts`）

- 6観点（PR間の整合・認証認可とデータ境界・実行ホストと共有ワークフローの新旧互換性・設定と移行の順序・候補固定と再試行時の状態整合・画面と実処理の一致）を版（`RELEASE_REVIEW_CHECKLIST_VERSION`）つきで持つ。**項目を変えたら版を上げる**。版が変わると前回の結果は引き継げず、全体確認へ戻る。
- 項目ごとに「確認済み／非該当／未確認」と根拠を記録する（`ReleaseVerification.findings.review.checks`）。**根拠の無い確認済み・報告されなかった項目は未確認**。未確認の項目と差分の入力省略（`totalFiles`・`reviewedFiles`）は`unverifiedScope`に入り、既存の`viewReleaseVerifications`が`passed`を`needs_check`へ読み替える。**プロンプトへ載せたことは確認の証明ではない**。

### 合格条件

- 止める指摘（`findings`）が1件でもあれば`needs_check`。止めない改善提案（`suggestions`）だけでは止めない。
- **止める指摘は、今回の差分に起因し、具体的な実害と根拠がそろったものだけ**（#4765）。判定は純関数`decideFindingBlocking`（`src/lib/release-review-result.ts`）が1か所で持ち、AIの申告をサーバー側で確かめる。
  - `blocking: true`の申告が無い指摘は提案（フラグ無しも提案）。`severity: high`でも`blocking: false`の申告を受け付ける（severityの名前では決めない）
  - 申告があっても、次のどれかに当たれば提案へ**降格**する: `impact`・`evidence`・`blockingReason`のどれかが欠けている／指摘の`file`がランナーの実測した対象ファイル（`targetFiles`）に無く、`evidence`が差分内のファイルパスを挙げていない／再レビューの新規`initial_miss`で、修正差分（`fixDiffFiles`）のファイルを指しても根拠で挙げてもいない
  - **セキュリティ相当（`checkId: "auth_boundary"`＝認証・認可・データ境界・機密の露出）は、申告・根拠・差分の有無にかかわらず止める指摘に固定する**
  - 降格の理由は指摘の`demotedReason`へ記録し、全体レビュー欄の改善提案の下に「提案へ降格: …」として出す
  - **旧ランナー（`checklistVersion`を報告しない結果）だけは従来どおり**: フラグ無しは止める指摘、`severity: high`は提案にできない。差分内かの確認・降格は行わない
  - 前回の止める指摘が今回は提案として載っている（降格を含む）場合、未解消（`unresolved`）として記録するが、止める指摘として再注入はしない
- 確認項目の観点と`BLOCKING_POLICY_LINES`は「〜を確認できたら指摘する」の肯定形の条件で書く（v2）。否定形（「〜の漏れは無いか」）は確かめられない仮定の状況を誘い、「念のため」の止める指摘を増やしていた。プロンプトの出力例も`"blocking": false`を既定にしている
- 合格は「現対象の必須項目に未確認が無く、止める指摘が無く、前回の止める指摘がすべて根拠つきで解消と確認できた」ときだけ。統合検証・CI・独立レビュー・main反映の承認は従来どおり。

### 再レビューの文脈（`release-review-context.ts`・`release-review-context-load.ts`）

- 取得元（新しい台帳は作らない）: 前回の`ai_review`記録（同じ候補系列の旧PR・旧head）、`ReleaseFixSeries`（`releasePrNumber`・`successorPrNumber`で系列を辿る）の`items`・`fixPrNumber`、その修正Issueの`ReleaseFixFinding`（`resolution`が対応の検証根拠）。
- **指摘IDは保存せず導出する**: `reviewFindingId`（`reviewFindingKey`のハッシュ、`R-xxxxxx`）。系列`items`も同じ関数で導出して突き合わせる。再発は前回のIDを引き継ぎ（`previousId`）、`occurrences`が増える。
  - **キーは「正規化した題｜ファイル」で、行番号を入れない**（#4766）。正規化（`normalizeFindingTitle`）はNFKC・小文字化・空白／句読点／記号の除去（記号をすべて消すので、`x + 1`と`x - 1`のように記号だけが違う題は同じ指摘になる。同じファイルでそこまで似た題の別の指摘は稀とみて、表記揺れの吸収を優先した）。以前は`題.trim()|ファイル|行`で、行のずれや言い換えのたびに別の指摘になり、戻せるのはAIが`previousId`を付けたときだけだった
  - **旧IDとの互換**: 保存済みの結果（`ReleaseVerification.findings[].id`）と判断（`ReleaseReviewDecision.findingId`）は旧ID（`legacyReviewFindingId`＝題・ファイル・行）のまま残る。照合は`buildFindingIdIndex`が持ち、**完全一致（保存済みのID・旧導出）を優先**し、現行の導出は一覧の中で1件にしか当たらないときだけ別名として使う（題・ファイルが同じで行だけ違う旧IDの指摘が複数あると現行の導出が衝突し、先着の指摘の判断・IDが別の指摘を覆うため）。判断の要約の読み替え（`summarizeReleaseReviewDecisions`）も、複数の指摘に当たる別名は使わない。再発した指摘は前回の記録のID（旧IDなら旧IDのまま）を引き継ぐので、旧IDで保存した判断・修正系列とつながったままになる。データ移行はしない
  - **バッチ間の重複除去**: ランナーのjq（`uniq_by_key`）は「小文字化・空白／句読点／記号を除いた題＋ファイル」でまとめ、止める指摘を優先して残す（jqはNFKCを持たない）。正は正規化（`normalizeReleaseReview`）で、最終的なIDが同じ指摘を1件にまとめる（止める指摘を優先し、提案側の重複を落とす）
- **全体確認へ戻す条件**（前回の結果を引き継がない）: 前回の記録が無い／前回が実行失敗／前回に項目別の記録が無い／確認項目の版が違う／base（main）が変わった／修正の履歴を辿れない／（ランナーが実測）前回の対象を取得できない・修正と無関係なPRが加わった。サーバーは記録時にも同じ文脈を取り直し、**ランナーの`carried_over`の申告は、前回に確認済み／非該当だった項目にだけ認める**。引き継いだ結果には旧headを残し、現SHAで実行した結果へ書き換えない。
- 新規の指摘には発見理由（修正由来／初回の見落とし／対象追加／不明）、再発した指摘が解消されない場合は原因（未修正／修正が効いていない／検証不足／実行障害／不明）と次の対応を残す。継続の上限・停止は#4410/#4478の機構に従い、ここではリセットしない。
- ランナーは`GET /api/dispatch/release-review-context?jobId=`（pollerの共有シークレット）で文脈を取り、修正差分（前回head→今回head）を載せる。

### 旧poller・旧サーバーとのデプロイ順

**サブPCのpoller更新（画面の「更新して再起動」）→サーバー**の順で出す。項目別の記録が無い旧ランナーの結果は、意図的に未確認範囲つきの`passed`（ゲートでは`needs_check`）になり、人の明示確認で通す。サーバーが先に出ると、更新前のpollerが出す結果はすべて人待ちになる。新ランナー→旧サーバーは追加項目が無視されるだけで、結果は旧形式として扱われる。

### #4495/#4496との接続

対象は従来どおり（PR・base・head）で扱う。候補revisionが導入されたときは、`loadReleaseReviewContext`の「前回の記録」を同じ候補系列の前revisionに差し替えるだけでよい（引き継ぎの可否判定は`decideReviewMode`に集約している）。バンプ後の引き継ぎ（`deriveInheritedRecords`）は元の結果を複写する別経路で、この判定とは独立している。

正式バンプ（#4496）で変わったのが版ファイル・更新履歴と、iOS設定の版番号行だけ（`versionLinesOnly`。書き換え後の`MARKETING_VERSION`が予約済みの正式版と一致することまで確かめる）なら、全体レビュー・統合検証はバンプ前の合格を引き継ぎ、全体レビューを最初からやり直さない（#4764。判定は`decideInheritedVerification`）。iOS設定の他の行・依存関係・その他が変わった場合と、iOS検証・Mac検証が必要なリポジトリの統合検証は従来どおり再実行する。詳細は[release.md](release.md)「検証対象の分離と引継ぎ」。

### セッション内の独立レビュー

修正Issue本文（`internalReviewSection`）に、同じ確認項目と止める／止めないの基準を載せる。

## 指摘ごとのユーザー判断（#4657）

全体レビューは**判断材料**として扱う。AIが挙げた指摘をすべて直し続けると、#4656のように「公開後にしかできない作業（フリートへの共有タグ配布）を公開前の条件にする」循環で候補を作り直し続けることになるため、指摘ごとにユーザーが採否と対応時期を決め、修正系列・完了系列・再レビューがその判断に従う。**#4559の指摘ID・#4354の完了待ち・#4587の停止／再開は再実装せず、その上に判断を足す。**

- **4つの判断**: 今回直す（公開前の修正対象）／公開後に対応する（関連Issue〈既存の番号か、明示操作で新規作成〉と実施時期が必須）／今回は見送る（残る影響と対象範囲が必須。**期限も修正Issueも作らない**）／指摘を採用しない（誤認・対象外・過剰な要求などの理由）。どれも理由が必須で、撤回（未判断へ戻す）もできる
- **保存先**: `ReleaseReviewDecision`。**追記のみ**で、変更・撤回も新しい行として残す（判断者・日時・理由の履歴）。AIの原判定（`ReleaseVerification.findings`の重大度・止める理由・根拠）は書き換えず、判断したときの対象（PR・headRef・base/head）と原判定の写し（重大度・止める指摘か）を行に持つ
- **範囲**: `scopeKey`＝リポジトリ＋修正系列（`successorPrNumber`）を遡った最初のリリースPR。旧方式の作り直し（後継PR）でも新方式RC（同じPRでrevisionが進む）でも同じ系列の判断を引き、**他の候補・他repoへは流用しない**
- **有効性**（`src/lib/release-review-decision.ts`の`assessDecision`）: 判断した指摘のファイルが判断時のbaseから現在のbaseまでの間に変わった・重大度が上がった・止めない提案から止める指摘になった・AIが前提の変化（`premiseChanged`）を報告した——のどれかなら「再確認が必要」で、無効として扱う。**文言の違いだけでは無効にしない**
  - **mainが進んだだけでは無効にしない**（#4766。`assessDecisionBase`）。以前は判断時の`baseSha`が今と違えば全判断を無効にしていたため、無関係なmainの前進のたびに同じ指摘を判断し直し、自動公開が止まっていた。変更ファイルはGitHubのcompare（`fetchBaseAdvanceChangedFiles`。改名前のパスも含める）で判断時のbaseごとに取り、結果をプロセス内に覚える（SHAの組の差分は変わらない。取得の失敗は覚えない）。**compareのファイル一覧は1ページ目にだけ、比較全体で最大300件**返り、`page`はコミットのページ送りにしか効かないので、ページ送りはせず300件に達したら確かめられないものとして扱う
  - **確かめられないときは従来どおり無効**: 指摘にファイルが無い・比較の取得に失敗した・mainが書き換えられて判断時のbaseが祖先でない・ファイル一覧が上限（300件）に達した・照合するbaseが多すぎる（5を超えた分）
  - 同じ規則を、再レビューへ渡す判断の`stale`（前回の指摘からファイルを引く）と、修正系列の巡回の`loadNonFixFindingIds`（系列の項目からファイルを引く）にも使う
- **同時判断**: 画面は見ていた最新の判断ID（`expectedDecisionId`）を送り、違えば409（`decision_conflict`）。通し番号（`sequence`）の一意制約で、確認と追記の間に入った保存も止める。黙って上書きしない。旧IDの判断を読み替えている指摘（`FindingDecisionView.aliasIds`）は、旧IDの行も含めて判断時刻で最新を確かめ、新しい判断は今の指摘のIDで保存する（#4766）
- **API**: `POST /api/repositories/release/review-decisions`。ガードは再実行と同じ（プレビュー→ログイン→リポジトリの所有確認→今のリリースPRの再取得とSHAの一致）。**今の結果に載っている指摘IDだけ**を受け付ける。外部エージェント用のreview-agent APIには書き込み口を作らない（採否はユーザーが決める）
- **画面**: 全体レビュー欄（PC・スマホ・本番マージ確認で共通）に「ユーザー判断」の集計（未判断の止める指摘・公開前に残る確認・公開後作業・見送り／不採用・次の操作）と、各指摘の下に判断の表示と入力を出す。公開後作業は「未実施」と出し、**配布済み・適用済みとは表示しない**。今回の結果に同じIDが無い判断は「判断が外れた可能性」として出す

### 判断を読む経路

| 経路 | 判断の使い方 |
| --- | --- |
| 修正Issueの起案（`createReleaseFixSeries`） | 有効な非修正の判断が付いた指摘は、選ばれても起案しない（画面でも選べない） |
| 次世代の自動起案（`continueAfterReverification`） | 「今回直す」と未判断の指摘だけを対象にする（`selectAutoFixIndexes`）。残りがすべて非修正なら次世代を作らない |
| 取り込み前の系列（`sweepGroup`） | 写した指摘がすべて非修正になった系列は止め、以降の取り込み・候補の更新をしない。**実行中のセッションと取り込み済みの修正PRは止まらない**旨を理由に書く |
| 完了系列（#4480） | 止める指摘の全件が有効な非修正の判断なら、`decideReleaseCompletion`は新たな修正を起案せず、開始時の`hasProblem`にも数えない。`decideCompletionMerge`は`isGateClearedByReviewDecisions`（要確認が全体レビューの止める指摘だけ）のときだけ`needs_confirmation`を通す。本番まで進めると開始者が選んだ系列に限られ、統合検証・Mac・CI・ラベルの条件は変わらない |
| 再レビュー（`loadReleaseReviewContext`） | 判断をプロンプトへ渡し、有効な非修正の判断は「前回の指摘の解消確認」と「未解消の自動再注入」から外す。判断済みの指摘を出し直すときは`previousId`を必須にし、前提が変わったときだけ`premiseChanged`を書かせる |

**解除できるのは全体レビューの止める指摘による要確認だけ。** マージゲート（`evaluateReleaseMergeGate`）の`needs_check`は書き換えず、未確認範囲・統合検証の要確認・実行中・失敗・古い結果・取得失敗は判断では解除しない。判断の保存だけではマージもIssueの作成（公開後対応で明示したものを除く）もしない。

### 公開前と公開後を分ける

レビュー方針（`BLOCKING_POLICY_LINES`。サーバーから配るのでpollerの更新は不要）に、**main公開後にしか実施・確認できない作業**（共有タグ配布・フリートへの配布・本番でのmigration適用の成功確認）を同じ本体の公開前の完了条件にしないことを足した。公開前に確かめられる移行の互換性・適用順序・手順・必要な設定の欠落は従来どおり止める指摘のまま。判断の節（ユーザーの判断・`previousId`・`premiseChanged`の指示）はランナー（`run-release-review.sh`）がプロンプトへ足すため、**pollerの更新後に有効**。更新前のpollerでも、サーバー側の正規化（判断済みの指摘を再注入しない・ID一致で判断を引き継ぐ）は効く。

### AIの推奨と理由案（#4676）

判断の理由を毎回一から書かせないため、**未判断の指摘と前提が変わった判断の指摘**にだけ、AIが4種類からの推奨と、判断の種類ごとの理由案を出す。**「理由を残すこと」と「ユーザーが一から手入力すること」を分ける**のが目的で、記録する理由はこれまでどおり空にしない。

- **生成**: `POST /api/repositories/release/review-recommendations`（ガードは判断APIと同じ）。アプリ内AI（`src/lib/claude/request.ts`、機能名`release_review_recommend`。公開前の判断を支えるため**推論側のモデル**〈アプリ内AI（推論）設定〉で動き、実行フロー設定の「新規アプリ相談・修正提案・判断の推奨」の行に出る）に、指摘の記録（影響・根拠・止める理由・推奨対応・影響PR・前回の判断と再確認の理由）だけを渡す。**コードは読ませない**ので、確かめられていない事項は「判断材料の不足」（`missing`）へ書かせる。8件ずつまとめて1回呼ぶ
- **保存**: `ReleaseReviewRecommendation`。範囲は判断と同じ`scopeKey`で、**対象（base・head）ごとに1行**。対象が変わった推奨は新しい対象へ使わず作り直し、原判定（重大度・止めるか）が変わった指摘も作り直す。失敗は`failed`で残し、画面を開くたびに呼び直さない（再取得はユーザーの「推奨を再取得」だけ）
- **捏造させない**: プロンプトで既存のIssue番号・具体的な期日を禁じ、応答の検証（`parseRecommendationResponse`）でも、期日の入った実施時期と`#番号`の入ったIssue題を捨てる。公開後対応の追跡先は**新しいIssueの題の案だけ**で、確定時もIssueを作ることをボタンに明示する
- **確定はユーザーの操作だけ**: 推奨を表示しただけでは何も保存しない。「推奨どおり確定」は推奨の判断と理由案をそのまま判断APIへ送り、必須項目が理由案に揃わない推奨（追跡先の案が無い公開後対応など）はワンタップを出さずフォームで埋めてもらう。「別の判断を選ぶ」はその判断の理由案を入れ、選び直しただけでは保存しない。保存の競合・対象の更新は判断APIの既存の検査（SHAの一致・`expectedDecisionId`）がそのまま止める
- **区別して残す**: 判断の行に、判断時の推奨の写し（`recommendationId`・`recommendedDecision`・`recommendedReason`）と理由の出どころ（`reasonSource`＝AIの理由案のまま／編集／手入力）を持つ。判断APIは推奨IDが今の対象・同じ指摘のものかを確かめ、違えば409（`recommendation_stale`）。画面は確定済みの判断に「AI推奨を採用／推奨を編集して採用／AI推奨と異なる判断」を出す
- **確定済みの判断には推奨を作らない**ので、新しい推奨で判断が上書きされて見えることはない。再レビューでの引き継ぎは従来どおり判断の有効性（`assessDecision`）に従い、前提が変わった判断にだけ新しい推奨が付く

## PRの6チェック表示とMac検証の独立記録（#4366）

PR詳細・PR一覧・ブランチ画面・本番マージ確認の一覧は、同じ6項目を同じ順で出す（`src/lib/pull-request-merge-checks.ts`・`src/components/dashboard/pull-request-merge-checks.tsx`）: **CI／コードレビュー／コンフリクト／全体レビュー／統合検証／Mac検証**。#4305の5項目にあった計画レビューはPRのチェックに含めない（Issue側の計画レビューは別機能として残る）。

## 修正系列：起案から修正候補の再検証まで（#4317）

全体レビューの指摘・統合検証の失敗から**修正Issueを起案**し、修正PRのdevelop取り込み→候補の作り直し→新しいSHAでの再検証を追跡する。
**終点は「検証済み候補の準備完了（本番承認待ち）」。mainへのマージとデプロイは従来どおり人が承認する。**
記録は`ReleaseFixSeries`（修正Issue1件につき1行）。判断は純関数`src/lib/release-fix-series.ts`、外部操作は`src/lib/release-fix-series-run.ts`、画面は`release-fix-panel.tsx`。

- **起案**（`POST /api/repositories/release/fix-series` `action=create`）: 全体レビューの指摘は複数選択して**1件のIssueにまとめる**（共通原因を分割しない）。
  根拠は**サーバーが現在のSHAの記録から読み直す**（クライアントの内容は信用しない）。機密は`redactDiagnosticText`で除去し、元リリースPR・base/head SHA・種別・関連PR・修正後の検証条件をIssue本文へ引き継ぐ。
  本文先頭の`<!-- issue-deck-release-fix:<鍵> -->`が目印
- **二重起案の防止**: 鍵は「リポジトリ・リリースPR・base/head SHA・種別・指摘」から決め、進行中の系列は`activeKey`のユニーク制約で1本に絞る。同じ対象は既存の系列（Issue・修正PR・進捗）を返す。同時起案に負けたIssueは閉じる
- **区別**: 全体レビューの実行障害（`failed`）は起案しない（再実行が主導線）。統合検証の失敗は文面から実行障害（終了コード126/127・接続失敗・Mac/ホスト無しなど）と見分け、疑わしいときは再実行を先に勧める。**利用者が明示（「コードの修正として起案する」）したときだけ起案する**。仕様判断が要るときは判断内容を必須にし、`21.plan-required`を付けて**計画の承認を省かない**
- **取り込み**: 修正PRのマージは**既存の自動レビュー・マージ機構**が行い、系列は`issue-<番号>`ブランチのdevelop向けPRを観測するだけ（GitHubの保護は外さない）。修正PRがマージされずに閉じたら理由付きで止める
- **作り直し**: 同じリリースPRに結び付いた系列が**全部**マージ済みになったら後継候補を作る。**PRを選んだ作り直し（#4335）に対応したリポジトリでは、画面の手動選択と同じ`requestSelectiveRebuild`（`release-rebuild-selection-run.ts`）で、修正PR（＋確認済みの`acceptedExtraPrs`）だけを元の候補へ足す**。未対応のリポジトリは従来の`release-rebuild`（閉じてdevelopの最新で作り直す）。`rebuildClaimedAt`の条件付き更新と、作り直し依頼の`activeKey`で二重の作り直しを防ぐ
- **混入の防止**: 選んだ作り直しでは、選んでいないdevelopの変更は入らないので判断待ちにしない（下記「PRを選んだ作り直し」）。未対応のリポジトリだけ、**修正PR以外の変更が入っていたら自動では作り直さず、PR番号を示して`awaiting_decision`（判断待ち）で止める**。「無関係な変更も含めて作り直す」で確認した番号だけを`acceptedExtraPrs`に記録する
- **再検証**: 後継候補を検出したら`reverifying`。新しいbase/headの統合検証・全体レビューがどちらも成功したときだけ`ready`（本番承認待ち）。失敗・要確認は、巡回が種別を分けて扱う（#4478）。**通常の追加指摘（全体レビューの指摘・コード由来の統合検証失敗）は確認待ちにせず、巡回が同じ修正Issueの次世代を起案して実装をサブPCへ起動し、旧世代は`superseded`（引き継ぎ済み）にする**（**世代数の上限は無い**〈#4589。世代番号・source key・指摘履歴は保持する〉。同一候補・同一指摘の再発は理由付きで`stopped`＋`00.check-user`。再発の判定に使う`sourceKey`は「リポジトリ・base・種別・指摘キー」で、**リリースPRの番号とheadを入れない**〈#4766。後継候補ではheadが必ず変わり、旧方式では番号も変わるため、以前は再発が一度も一致しなかった〉。同じPRでの二重起案は`activeKey`がPR番号を前置して止め、再発の判定は二重起案の確認より先に行う〈新方式では再検証中の親系列が同じ`activeKey`を持つため〉。進捗の無い停滞・実行予算・本人判断は#4587の再開可能な一時停止が受け持つ）。実行障害（全体レビューの実行失敗・環境由来の統合検証失敗）は起案せず再実行を待ち、コードか実行障害か判別できない失敗は本人へ渡す。旧い巡回が一律に`stopped`にした系列（停止理由に「の再検証で指摘・失敗が残りました」）と、旧3世代上限で止めた系列（「修正の反復が上限（」）も巡回が再評価して同じ記録から続ける。後継世代が既にあれば二重起案・二重起動せず、旧世代の`00.check-user`＋`01.check-blocked`（他理由の札は残す）を解く。後継候補がさらに更新・取消・マージされたら`superseded`にして誤った候補を追わない
- **巡回**: `scripts/subpc-dispatch-poller.sh`の`sweep_release_fix_series`（`DISPATCH_POLLER_VERSION=37`）が`POST /api/repositories/release/fix-series/sweep`を呼ぶ。進行はすべてDBの行にあり、再起動しても続きから進む。止まった・判断待ちのときは修正Issueへ理由をコメントし`00.check-user`＋`01.check-blocked`を付ける
- **画面**: 全体レビューの指摘・統合検証の失敗の下に「修正Issueを作成」、検証区分の下に「この候補への修正の進捗」（Issue作成→計画・実装→PR検証→develop取り込み→候補作り直し→再検証→本番承認待ちの現在地・関連リンク・停止理由・各SHA）。PC・スマホ共通の部品

## 修正の内部確認：1セッション内で往復し、修正PRを1件にまとめる（#4410）

修正Issueのセッション内で「実装 → 独立レビュー → 修正 → テスト」を繰り返し、**内部確認が完了してから**develop向けの修正PRを1件作る。
レビューのたびに修正Issue・PR・リリース候補が世代をまたいで増えるのを避ける。対象はリリース修正系列（`ReleaseFixSeries.internalReview=true`の系列。旧い系列は従来どおり）で、通常Issueの実装フローは変えない。

- **担当**: 実装は修正Issueのセッション。独立レビューは同じセッションが`Agent`ツールで呼ぶ**読み取り専用の別エージェント**（Claude Code標準の通信機構）。実装担当は合否を決めず、レビューの指摘と検証結果を報告APIへ書き写す。`tmux send-keys`・常駐の監督役は使わない
- **作業場所**: 元候補（凍結ブランチ）を一時worktreeへ取得し、修正を重ねた状態で確認する。developの最新は混ぜず、内部の往復では候補の作り直し・バージョン更新をしない（手順は修正Issue本文の「内部確認」節。`internalReviewSection`）
- **記録**（`ReleaseFixInternalRound`・`ReleaseFixFinding`）: 論理セッションは**リポジトリ＋修正Issue番号**で、再検証の失敗で世代が進んでも指摘・往復を引き継ぐ。指摘はサーバーが`F-001`から採番し、解消は根拠つき、再発は`reopenCount`で数える。中断・再起動しても同じ記録から再開する
- **報告API**（`POST /api/dispatch/release-fix-internal`、`scripts/report-release-fix-round.sh`）: `review`・`test`・`status`。認証は共有シークレット。**対象のSHAは受け取らず、サーバーが`issue-<番号>`ブランチのHEADから取り直す**。進行中の内部確認つき系列に結び付かない報告・整合しない報告（`pass`なのに未解決が残るなど）は記録しない
- **完了判定**（`evaluateInternalGate`）: 最新の往復で、独立レビューの実施・未解決指摘0件・必要テストの合格が**同じ対象SHA**に対してそろっているときだけ。レビューやテストの後に内容が変わると古い合格は使われない
- **PR作成**: `scripts/create-release-fix-pr.sh`が完了判定・push済みの内容との一致・開いているPRの有無を確かめ、満たさなければ作らない（再実行でも重複しない）
- **強制は取り込みの手前**: GitHub側のPR作成そのものはサーバーから止められない。そこで巡回（`sweepGroup`）が修正PRのhead SHAで同じ判定をし、**未完了または確認した内容と違うPRは候補の作り直しへ進めず`awaiting_decision`にする**（`decideReleaseFix`の`internalHold`）。確認が完了すれば次の巡回で自動的に進む
- **一時停止の条件**（`decideInternalStop`・#4587）: 往復の回数では止めない（5往復・系列作成から120分の固定停止は廃止）。止めるのは**進捗の根拠が無い停滞**（変更も解消も無いまま同一指摘が2回再指摘される／未解決が減らず解消の根拠も無い往復が続く）と**実行予算の到達**だけ。進捗の根拠は、指摘の解消・未解決件数の減少・確認対象SHAの変更。件数だけでは断定しない。停止は`ReleaseFixInternalSession`に原因・次の操作・停止時のSHAを残す一時停止で、指摘・往復・稼働時間は失われない。判断や権限が要る場合と実行環境の障害は、担当が`pause`で報告する
- **稼働時間と予算**（#4587）: 単位は**稼働分**、既定は`INTERNAL_DEFAULT_BUDGET_MINUTES`=120。報告・担当の更新のたびに、前回からの間隔を**10分（`INTERNAL_ACTIVE_GAP_MINUTES`）まで**算入し、超えたぶん（待機・中断・担当不在）と一時停止中は消費しない。担当を引き継いでも累積はゼロにならず、予算は再開時の追加でだけ増える
- **担当と競合排除**: `claim`（`takeover`で別担当から引き継ぎ）・`release`。担当が変わるたび世代番号`assignmentEpoch`が増え、報告に添えた`assignee`・`epoch`が合わない旧担当の遅延報告は`stale_assignee`で弾く。持ち時間（30分）内の別担当は、明示の引き継ぎが無ければ取れない。取得・再開は世代番号・停止原因を条件にした更新で、同時の操作は一方だけが成功する
- **再開**: 状態の取得（`status`・画面の読み込み）は読み取り専用で、停止・再開・担当変更・コメント・ラベルをしない。再開は別の操作（画面の主操作 `resume_internal`／エージェントの`resume`）。予算到達は稼働時間の追加、停滞・判断待ちは方針の入力が要る（同じ修正を繰り返させない。再開後は再開時点の往復より後だけを停滞の根拠にして即再停止を避ける）。回復済みの実行障害（`environment`）は入力なしで再開でき、`00.check-user`も付けない。完了・置換・修正PRマージ済みの系列は再開しない
- **旧方式の停止の移行**: `internalStopReason`だけが入った旧い停止は、理由文面を保持したまま一時停止として読み替える（往復・時間の上限は`budget_reached`扱い）。実際の再開時に新しい予算で再評価する
- **止まったときの通知**: 停滞・予算・判断待ちはIssueへ理由と必要な操作を残して`00.check-user`＋`01.check-blocked`を付ける（一度だけ）。再開するとコメントを残して外す
- **最終検証で追加修正が出たとき**: 元のPRはすでにマージ済みで足せない。既存の世代（`generation+1`）を使い、**同じ修正Issue・同じ`issue-<番号>`ブランチ・引き継いだ内部確認の記録**へ戻して追加PRを1件作る（Issueへ理由を記録。新しいIssueは作らない。Issueが閉じているときだけ新規）。前の世代が使ったPRは次の世代の修正PRとして拾わない
- **画面**: 修正パネルの現在状態の下に「内部確認」欄（レビュー・テストの状態、未解決指摘、稼働時間と予算、担当、一時停止の原因と次の操作、再開・引き継ぎの主操作。`ReleaseFixInternalReview`。PC・スマホで同じ部品）
- **PR取り込み後**: 選択的取り込み・候補再構築・最終候補のSHAでの再検証・GitHub CI・本番マージを人が行う点は従来のまま

## リリース完了まで進める：候補の失敗から本番稼働確認まで（#4480）

リリース候補の失敗（全体レビューの指摘・統合検証の失敗）から、**一度の開始で修正・候補の作り直し・再チェック・
（許可した範囲の）本番マージ・deploy・稼働確認までを同じ論理系列が続ける**。記録は`ReleaseCompletionRun`
（世代ごとの`ReleaseFixSeries`を束ねる親）。判断は純関数`src/lib/release-completion.ts`、外部操作は
`src/lib/release-completion-run.ts`、画面は`release-completion-panel.tsx`（修正パネルの要約帯に入る。PC・スマホ共通）。

- **開始**（`POST /api/repositories/release/completion`）: 範囲は「チェック通過まで」（`until_ready`）か
  「本番反映・稼働確認まで」（`until_production`）を**開始者が必ず選ぶ**（省略不可）。開始できるのは、現在のSHAの
  検証に問題があるか修正系列の記録がある候補だけ（問題の無い候補は通常のリリース）。同じリポジトリで1本だけ
  （`activeKey`）。期限は24時間で延ばさない。開始者・範囲・期限は行に残し、本番マージの権限はこの記録だけで判定する
- **役割分担**: 世代の進行（修正PRの観測・候補の作り直し・再検証）は従来どおり`runReleaseFixSweep`が持つ。
  完了系列の巡回（`runReleaseCompletionSweep`）は**`ReleaseFixSeries`の状態を書き換えず**、次だけを行う
  - 修正Issueの起動（`enqueueDispatchJob`。同じ世代は1回だけ。起動から3時間修正PRが現れなければ止める）
  - 再検証で指摘・失敗が残った停止から、次の世代を起案する（`createReleaseFixSeries`。同じ修正Issueへ戻す既存の流れ・同一指摘の再発拒否をそのまま使う。世代数の上限は無い）
  - 修正系列が作り直した後継の候補へ追従する
  - 全部合格したら、`until_ready`は本番承認待ち、`until_production`は`decideCompletionMerge`で本番マージ（`release.md`「リリース完了系列に限り…」）
  - 本番反映後のdeploy追跡・稼働SHAの確認（#4007の`decideDeployRecoveryRelease`）。人がマージした場合も同じく追跡する
  - deployが再実行も失敗したら、本番復旧系列（`DeployRecoverySeries`）へ引き継ぎ（範囲は`until_production`なら`fix_until_main`）、その完了で系列も完了にする
- **区別**: 統合検証の失敗が実行障害（`classifyIntegrationFailure`）、全体レビューの失敗に指摘が無い（実行障害）ときは
  修正Issueを作らず止める。**全体レビューが指摘0件で未確認範囲だけの要確認（`needs_check`）は実行障害として扱わない**（#4768。以前は統合検証の待ちより先に
  `execution_failure`、公開承認の系列では`approval_checks_failed`で止まっていた）。統合検証が終わっていなければ待ち、終わっていて再評価がまだ
  （共通の段階が「検証結果を確認中」）なら`reevaluate_review`で既存の自動再評価（`reevaluateReleaseReviewIfReady`）を積んで待つ。再評価済み、または
  証跡に依存しない未確認（再評価しても変わらない）なら、未確認の種類と範囲を添えて`review_unverified`で止める（公開承認の系列でも承認を失効させない理由）。
  再評価を積めない理由（対象外など）が返ったときも同じ理由で止め、待ち続けない。判断は純関数`decideReleaseCompletion`・`describeUnverifiedReview`・`reevaluationKeepsWaiting`。設定不足（Mac検証の`needs_setup`など）も止める。#4452の経路（選んだ修正での作り直し・
  履歴だけの差の反映）は修正系列がそのまま使い、「修正PRを足せない」停止は修正系列の再評価を待つ（理由を表示）
- **排他・冪等**: 巡回は`lastSweepAt`の条件付き更新で実行権を取る。二重起案は`ReleaseFixSeries.activeKey`、二重起動は
  `DispatchJob.activeKey`、二重マージは状態の条件付き更新とHEAD指定のマージが防ぐ。巡回は`hostName`を持つ
  `POST /api/repositories/deploy-recovery-series/sweep`に相乗りする（pollerは変更なし）
- **上限・停止**: 期限・費用上限（修正Issueのセッションの`SessionUsage.costUsd`合計。既定$30。API換算の目安）に
  達したら新しい起動・起案・マージをせず止める。停止（`DELETE`）後は巡回の対象から外れ、引き継いだ本番復旧も止める。
  止まったときは修正Issue（無ければ候補のPR）へ理由をコメントし、修正Issueに`00.check-user`＋`01.check-blocked`を付ける
- **画面**: 6段階（原因を調査中／修正とレビュー中／修正後のチェック中／本番へ反映中／稼働確認中／完了）の現在位置、
  世代・費用・許可範囲、原因・残り・操作の要否、詳細（修正Issue・修正PR・候補の変遷・対象SHA・承認）

## PRを選んだ作り直し（#4335）

「修正を入れて作り直す」は、元の候補（`release-main/vX.Y.Z`のhead）へ**選んだPRのdevelopへのマージ差分だけ**を
`cherry-pick -m 1`で足した状態からバンプする。以前はdevelopの最新を丸ごと取り込んでいたため、元の候補の後に入った
無関係な変更まで混ざっていた。GitHubのmerge APIで祖先ごと取り込む方式は、選んだ差分だけになる保証が無いので採らない。

- **画面**（`release-rebuild-button.tsx`・`release-rebuild-selection-list.tsx`。PC・スマホ共通）: 元の候補の後にdevelopへ入ったPRと
  当該リリースの修正PR（未マージを含む）を、番号・題・関連Issue・マージ／CIの状態つきで並べ、複数選べる。**既定は当該リリースの
  修正系列の修正PRだけ**で、無関係なPRは選ばない。未マージ・取り込み済みは理由を添えて選べない（developのレビュー・マージを省かない）。
  押す前に「追加される範囲」を出す
- **検証**（`release-rebuild-selection.ts`・`-run.ts`）: PR番号だけでなく、マージ済みか・base=developか・バンプPRでないか・
  マージコミットが選んだ時点と同じか・元の候補に既に含まれていないかを確かめ、元の候補のPR番号とheadと一緒に
  `rebuild_selection` inputとしてworkflowへ渡す。同じ元の候補（番号＋head）への起動は`ReleaseRebuildRequest.activeKey`で1本に絞る
- **workflow**（`reusable-release-develop-to-main.yml`の状態判定）: 元の候補が今も同じheadで開いているかを確かめ直し、PRを
  developへ入った順に当てる。マージコミットの件名がそのPRのものでなければ、既に元の候補にあれば、当てて競合すれば止める。
  競合したときは、元の候補の後に同じファイルを触ったPRを「先に必要な可能性があるPR」として示す。**選択は自動では広げない**。
  当てた結果の差分のファイルが、選んだPRのマージ差分の範囲に収まることも確かめる
- **後継の候補とバンプPRを分ける**: 「元の候補＋選んだPR＋版の書き換え」を後継の候補として`release-candidate/v新版`に置き、
  developへのバンプPRには**版の書き換えだけ**を当てる（候補ごとdevelopへマージすると、選んだPRの後にdevelopで同じ行を直した
  PRがあったとき衝突する）。バンプPR本文の`<!-- issue-deck-rebuild-candidate:<SHA> -->`から、マージで起きるrunが凍結点を
  この候補にする。**元の候補は後継のリリースPRを作れてから閉じる**（`<!-- issue-deck-rebuild-origin:#N -->`）ので、途中で失敗しても
  元の候補は残り、失敗の記録に選択が残る（リリース画面の「再開」は、同じ選択を現在の状態で検証し直してから起動する）
- 後継の候補のSHAで統合検証・全体レビューが走り直す（旧SHAの成功は流用しない）。本番mainへのマージは従来どおり人が承認する
- **未対応のcaller**（配布先の旧タグ）には選択を出さず、従来の作り直しだけにする（`releaseCallerSupportsSelection`がdevelopのcallerに
  `rebuild_selection`があるかを読む）。新規アプリの雛形（`src/lib/new-app/scaffold-workflows.ts`）は最初から対応している

## 全リポジトリへの展開と導入台帳（#4365）

**宣言はコード、状態は導出。** `release-verification-config.ts`が正本で、`RELEASE_VERIFICATION_REPOS`（検証コマンド・技術構成・前提不足`setupGaps`・Mac検証の有無と配布状況）と
`RELEASE_VERIFICATION_EXCLUSIONS`（アーカイブ・本番リリース経路なしの**根拠付き**対象外）を持つ。導入状態は`release-rollout.ts`が宣言と
`ReleaseVerification`・`DispatchHost`の申告から導く（新規テーブルは無い）。画面は設定＞フリート運用の「リリース検証の導入状況」（`GET /api/repositories/release/rollout`）。

状態（上ほど優先）: 対象外／未導入（管理対象なのに台帳が無い）／設定不足／配布待ち（実行できるホストの申告が無い・poller未対応）／検証待ち／検証済み（必須化待ち）／必須化済み。

- **設定不足を対象外にしない。** `not_applicable`はゲートで合格扱いになるため、根拠のある対象外（`RELEASE_VERIFICATION_EXCLUSIONS`・`integrationNotApplicableReason`）だけに使う。
  台帳に無い・コマンドが空・`setupGaps`がある場合、統合検証の依頼は**`failed`（理由付き）を記録してジョブを積まない**（`describeIntegrationSetupGap`）
- **Mac検証の前提**（`ios/scripts/remote-build-check.sh`の配布）は`describeMacSetupGap`。Linuxの統合検証は止めないが、導入状態は設定不足で、`enforced`にもできない（テストが守る）
- **`enforced`を立てる条件**: 設定不足が無く、実リリース候補で統合検証・全体レビューが合格し、ホストが申告している。1リポジトリずつ立て、全対象が揃うまで#4365は完了にしない

### 新規リポジトリを足すとき

1. 本番リリース経路（develop→main）があるか確認する。無ければ`RELEASE_VERIFICATION_EXCLUSIONS`へ**理由付きで**足す
2. 有るなら、そのリポジトリの`ci.yml`に合わせて`RELEASE_VERIFICATION_REPOS`へ宣言する（`integrationCommands`は各々単独の`bash -c`。pnpmの流用をしない。DB・環境変数が要るなら`setupGaps`へ書く。iOSがあれば`macBuildCheck`と`ios/scripts/remote-build-check.sh`の配布）
3. サブPCの`DispatchHost`にリポジトリを申告させ、poller（`releaseVerify`・`releaseReview`対応版）を更新する
4. 次のリリース候補で実走させて合格を確認し、`enforced: true`にする。台帳へ載せ忘れた管理対象は、導入状況の一覧に「未導入」として出る

## 統合ビルドの検証用環境（#4331）

IssueDeckの `pnpm run build:ci` / `pnpm build:ci` は、更新済みサブPCの
`run-required-checks.mjs --group lint-and-build --check build` を統合worktree内で実行する。
ビルド用envは通常CIと同じ `ci/required-checks.json` の `build.env` が正本で、
ビルド子プロセスだけへ適用する。本番用の秘密鍵や `.env` はコピーしない。
テスト・報告処理・他リポジトリのコマンドは従来どおりで、この設定を適用しない。
検査IDが欠落・重複した場合は終了コード2、ビルド失敗は1となり統合検証を失敗にする。

配布はdevelopへマージ後にサブPCの「更新して再起動」で行う。サーバーの本番反映や
リリース候補の作り直しを待たず、既存候補を再実行できる。実行対象は要求された
base/headの統合状態のまま、通常CIのビルド定義は更新済み実行側から読む。
この成功は本番認証の疎通確認やMac検証の成功を意味しない。

## 現在の状態の決め方（#4498）

`describeFixOverview`は、見出しと主操作を**実際に動いている処理**から決める。順序は次のとおり。

1. 進行中のリリース完了系列（調査・修正とレビュー・修正後のチェック）。未解決指摘は見出しにせず「修正対象」の説明として添える。修正Issue作成は出さない
2. 修正系列の状態。`fix_in_progress`は修正PRが無ければ「修正中」、あれば「修正PRの検証中」。未開始・停止は自動進行中と表示しない
3. 現在のSHAの検証結果。全体レビューが`needs_check`かつ指摘0件は「レビュー範囲の確認待ち」（確認数が取れたときだけ`65/71ファイル`を添える。修正指摘にも成功にも変えない）。全体レビューの実行失敗（指摘なし）は「レビューの実行に失敗」。実際の指摘がある場合だけ「修正が必要」

完了系列の取得は`useReleaseFixOverview`で1回だけ行い、要約帯と`ReleaseCompletionPanel`へ渡す（二重ポーリングによる見出しの食い違いを防ぐ）。
