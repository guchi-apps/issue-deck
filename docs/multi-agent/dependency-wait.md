# 実装セッションの依存待ち

**いつ読むか**: 実装セッションが他のIssue・PRの完了を待って保留する仕組み、またはその表示・自動再開を触るとき（#4321）。

## 何を解決するか

`11.local`は「ローカルで対応中（Actionsを起動しない）」の抑止フラグで、何を待っているのかは表せない。
保留コメントと`11.local`だけが残ると、依存先が完了しても誰も気付かず、会話を開いて手で再開するしかなかった。

## 構成

| 役割 | 場所 |
| --- | --- |
| 待ちの記録（依存先・条件・理由・追跡） | `SessionDependencyWait`（`prisma/schema.prisma`）。`DispatchSession`とは別にして、セッションが消えても残す |
| 条件の判断・文言（純関数） | `src/lib/dispatch/dependency-wait.ts` |
| 観測・登録・再開・巡回（IO） | `src/lib/dispatch/dependency-wait-run.ts` |
| セッションからの報告 | `scripts/report-dependency-wait.sh` → `POST /api/dispatch/sessions/dependency-wait`（`DISPATCH_SECRET`） |
| 定期照合 | pollerの`sweep_dependency_waits` → `POST /api/dispatch/dependency-wait/sweep` |
| 画面の操作（再確認・再開・解除・既存保留の登録） | `POST /api/dispatch/dependency-wait`（ログイン認証）。一覧・詳細・スマホは`GET /api/dispatch`の`dependencyWaits`を読む |

## 条件は区別する

`closed`（クローズ）・`merged`（PRのマージ）・`released`（マージ済みPRのマージコミットがmainの祖先）・
`verified`（実環境の検証。**機械では成立させない**）。クローズやdevelopへのマージだけで本番反映・検証済みとはみなさない。
未成立が残れば待機を維持し、判断不能な条件だけが残れば`NEEDS_CONFIRM`（人の確認）へ回す。

## 通常の実装依存の既定は`merged`（#4570）

通常のコード実装を前提にする依存は、依存先Issueのクローズ（＝本番反映）を待たず、**実装PRがdevelopへマージ済み**
（`merged`）で解除する。A→B→Cを順にdevelopへ取り込み、最後にまとめて本番リリースできる。

- **Issue参照の`merged`/`released`**: `issue-<番号>`ブランチをheadとするPRへ解決して評価する（`observeDependency`）。
  マージされず閉じたPRは証拠にしない。**複数PRは全件が条件を満たしたときだけ成立**（無関係な1件では成立させない）
- **統合ブランチ**: `develop`があればそれ、無ければリポジトリのデフォルトブランチ。**mainや別ブランチへのマージは`merged`として成立しない**
- **成立にしないもの**: PR作成のみ・未マージで閉じたPR・Issueのnot plannedクローズ（PR無し）・参照不明・取得失敗
  （PR無しのクローズと取得失敗は`NEEDS_CONFIRM`＝人の確認、またはエラーとして待機を維持する）
- `released`は本番機能・本番設定が必要な依存だけ、`verified`は実環境の確認が必要なときだけ明示する。`closed`は
  クローズ自体が必要な根拠があるときだけ。条件の省略は拒否する（変更なし）
- 完了の分離: 後続の開始はdevelopマージで進められるが、Issueのクローズ（本番反映時）と親の本番確認条件は変えない

### 既存の`closed`待ちの見直し

`closed`だけを待つIssue依存（`isClosedWaitReviewCandidate`）に限り、Issue詳細の待機パネルに「developマージ待ちへ見直す」が出る。
**人が1件ずつ押す**（一括変更しない。`released`/`verified`を含む明示的な待ち・PR参照は対象外）。押すと`conditions`を`merged`へ変え、
変更前後・理由・操作者を`SessionDependencyWait.conditionHistory`へ残し、直後に条件を評価し直す（成立済みならそのまま再開）。
再開の追跡中・終了済みの待ちは変えず、稼働中の親子実行計画は書き換えない（計画は既存の版更新・再計画の経路で見直す）。

### 画面の表示

条件は「#Aのdevelopマージ待ち」「#Aの本番反映待ち」「#Aの検証待ち」「#Aのクローズ待ち」に区別して出し（`describeWaitTarget`）、
成立根拠・不足・依存先リンクを待機パネルに出す。PC・スマホは同じ`DependencyWaitPanel`を使う。

## 状態

`WAITING` → `RESUME_REQUESTED`（指示を積んだ）→ `RESUME_SENT`（ジョブ成功）→ `RESUMED`（送信後にセッションが
ツール実行または応答の進行を確認）。送信しただけでは実行中にしない。失敗は`RESUME_FAILED`（理由付き・画面の
「作業を再開」で再試行）。自動では蒸し返さないが、**未送信入力・作業中で見送られたものだけは巡回が間隔を空けて
再試行する**（下記「一時的な見送りの自動再試行」）。

## 進捗の戻しと再開（#5118）

前提が未達で保留したIssueが`Implementation`のまま残ると、盤面では作業中に見える。そこで待ちの登録時に
進捗を`Ready`（未着手）へ戻し（`onlyFrom: planning, implementation`。`Develop PR`以降は動かさない）、
再開がセッションの動きで確認できた時点（`RESUMED`）で`Ready`なら`Implementation`へ進める。どちらも
`reportProgressStatus`の失敗は握りつぶし、待ちの処理は止めない。待ちの取消（`CANCELLED`）は監視をやめるだけで再開の指示を送らないため、進捗は`Ready`のままにする（作業へ戻す操作は「作業を再開」で、`RESUMED`を経由して`Implementation`へ進む）。待機パネルと一覧のバッジは既存のまま、
パネルの案内に「進捗は未着手へ戻しています」を添える。実装プロンプトには、本文の`## 前提条件`が未達で
実装を進めないと判断したときも同じ保留報告をするよう明記した。

## 二重起動の防止

- 同じIssueの待ちは`activeKey`（`repo#issue`）で1行
- `WAITING`系→`RESUME_REQUESTED`は`updateMany`の条件付き更新で1本だけが取る
- 巡回は行ごとに`lastSweepAt`で実行権を取り、60秒に1回へ抑える
- 通知（Issueコメント・`00.check-user`）は`notifiedKey`で状態の変わり目ごとに1回

## 既存の保留（#687相当）

待機の登録が無い`11.local`のIssueでは、コメントの保留表現と`owner/repo#番号`から**依存先の候補**を画面に出す。
自動では登録・再開せず、人が条件を選んで確定する（`gates.md`の「実行体が判断して送らない」と同じ線）。

## 再開の文面

固定の1行（`buildDependencyResumeInstruction`）で、依存先の参照だけが入る。既存の`INSTRUCTION`ジョブ
（3段階プロトコル・承認プロンプト中は送らない）で送る。**セッションが終了していれば、待ちの記録を残したまま
`RESUME_FAILED`で「セッションを復旧」へ案内する**（既存の復旧経路は履歴を引き継いで呼び戻す）。

## 未送信入力の退避（#4383）

入力欄に未送信の文字が残っていると、再開の指示（と通常の追加指示）はpollerの`instruction_ready`が見送る。
見送り理由は`DispatchJob.message`をそのまま失敗理由（`failureReason`）へ載せ、`SKIPPED`だけで終えない
（`src/lib/dispatch/input-stash.ts`が未送信入力・作業中・承認待ち・状態不明・退避失敗を分類する）。

**未送信入力が理由のときだけ**、画面に「未送信の入力を退避して、再開指示を送信」が出る（依存待ちパネルと
セッション詳細の追加指示）。確認ダイアログで対象・ホスト・セッション・今回の指示を見せ、押すと
`stashInput`を立てたジョブが積まれる。キャンセルでは何も変更しない。

- 前提は`instruction_ready`が返り値`3`（作業中・承認待ち・状態不明の確認は通り、入力欄だけが理由）のとき。
  それ以外は入力欄へ1キーも送らない（承認プロンプトの保護を迂回しない）
- 取得（`instruction_capture_input`）は、入力が1行で直下が枠線、かつ**カーソル位置が読み取った文字列の表示幅と
  一致する**ときだけ「完全」とみなす。複数行・折り返し・末尾の空白・読み取れない文字は、改行と折り返しを
  見分けられないため**消さずに止める**（理由付きで見送り）
- 2回取得して内容が一致し、状態も変わっていないことを確かめてから`POST /api/dispatch/input-stash`で保存する。
  **保存の応答を確認するまで消去しない**。消去は`C-e`→`C-u`の固定キーで、空になったことを確認してから
  今回の指示だけを3段階プロトコルで送る（元の入力は再送せず、連結もしない）
- 退避は`SessionInputStash`（`jobId`のunique＝二重退避しない）。本文はログイン必須の画面にだけ出し、GitHub・
  通常ログ・通知・ジョブの`message`へは出さない。保持7日（参照のたびに期限切れを削除）、画面から削除できる
- 送信待ちのジョブが`DEPENDENCY_WAIT_RESUME_CONFIRM_TIMEOUT_MS`（10分）を過ぎても未処理なら理由付きで`RESUME_FAILED`
- Codexは`codex queue`の既存経路のままで、TUI操作（退避・消去）は行わない


### 一時的な見送りの自動再試行（#5005）

yoteiflow#1347では、依存先のマージ後に再開の指示が未送信入力で見送られ（`RESUME_FAILED`）、その後3時間、
人が声をかけるまで止まっていた（`00.check-user`＋`01.check-blocked`は付いていたが、確認待ちの1件として埋もれた）。
未送信入力は人が送るか消せば解ける一時的な理由なので、巡回が自動で試し直す。

- 対象は`isTransientResumeFailure`（`src/lib/dispatch/dependency-wait.ts`）が真のもの＝見送り理由が**未送信入力**か
  **作業中**のときだけ。承認待ち・状態不明・退避失敗・セッション終了・積み込み失敗は従来どおり人へ渡す
- 失敗時刻`resumeFailedAt`から`DEPENDENCY_RESUME_AUTO_RETRY_DELAYS_MS`（2分・5分・15分）空けて、最大3回。
  回数は`autoRetryCount`で、巡回が`updateMany where autoRetryCount = 現在値`で数えてから試す（重なっても1回）
- 再試行は自動の再開と同じ固定の1行・同じ`INSTRUCTION`ジョブで、**`stashInput`は立てない**（入力欄に触れない）。
  入力欄が空になっていればそのまま再開し、条件が崩れていれば`WAITING`へ戻す
- 再試行が残っている間は`00.check-user`を付けず、最初の見送りでだけ「自動で再試行します。下書きなら送信するか
  消してください」とIssueコメントする。使い切ったら「自動の再試行（3回）でも再開できませんでした」とコメントし、
  `00.check-user`＋`01.check-blocked`を付ける（Push通知は`check-user-push.ts`がラベルから送る）
- 人が「作業を再開」を押すと回数は0へ戻る。画面の依存待ちパネルは未送信入力を強調し、次の自動再試行の時刻を出す
- **未送信入力の自動退避は入れていない。** 「完全に取得でき、最後の入力から一定時間経過したら無人で退避する」案は、
  人の下書きを消しうるため判断を保留した（退避は従来どおり確認ダイアログを通した人の操作だけ）

### 退避操作とpollerの互換性（#4408）

未送信入力の退避は `stashInputCapable=true` を申告したホストだけで利用できます。
poller v39から対応を明示申告します。v38には退避処理がありますが申告がないため、Web更新だけでは退避操作を有効にしません。
ホストの「更新して再起動」でpollerを更新し、新しいホスト申告が届くのを確認してください。
未申告・falseの場合は画面とAPIで退避指示を拒否し、配布時も `stashInput=false` のジョブだけを渡します。
通常の追加指示と停止操作は従来の対応申告で利用できます。
DBのnullable列追加を先に適用してください。旧pollerの申告は対応状態をnullへ戻すため、旧版へ戻した後も退避指示を配布しません。

## 再開の見落としと古い試行の混入を防ぐ（#4688）

`WORKING`は承認待ちが解けた直後にだけ報告されることがあり、普通の作業中ずっと届く値ではない。
再開の確認は、成功済みINSTRUCTIONジョブの宛先ホスト・セッションと、`stepSeenAt`（ツール実行）または
`WORKING` / `RESPONDED`の`activityAt`を突き合わせる。承認待ちの表示だけ・古い活動は根拠にしない。
これは依存待ちの解消の確認であり、Issue完了や新しい質問への回答を意味しない。

- `resumeSentAt`はジョブの`finishedAt`を保存する。巡回時刻では、送信から巡回までに完了した作業を見落とす。
- INSTRUCTIONはRUNNINGを経由せず、成功報告の通信中にも活動が届くため、活動の比較基準は成功したジョブの
  `claimedAt`とする。古い記録で欠ける場合は`finishedAt`、それも無い場合は保存済み送信時刻へフォールバックする。
  指示の作成時刻は使わない。成功した送信と同じ宛先の新しい活動を組み合わせた確認で、個々のツールの目的を推測しない。
- 再試行の取得時に以前のジョブID・送信時刻・再開時刻を消す。積み込み途中に前回の成功や失敗を読まない。
- 観測した状態・activeKey・ジョブID・要求時刻が一致するときだけ更新する。取得中の待機解除や他の試行を
  古い巡回で上書きせず、変更権を取れた処理だけが結果を通知する。
- 待機解除はすでに送出された指示の取り消しではない。既存の送出中のジョブや実装セッションを勝手に中断しない。

終了済みセッションの自動再起動、承認・質問への自動回答、失敗後の無条件再送は追加していない。
既にRESUME_FAILEDとなった記録は自動変更しない（#5005で、一時的な見送りだけ上限付きで自動再試行するようにした）。既存の確認待ちラベルも他の確認理由と共有するため一括解除しない。


## 通常のIssue実装フローの現状確認（2026-10-17 / #4688）

調査基準はdevelop `5e67c4fe`。以下はコードで確認した経路であり、全リポジトリ・全ホストでの実走確認ではない。

| 工程 | 既存の仕組み | 今回の扱い |
| --- | --- | --- |
| Issue実装の開始 | DispatchJob、poller、Issue単位のセッションとworktree。Actions実装入口は#4680で廃止 | 再実装しない |
| PR後の修復 | CI・競合・レビュー修正workflow、`pull-request-auto-repair-sweep.ts`の修復系列 | 既存の指摘・権限・試行制限を維持 |
| 人の判断が必要なレビュー | `review-fix-jobs.ts`が現在HEADの判定と自動修正可否を検査 | 自動で回答・承認しない |
| 別Issueの実装待ち | SessionDependencyWait、developマージ待ち（#4570）、条件成立後の固定指示 | 再開追跡の誤判定と競合を修正 |
| セッション終了後 | 待機記録は残り、SessionRecoveryButtonから履歴を引き継ぐ復旧 | 自動起動は未対応のまま。利用者による終了との区別が必要 |
| 運用作業の共通化 | 既存Epic #4520と子Issueで追跡 | 重複起票・同時実装しない |

再現テストでは、通常のツール実行、応答完了、成功報告前の活動、再試行中の古いジョブ参照、待機解除中の上書きを確認した。
本番DBの停止履歴は取得しておらず、過去の失敗総数・この不具合の発生件数は不明。
この修正だけで全ての停止が解消した、あるいはIssueDeckの役割が不要になったとは結論しない。

## リリース前後の依存との接続（#4523）

実行計画の`timing`（`pre-release`など）はこの4条件の上に乗る。リリース前必須の作業が未完了のあいだは、
候補のmainマージ（手動・自動とも）が`evaluateReleaseMergeGate`で止まり、成立後は次の巡回で再評価される。
ユーザー操作が要らない待ちは`00.check-user`へ送らない。詳細は[../execution-plan.md](../execution-plan.md)「リリース前後の区分とゲート」。
