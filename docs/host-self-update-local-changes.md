# ホスト更新時のローカル変更（#4686）

「更新して再起動」とpollerの自動更新は `scripts/lib/self-update.sh` を共用する。
未追跡バックアップの存在だけでは止めず、取り込み先と衝突するかを個別に判定する。
取り込み先と同じ内容の追跡済み変更は、indexに独自変更がなくfast-forward可能な場合に限り
HEADへ戻してから取り込む。未追跡ファイルはそのまま保持する。
取り込み先と異なる独自変更は自動stash・削除しない。ファイル名を付けて停止する。

## 稼働用チェックアウトに応急修正を残さない

- 修正は専用ブランチ・worktreeで行い、PRを通して正式反映する。
- 実機での応急修正が不可避なら、差分・理由・元SHAを対応Issueへ記録し、正式反映後に解消する。
- バックアップはリポジトリ外の専用ディレクトリへ保存する。`.gitignore`で隠して解決扱いにしない。
- 更新を通すための `reset --hard` や `clean -fd` は使わない。

## 旧能力申告の応急修正について

`releaseVerify` / `releaseReview` の追加は現行APIには不要。
サーバーは機密除去対応を示す `releaseVerifyRedact` / `releaseReviewRedact` のみを読む
（#4629、`src/app/api/dispatch/hosts/route.ts`）。旧キーを正式コードへ再追加したり、
API側で旧キーを受け入れる対応はしない。

初回は古い更新処理そのものが動いているため、この修正だけでは既に停止したホストを更新できない。
担当者が差分を確認し、旧キーの追加だけであることを確かめたうえで、対象スクリプトと
バックアップの正確なパスを指定して `git stash push -u -m "poller local patch before update" -- <対象パス>`
で保全する。画面から更新して再起動し、表示された起動版と最新heartbeatを確認する。
退避内容を自動で `stash pop` してはいけない。必要な変更は最新版との差分を確認して正式PRへ反映する。
機能申告の確認は、旧キーの存在ではなく、現行APIとホストの検証・レビュー対応状況で行う。

## 検証

`src/lib/self-update.test.ts` は実Gitリポジトリで、バックアップ併存、独自修正、indexの保全、
特殊なファイル名、ディレクトリ衝突、fast-forward不可を検証する。
実機の更新・再起動確認はPRのコード検証と区別して記録する。
