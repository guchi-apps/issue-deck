# リリース体験の再設計

目的は、通常は少ない操作で公開まで進み、具体的な危険と人の判断が必要な場面だけ止まること。
チェック項目数ではなく、公開後の不具合と、停止回数・手動操作数・待機時間を合わせて評価する。

## 公開の方針

- PR時のレビューとテストの証跡を使い、リリースではPR間の相互作用、設定・移行の順序、本番特有のリスクを重点確認する。
- データ消失、認証不備、主要機能の破綻など、具体的な影響と根拠のある問題を公開前の判断対象にする。重大度の名前だけで停止を決めない。
- 改善提案は公開を止めない。未確認は不具合と分け、何を・どこで・いつ確認する必要があるかを示す。
- 公開後でしか取得できない証拠を、同じ本体の公開前完了条件にしない。公開前の互換性・設定・手順の確認は残す。
- 必須テストの失敗・取得不能をAIや利用者の判断だけで合格へ変換しない。
- 再確認は修正箇所・影響範囲・新しい証拠を対象にする。同じ条件で成果のない再実行を繰り返さない。
- 一度の公開承認から既存の公開系列で進める。承認対象外の変更は既存の失効判定に従う。

## 画面の情報構成

最初に公開内容、現在地、今必要な対応を示す。検証の技術詳細はその後に置く。
共通の検証パネルに「今必要な対応」を設け、PC・スマホ・公開確認で同じ意味を使う。
複数の問題がある場合は隠さず列挙する。取得エラー時や修正前の履歴には現在の助言を出さない。

| 状況 | 案内 |
| --- | --- |
| 検証実行中 | 対象の処理と待機理由。重ねて実行する必要はない |
| 統合検証失敗 | テスト不合格と実行環境不足を詳細で確認して復旧 |
| レビュー実行失敗 | コード指摘と分け、診断から実行環境を復旧 |
| 阻害指摘 | 影響・根拠・公開前に必要な理由と採否の選択 |
| 未確認 | 未確認理由と必要な証拠。再実行だけで直ると約束しない |
| 改善提案のみ | 任意の記録。対応判断を公開の必須操作に見せない |
| 確認完了 | この画面の対応待ちはない。CI等の他条件と公開承認は別 |

## #4678の実装

- 共通パネルの先頭に停止・待機理由と次の操作を表示する。複数の理由を列挙し、累計失敗数は推測しない。
- AIレビューのimpact/evidence/blockingReasonが揃った阻害指摘では「今回直す」の理由を引用して準備する。
  新しいAI推論ではなく既存レビューからの入力補助であることを表示する。ユーザーが明示保存するまで判断は作成しない。
- 他の選択では理由を流用しない。理由の下書きは選択ごとに保持する。見送りの影響・範囲、公開後のIssue・時期は既存検証を維持する。
- SHA変更時には入力フォームを作り直す。保存は既存APIの認証・対象SHA・expectedDecisionIdの比較と履歴保存を用いる。
- 失敗時に入力を維持する。AI原判定と利用者判断は引き続き別々に表示する。
- 公開承認済みでも「人がマージする」と案内していた説明を修正する。

## 継続して必要な実装

本PRは停止条件のサーバー判定や検証の実行回数を変更しない。以下は未実装であり、表示改善で達成済みにしない。

1. #4676: AIが4種類の採否・理由を提案する処理と、提案元・利用者の最終判断を区別した記録。今回の理由引用だけでは完了ではない。
2. 未確認事項の構造化: 公開前必須・公開後確認・任意の区別、対象と理由をAPI/保存/ゲート/自動公開まで共通化する。自由文から単語一致でゲートを解除しない。
3. 起動前検査: 実行ホスト、依存関係、外部workflow参照、報告用スクリプトとAPIの利用可否を検証開始前に確認する。
4. 実行履歴: 候補単位の開始・停止・再開イベントと原因ID、ユーザー操作、時刻を記録する。同じ原因と新しい原因、再レビュー回数と失敗回数を区別する。
5. 自動復旧: 一時的な障害の再試行、同じ原因・同じ証拠での繰り返し停止、必要な操作への直接導線。#4664の証拠到着時の再評価は再利用する。
6. 公開後の異常: 稼働版確認とアプリ機能の正常性を分け、ロールバック・機能停止・追加修正の適用条件を設計する。

これらはDB・実行ホスト・公開権限の境界を含むため、今回の画面用の助言関数を公開可否の判定に流用しない。

## 既存ブランチ画面の情報配置（#4683）

ヘッダー、一括リリース、スマホの開閉一覧、PCの2ペインを維持する。折りたたんだ行は既存の状態バッジと短い操作ラベルを同じ行へ置く。説明文と状態の重複を増やさず、対応が必要な操作だけを琥珀色と注意アイコンで区別する。操作ラベルは行の展開操作であり、公開や修正を直接実行しない。展開中は「閉じる」、PCの選択中は「表示中」とする。

詳細の先頭は既存の失敗の帯と現在の候補・主操作・検証を保つ。開発中の作業・PR、公開対象の変更、公開済みの変更をそれぞれ開閉できる単位にする。作業と変更は初期展開して既存の修正・マージ導線を隠さず、長い候補の作り直し履歴だけを初期折りたたみにする。過去の変更に残る手作業と関連不明のIssueは従来の帯で表示する。

一覧の案内は表示専用で、公開ゲートの代用にしない。デプロイ失敗、取得不能、検証の問題、PRの要対応を進行中より優先する。取得不能を変更なしと扱わず、mainへのマージ情報を「本番稼働中」と断定しない。RCの公開承認・対象SHA照合・判断理由保存は既存の処理を引き続き使う。

候補の作り直し履歴は過去の全停止回数ではない。新しい停止イベントの収集、稼働確認の追加、公開後同期の状態APIは本変更に含めない。
