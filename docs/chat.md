# IssueDeck Chat（会話型の操作入口）

#3975。左メニュー・スマホホームの「チャット」（`?pane=chat`／`?mscreen=chat`）から、自然言語でIssue・PRの状態確認、PR自動修正、Issue起案を行う。**チャットは新しい実行基盤ではなく、既存のService/APIを呼ぶ会話型の入口**で、一覧・Issue/PR詳細は変わらず併存する（回答のカードから「PR詳細を開く」「GitHubで開く」で移れる）。

## 構成

| 層 | ファイル | 役割 |
|---|---|---|
| 意図解釈 | `src/lib/chat/intent.ts` | 決まった言い回しだけを拾う（LLMには任せない）。`resolveIntent`が会話コンテキストを当てはめ、対象が決まらなければ`ask`（聞き返し） |
| カード | `src/lib/chat/status-card.ts` | 既存の判定値（CI・レビュー判定・mergeable・修復run）を言葉と色に写すだけ。判定ロジックは持たない |
| 処理 | `src/lib/chat/handlers.ts` | 状態取得は既存関数、修復・Issue作成は下の共通サービスを呼ぶ |
| 共通サービス | `src/lib/github/pull-request-repair-service.ts`・`issue-create-service.ts` | 画面のボタン（`POST /api/pull-requests/repair`・`POST /api/issues`）とChatが**同じ関数**を呼ぶ。HTTPへの写し方だけが各ルートに残る |
| API | `src/app/api/chat/` | 会話一覧・作成、発言（`[id]`）、確認カードの実行（`[id]/confirm`） |
| 保存 | `ChatConversation`・`ChatMessage`（Prisma） | 会話コンテキスト（直前の対象・実行した操作）と発言・カード・確認状態 |

## 書き込み操作の確認ルール

- 状態確認（読み取り）は発言からそのまま実行する。
- **PR自動修正とIssue作成は、発言では実行しない。** 確認カード（`confirm_repair`・`confirm_issue`）を返し、`POST /api/chat/[id]/confirm`の`execute`だけが実行する。確認APIは次を守る。
  - カードの内容はクライアントの申告でなく**保存済みの発言**から読む（Issue案のタイトル・本文の編集だけは利用者自身の入力として受ける）
  - `confirmState`を`pending`→`done`へ更新できた1回だけ実行する（二重クリック・再送で2回走らない）。失敗したときは押し直せるよう`pending`へ戻す
  - `PREVIEW_MODE`では実行を403で止める
- 修復は既存と同じく、実行時のHEADから`repairKindsFor`で種類を組み直し、conflict → ci → review の先頭1種類だけを起動する。確認カードには起動順を表示する。

## 会話コンテキストの解釈

`ChatContext.targets`は**直前の発言で見せた対象**（発言のたびに置き換える）。1件なら「それ」「直して」「もう一度確認して」「マージできる？」が指し、複数を並べた直後は聞き返す（候補をボタンで出す）。番号だけの発言は`ChatContext.repo`（会話を作るときに選ぶrepository）を補う。

## 会話セッションの保存・管理・再開（#4047）

会話（`ChatConversation`）は作業単位のセッションで、画面を閉じても・別端末でも・後日でも、同じ会話を開けば続きから再開できる。

| 項目 | 仕様 |
|---|---|
| 保存 | 発言は送信のたびにサーバーへ保存する。画面には「保存中…／保存できませんでした」を出し、失敗した入力は消さず**同じ`clientMessageId`で再送**できる。`ChatMessage`の`(conversationId, clientMessageId)`は一意で、再送・複数端末の重複送信は保存済みの返信を返して**二重登録も二重実行もしない** |
| 一覧・検索 | `GET /api/chat?q=&archived=`。タイトル・本文の部分一致と、`#3966`／`3966`の番号検索（`refsText`＝対象・実行記録・発言に出た番号）。アーカイブ済みも`archived=1`で再表示・再開できる。状態は「判断待ち」（確認カードが`pending`）・実行件数を出す |
| 名前変更・アーカイブ | `PATCH /api/chat/[id]`（`title`・`archived`）。**アーカイブは一覧から外すだけ**で、削除でも実行の停止でもない。自動削除は入れない |
| 新しい会話 | 既存会話を消さず独立した会話を作る。対象・メモ・実行記録は会話ごとに分かれる |
| 会話メモ | `ChatConversation.memory`。合意した方針・未解決の質問（`PATCH`の`memoryOp`）と、状態カードを返した時点の調査結果（`findings`）。**メモは手がかりで、操作の許可根拠にならない**（実行は確認カードの`/confirm`だけ。許可範囲をメモ・要約から広げない） |
| 長い会話 | 履歴は全件保持し、開くときは新しい側から100件、`before=<発言ID>`で遡る。方針・未解決・根拠は発言を遡らずメモから参照できる |
| 再開時の最新化 | `GET /api/chat/[id]?refresh=1`が対象のPR・CI・レビュー・実行状態をGitHubから取り直し、**調査時点（`findings`）と現在の差**を返す。確認待ちの修復カードは、いま実行して意味があるか（修復できる問題が残っているか・種類が変わっていないか）を照合して画面に出す |
| 実行の引き継ぎ | 実行結果は`context.actions`と確認カードの`confirmState`（`done`）に残るので、閉じて開き直しても結果が分かり、同じ操作を再起動しない（実行は`pending`→`done`を取れた1回だけ） |
| 複数端末 | 会話に`version`（楽観ロック）を持つ。発言の保存・メモ更新は`version`を条件にし、衝突したら読み直してやり直す。確認の実行記録は最新の会話へ足すため、古いコンテキストで他端末の更新を上書きしない。画面に戻ったとき（`visibilitychange`）に別端末の進みを取り込む |
| 認可 | 会話は所有者だけが読み書きできる。対象リポジトリの権限をサーバーで確かめ、**権限を失った会話では新規の取得・発言・確認の実行を403で止める**（履歴の閲覧だけ残す） |

### 移行

`20261005150000_chat_session_management`は追加だけのマイグレーションで、既存の会話・発言・確認カードの状態（`confirmState`）はそのまま残る。新しい列（`memory`・`refsText`・`version`・`archivedAt`・`clientMessageId`）は既定値で埋まり、既存会話は`memory`が空・`archivedAt`がNULL（一覧に出る）として扱う。`refsText`は既存会話では空で、番号検索は以後の発言・実行から効き始める（タイトル・本文検索は既存の発言にも効く）。ロールバックは追加列と索引を落とすだけでよい。

### 今回の範囲外（後続）

添付画像のセッションへの関連付けと永続化・認可（現在チャットに添付の入口が無いため）、Claude/Codexの実行セッションとのIDでの関連付け（`context.actions`には実行の起点だけが残る）、要約の自動生成（LLM）。#4045との結合シナリオは、#4045の入口が揃った時点で検証する。

## 第一段階で扱わないもの

自由形式のコード編集、LLMによる意図解釈（言い回しの拡張が必要になったら別Issue）、Claude/Codexの直接起動（既存の実行系はIssue詳細・実行状況から使う）、セッション詳細の表示（状態カードにはセッション名と状態だけを出す）。
