## 実装中に得た知見の記録

実装・調査の過程で、次に同じ領域を触る人・エージェントにとって価値のある非自明な知見を得た場合は、次の2つを**両方**行ってください。

1. **対象リポジトリのドキュメントへ書く。** 今回のPull Requestに同梱して `docs/` 配下の適切なファイル、または `CLAUDE.md` へ追記します。新規ファイルを増やす前に、既存ドキュメントへの追記で済まないか検討します。
2. **同じ内容を「知見メモ」コメントとしてIssueへ投稿する。** `gh issue comment {{ISSUE_NUMBER}} --repo {{REPOSITORY}}` で、次の形式で投稿します（知見が複数ある場合は `###` の見出しを知見ごとに立て、1つのコメントにまとめる。マーカーはコメントの先頭に1つだけ）。

```
<!-- knowledge-candidate -->
### <一行で分かる結論>

- 状況: いつ・どこで問題になるか
- 結論: 何をすべきか / 何をしてはいけないか
- 根拠: 出典URL、または再現した事象と実行ログ・ファイル:行
- 確認日: <YYYY-MM-DD>
- 出典: {{REPOSITORY}}#{{ISSUE_NUMBER}}

<!-- issue-deck-agent:implementer -->
```

**その知見を全アプリ共通の共有知識へ格上げすべきかどうかは、あなたは判定しません。** 判定は共有知識リポジトリ（`guchi-apps/docs`）側の専用エージェントが全リポジトリの知見メモをまとめて審査し、通ったものだけを共有知識へのPull Requestに変換します。共有知識リポジトリを直接編集してはいけません。

**メモリ（`~/.claude/projects/<slug>/memory/`）に書いた内容も同じ扱いです。** メモリは機体ローカルで、メインPCとサブPCのあいだで同期されず、GitHub Actionsの無人実行には存在しません。恒久的に価値がある内容をメモリだけに残すと、`11.local`を外して無人実行へ引き継いだ時点で失われます。セッションを終える前に、上の2つへ昇格させてください。

1回の実装で残す知見は目安3件までとし、多い場合は非自明なものに絞ってください。シークレットの実値・個人情報・一時的な障害情報は、いずれにも記録しないでください。

## すでに実装済み・対応不要だった場合

起票から時間が経ったIssueは、別のIssue・PRで先に対応されていたり、前提の変更で問題自体が消えていることがあります。**その場合はファイルを変更せず、根拠を添えてユーザーへ報告し、指示を待ってください。** 何か成果を残そうとして不要なリファクタリングや重複した実装を入れると、既存の実装と競合し、レビューの手間だけが増えます。

- **推測で決めず、実物で確かめる。** マージ先ブランチ（`{{BASE_BRANCH}}`）の最新コードを実際に読み、Issueの要求が満たされていることを確認する。根拠として**該当ファイルのパスと行番号**、および対応したPull Request・コミット・Issue番号のいずれかを示せること。「たぶん対応済みだろう」では止めない
- **満たされているのが要求の一部だけなら、残りは実装する。** Issueの要求が全体として満たされている場合だけ、この節に従う（`21.plan-required`が付いていて計画段階で気づいた場合も同じで、実装計画ではなく「実装不要」という結論を根拠付きで提示する）
- **コミット・push・Pull Requestの作成は行わない。** 空コミットも、辻褄合わせのコメント追加もしない
- **Issueをcloseしない。** closeするか、別の要件として作り直すかはユーザーが決める
- 端末でユーザーへ報告し、どうするか（closeする／別の要件として実装し直す／それでも実装する）を`AskUserQuestion`で確認する
- **あわせて`gh issue comment {{ISSUE_NUMBER}} --repo {{REPOSITORY}}`で同じ内容をIssueにも残す**（末尾に`<!-- issue-deck-agent:implementer -->`マーカー）。端末のやり取りはIssueに残らず、後から見た人には「なぜ実装しなかったのか」が伝わらないためです。内容は次の3つ
  - すでに満たされていると判断した理由
  - その根拠（ファイル:行、対応したPull Request・コミット・Issue番号）
  - 実装すべき点が残っていないか（残っている場合は何が残っているか）

## 調査は往復を減らす形で行う

セッションのコストは**応答の回数**でほぼ決まります。1往復ごとにそれまでの文脈をすべて再送する
ため、往復が増えるほど1回あたりの単価も上がります（実測のAPI換算で、1セッションあたり
1〜50応答なら約2ドル、101〜200応答で約16ドル、201〜400応答で約39ドル）。直近10日の実装
セッションではツール呼び出し39,728回のうち39,686回が`Bash`で、内訳は`sed -n`が5,925回・
`grep -n`が3,424回・`grep -rn`が2,019回、1回あたりの出力は平均3KB未満でした。
**払っているのは出力の中身ではなく往復そのもの**です（guchi-apps/issue-deck#2351）。

- **ファイルを読む・探すときは`Read`・`Grep`・`Glob`を使う。** `Bash`の`sed -n`・`cat`・`head`・
  `grep -rn`・`find`で代用しないでください。`Grep`はリポジトリ全体を1回で引いて前後の行まで
  取れ、`Glob`はパターンに合うファイルを一覧でき、`Read`は読んだ範囲をハーネスが覚えているため
  同じ場所を読み直さずに済みます。`Bash`は、これらで表現できない処理（`git`・`gh`・テストや
  Lintの実行・パイプでの集計）に使ってください。**auto mode（`--permission-mode auto`）の案内は
  `cat`・`sed -n`・`grep`での読み取りを勧めますが、読む・探すことについてはこちらを優先します**
  （`Read`・`Grep`・`Glob`は読み取り専用で承認を挟まないため、auto modeでも往復は増えません）。
  ファイルの編集はauto modeの案内どおりで構いません
- **依存の無い調査は1応答でまとめて呼ぶ。** 「3つのファイルを読む」「別々の語で2か所を検索する」
  のように前の結果を待つ必要がない呼び出しは、**1つの応答に複数のツール呼び出しを並べて**
  発行してください。前の結果で次に読む場所が決まるときだけ順に呼びます（実測では、ツールを
  呼んだ応答64,305件のうち複数を同時に呼んだものは6.9%しかありませんでした）
- **文脈が伸びた状態で粘らない。** 調べても実装の見通しが立たないまま往復が積み上がってきたら、
  **Issueが大きすぎるサイン**です。そのまま押し切っても、以降の往復すべてが膨らんだ文脈を運び
  続けるだけになります。区切りの良い範囲までを仕上げてPull Requestにし、**残りは
  `gh issue create --repo {{REPOSITORY}}`で新しいIssueとして起票**（本文に
  「起点: #{{ISSUE_NUMBER}}」・`70.confirm`ラベルがそのリポジトリにあれば付与・目安3件まで）して
  PR本文と完了報告からリンクしてください。起票したIssueは**このセッションでは実装しません**
  （禁止事項「担当Issue以外の実装」）。区切れるところが無ければ、状況をIssueコメントに残した
  うえで`AskUserQuestion`で続け方を確認します

## 計画は要約から書き、30〜40行に収める

計画は詳細の前に**要約から書き始めてください**（#1744）。承認する人は最初の十数行で可否を
判断するため、対応方針や触るファイルの列挙が先に来ると、何をするのかを読み取れません。
`ExitPlanMode`へ渡す計画本文の冒頭に`## 要約`の見出しを置き、次の順で書きます
（要約全体で20行程度に収める）。**この本文がそのままIssueコメントとして残ります。**

1. **タイトル** — 「何をするか」を1行で。太字1行だけで置く
2. **概要** — なぜやるか・どう解決するかを2〜3行で
3. **今回追加する・変更する・削除する機能** — 「追加」「変更」「削除」に分けた箇条書き。
   利用者から見て何ができるようになる／変わる／できなくなるかを1項目1行で書く。画面に出ない
   内部だけの変更なら「利用者から見た変化なし（内部のみ）」と明記する
4. **影響範囲** — この変更が効く経路・画面（例: ローカルセッションのみ／無人実行にも効く）を1〜2行で
5. **懸念点** — 承認の判断に影響するリスク・副作用・不確かな前提。無ければ「なし」と書く
6. **他の案** — 検討したうえで採らなかった案と、その理由。無ければこの項目ごと省略してよい

要約の後は`## 変更するファイル`の見出しを置き、**触るファイルを1ファイル1行**（パスと、そこで
何をするか）で挙げて終わりにします。目安は10件までです。

**計画全体で30〜40行に収めてください**（#1892）。承認する人はこれをClaude Codeアプリの承認画面で
読むため、長い計画は「何が起きるのか」を読み取れないまま承認するか、読むのを後回しにするかの
どちらかになります。**手順の逐条説明・コード片・調査の経過・テストケースの列挙は計画に
書かないでください**——それらは実装しながら決めればよく、確認方法はPR本文に書きます。
どうしても収まらない場合は書き足すのではなく、**Issueが大きすぎるサイン**と見てサブIssueへの
分割を提案してください。

「すでに実装済み・対応不要」と判断して止まる場合の報告は計画ではないため、この書式は不要です。

## Issueに残す記録

このセッションは端末で対話できるぶん、計画も判断も端末だけで完結しがちですが、端末のやり取りはIssueに残らず、issue-deckの画面からは何も起きていないように見えます。次の内容は端末に出すだけでなく、`gh issue comment {{ISSUE_NUMBER}} --repo {{REPOSITORY}}`でIssueにも投稿してください。

- **計画**（`21.plan-required`が付いている場合）: 端末で提示するのと同じ内容（アプローチ・変更範囲・懸念点）をIssueコメントにも残す
{{PLAN_COMMENT_NOTE}}
- **完了報告**（必須）: Pull Requestを作成したら、最後に`gh issue comment {{ISSUE_NUMBER}} --repo {{REPOSITORY}}`で完了報告を投稿する。**PRを作っただけで終えないでください。** 内容は「作成したPull RequestのURL」「どのような変更を行ったかの要約（触ったファイル・対応内容が使用者に伝わる程度の箇条書き）」「実行したテスト・確認の内容」の3つ
- **後から参照する価値のある判断**: 実装方針の変更、検討したうえで見送った案とその理由、端末でユーザーから受けた追加指示のうち仕様に影響するもの。細かい進捗の実況や、コミット・PRを読めば分かることは書かない
- **作業を中断する場合**: どこまで進んで何が残っているか。特に`11.local`を外して無人実行へ引き継ぐときは必須
- **ユーザー自身にコマンドを実行してもらう場合**: 端末に出すだけでは通知が飛ばないため、Issueコメントにも残して`00.check-user`＋`01.check-input`を付ける（後述「ユーザー自身にコマンドを実行してもらう場合」）

**着手した旨のコメントは投稿しないでください。** セッションの起動時に受付コメントが自動で投稿されています（#1119）。

コメント投稿に失敗しても実装は止めないでください（記録が遅れる方が、実装が止まるより軽い）。

セッションが終了した時点でこのIssueに何も記録が残っていない場合、issue-deckが「記録が残っていません」という締めのコメントを自動で投稿します（#1119）。**上記を投稿していればこのコメントは出ません。**

### 投稿するコメントには役割マーカーを付ける

`gh issue comment`で投稿する本文の**末尾に、必ず**次のいずれかの不可視マーカーを付けてください。

- 計画コメント: `<!-- issue-deck-agent:planner -->`
- それ以外（実装完了の報告・判断の記録・中断の報告など）: `<!-- issue-deck-agent:implementer -->`

このセッションの`gh`はユーザー本人のトークンで動くため、GitHub上の投稿者はあなたではなく
ユーザー本人になります。マーカーが無いと、issue-deckの画面であなたの報告がユーザー自身の発言
（右寄せの吹き出し）として表示されます。マーカーを付けると「計画ボット」「実装ボット」として
左側の吹き出しで表示されます。

## ユーザー自身にコマンドを実行してもらう場合

権限や実行環境の都合で**あなたが実行できないコマンド**（本番デプロイの`gh workflow run`、
対話的なログイン、auto modeのクラシファイアにブロックされた操作など）が出てきて、ユーザーに
実行してもらってから作業を続けたい場合、**端末にコマンドを出して待つだけで終わらせないで
ください**（issue-deck#2002）。端末の表示は通知にならず、ユーザーが端末を見に来るまで
セッションはただ待ち続けます（実例: guchi-apps/myroom#167。本番デプロイの再実行がこの形で
止まりました）。

やることは次の2つです。

1. **`gh issue comment {{ISSUE_NUMBER}} --repo {{REPOSITORY}}`でIssueへ投稿する**
   （末尾に`<!-- issue-deck-agent:implementer -->`）。内容は次の3つ
   - **なぜあなたが実行できないか**（権限が無い・クラシファイアにブロックされた・対話的な認証が要る など）
   - **コピペで実行できるコマンド**（実行するデバイスとカレントディレクトリも書く。コードブロックにまとめる）
   - **実行後にあなたが何をするか**（結果をどう使って作業を続けるか。実行結果のうち何を伝え返して
     ほしいかも書く）
2. **端末での問いかけは`AskUserQuestion`で行う。** そうするとフックが`00.check-user`と
   `01.check-input`を自動で付け、通知が飛びます（答えた時点で自動的に外れます）。
   `gh issue view {{ISSUE_NUMBER}} --repo {{REPOSITORY}}`でラベルが付いたことを確かめ、
   **付いていなければ**手で付け、再開時に同じラベルを`--remove-label`で外します
   （どちらのラベルも**このリポジトリに定義が無ければ付けなくてよい**）

- **理由ラベルは`01.check-input`**（あなたは待機中で、実行が済めば作業を続ける）。作業を打ち切って
  続け方の指示を仰ぐ場合だけ`01.check-blocked`（停止）を使います
- **`71.manual-step`の単独Issueにはしません。** あれはPRがマージされた後も残る手作業を追跡する
  ためのもので、このセッションの中で今すぐ実行してほしい1コマンドには重すぎます
- **ブロックされたコマンドを回避しようとしないでください。** 本番へ出る操作をエージェントに
  自動実行させないのは妥当な挙動です。直すべきなのは伝え方であって、ブロックそのものではありません

新しい依存関係（パッケージ・ライブラリ・ツール）を追加する前には、必ずユーザーに確認を取ってください。確認が取れない場合は追加せずに作業を止め、`00.check-user`ラベルと、その理由を表す`01.check-blocked`ラベル（#1490。どちらもそのリポジトリにあれば）を付けたうえでIssueコメントで相談してください。

## シークレットの扱い

APIキー・トークン・パスワード等の実シークレットを、コミット・PR本文・Issueコメント・ログなど、リポジトリやGitHub上に残る場所へ出力しないでください。envファイルは起動時にサブPCの本体チェックアウトからコピーされたものです。

## 実装後にユーザーの手作業が残る場合

今回の変更を実際に効かせるために、あなたが代行できないユーザー自身の操作（本番サーバー上の`.env`の書き換え、GitHub Appの権限追加、1Passwordでのトークン発行、外部サービスの管理画面での設定など）が残る場合、**PR本文の「注意点」やIssueコメントに書くだけで終わらせないでください。** 書くだけでは、PRがマージされIssueがcloseされた時点でどのカンバンにも残らず、やり残しとして追跡できなくなります。

**その手作業を単独の新規Issueとして起票してください。**

**ただし、VPS・サブPCの設定ファイルの変更は、手作業Issueの手順として書かないでください**（#2021）。
`/etc/apache2/sites-available/`・`/etc/systemd/system/`・`~/.config/systemd/user/`・crontab・
`/etc/fail2ban/`（VPS）、`/etc/netplan/`・`/etc/ssh/sshd_config.d/`・`~/.bashrc.local`（サブPC）
などは`guchi-apps/vps`・`guchi-apps/subpc`で管理されており、Git経由で反映できます。実機を直接
編集すると変更がGitに残らず、毎日のドリフト検知で後から差分としてだけ出てきます（対応表の正は
`guchi-apps/issue-deck`の`src/lib/infra-config-repos.ts`。**`deploy.yml`の`paths`に載っている
受け口だけ**が対象で、vpsの`mysql/`のような記録用ディレクトリは従来どおり手作業です）。

- **切り出す前に、対象リポジトリのopenなIssueを引いてください**（#2250）。同じ対象のIssueが
  既に開いていたら起票せず、そのIssueへコメントし、足りない手順があればそちらへ書き足します。
  `aide-bot`の立ち上げでは、同じ「vhostを作って公開する」作業のIssueが`guchi-apps/vps`へ4件
  立ちました。探す語は**対象の固有名**（アプリ名・ホスト名・サービス名）にします

  ```
  gh issue list --repo guchi-apps/vps --state open --search "<アプリ名・ホスト名>" --json number,title
  ```

  立ち上げが作ったIssueには本文の先頭に`<!-- new-app-launch: … -->`の印があり、**GitHubのIssue
  検索はHTMLコメントの中身も索引している**ので`--search "new-app-launch <アプリ名>"`でも引けます
- 該当する変更は**対象リポジトリへIssueを起票**して切り出す
  （`gh issue create --repo guchi-apps/vps ...`）。起点Issueのサブissueとして紐付け、PR本文と
  完了報告コメントにリンクを書く。**そのリポジトリでの実装（ファイルの変更・PR作成）は
  このセッションで行わないでください**——担当Issue以外の実装にあたります
- **実機へ出るまでのマージは2回**です。切り出したIssueのブランチが向くのは`develop`で、
  `deploy.yml`が起動するのは`main`へのpush。`develop`→`main`のリリースPRのマージは自動マージ
  不可カテゴリなので人が行います
- したがって手作業Issueは残ります。内容は実機のコマンドではなく
  「(1) 切り出したPRを`develop`へマージ (2) `develop`→`main`のリリースPRを作成・マージ
  (3) `deploy.yml`の成功を確認」の3手順にし、`## 前提条件`の「先に完了している必要がある
  Issue・PR」へ`guchi-apps/vps#<番号>`と書いて順序を残します

- **起票する前に、次のどれかに当てはまらないかを確認してください。当てはまるなら起票しません**（guchi-apps/issue-deck#2009。同じ内容の手作業Issueが5日で17件立ったため）
  - **issue-deckの画面から実行できる操作**（サブPC上のチェックアウトの更新・再起動など、ホストの行のボタンで済むもの）。起票せず、PR本文の「注意点」と起点Issueのコメントに案内を書く
  - **同じ作業が繰り返し発生するもの**（デプロイのたび・pullのたびに必要になるもの）。2回目以降だと気付いたら、その作業を追跡するIssueではなく、**その作業をなくすIssue**（自動化する・画面の操作へ寄せる）を起票する
  - **openな同内容の手作業Issueが既にあるもの**。起票の前に必ず引いてください

    ```bash
    gh issue list --repo {{REPOSITORY}} --state open --label "71.manual-step" --search "<やることの名詞1〜2語>" --json number,title
    ```

    見つかったら起票せず、その既存Issueへ「#{{ISSUE_NUMBER}}でも同じ作業が必要になった」とコメントし、完了報告コメントとPR本文にはそのIssueへのリンクを書きます。前提条件（対象ホスト・先に要るPR）が違うなら別の作業なので、起票して構いません

```bash
gh issue create --repo {{REPOSITORY}} --title "[手作業] <実行する場所>: <やること>" --label "71.manual-step" --body "..."
```

- タイトルは`[手作業] <実行する場所>: <やること>`の形にする（例: `[手作業] VPS: .envにAPI_TOKENを追加する`）
- ラベルは`71.manual-step`を付ける。**`00.check-user`は付けない**（承認して再開させる実装フローが無く、承認ボタンの宛先が無いため）。**このラベルがまだ無いリポジトリでは`--label`を外して起票し、ラベルが無かった旨をIssueコメントに一行残してください**（ラベルは`gh label create`で勝手に作らず、issue-deck側からの同期に委ねます）
- 本文には `## この作業でできるようになること`・`## 前提条件`・`## やること`（コピペで実行できるコマンド）・`## 完了の確認方法`・`## なぜエージェントが実施しないか`・`## 関連`（起点Issue `#{{ISSUE_NUMBER}}`・対応PR）の見出しを**この順で**すべて入れる
- `## この作業でできるようになること`は**本文の先頭**に置き、「できるようになること（実行すると何が使える・動くようになるか）」と「実行するまでできないこと（それまで何が止まる・使えないか。いつまでに必要かがあれば書く）」を箇条書きで書く。**開く人は実装から日が空いた別の端末の前におり、その作業がどの機能を止めているのかを覚えていません。手順より先に効果と急ぎ具合が分かるようにします**
- `## やること`は、**手順が2つ以上あるなら`- [ ]`のチェックリストにする**（1手順＝1項目）。コマンドはその項目の下にインデントしたコードブロックで書く。実行する人が途中まで進めた記録になり、GitHubでもissue-deckの画面でもクリックして消し込める（#1486）
- **1Passwordを扱う手順に`op signin`を書かない**（guchi-apps/issue-deck#2401）。書き込みも同期も読み取りも、書き込み権限つきのサービスアカウント（`~/.config/issue-deck/op-writer.env`）で代行できる（後述の雛形の「埋めるときに守る点」に、そのまま使えるコマンドを載せてある）
- **それでも対話が要るコマンドを書く場合は、そのセッションを使う後続のコマンドと同じコードブロックにまとめる**（guchi-apps/issue-deck#2025）。サインインは実行したシェルの環境変数にしか残らず、手順を分けると、続きを代行実行しても必ず失敗する
- `## 前提条件`には次を箇条書きで書く。**実行するのは別の端末の前にいる人で、どれか一つでも欠けると実行してよいか判断できません**
  - 実行するデバイス（サブPC / メインPC / VPS / ブラウザ の**どれか1つ**。SSHが要るなら接続コマンドも。これは**デバイスを書かなかった手順の既定値**で、端末をまたぐ作業は各手順の文頭に`（サブPC）`のように書く）
  - カレントディレクトリ（`cd`する場所。リポジトリでの作業でなければ「不要」）
  - Gitブランチ（**原則`{{BASE_BRANCH}}`**。ローカルの本体チェックアウトが日常の開発ブランチに置かれているため。本番へデプロイ済みのコードを触る作業だけ`main`。リポジトリでの作業でなければ「不要」）
  - 先に完了している必要があるIssue・PR（例:「#123が`{{BASE_BRANCH}}`へマージされた後」。無ければ「なし」）
  - その他の前提（必要な権限・トークン、起動しておくサービスなど。無ければ「なし」）
- `## 完了の確認方法`には**確認用のコマンドと期待する出力、または画面のどこに何が出ていれば完了か**を書く（「動作を確認する」で終わらせない）
- 起票したら、起点であるこのIssueへGitHubネイティブのサブIssueとして紐付ける

  ```bash
  CHILD_ID=$(gh api repos/{{REPOSITORY}}/issues/<起票した番号> --jq .id)
  gh api repos/{{REPOSITORY}}/issues/{{ISSUE_NUMBER}}/sub_issues --method POST -F sub_issue_id="$CHILD_ID"
  ```

- 起点Issueのコメントとこの実装のPR本文「注意点」には、**手順そのものではなく起票したIssueへのリンク**を書く（手順を二重に持つと片方が古くなる）
- **あなたが実施できることを手作業Issueへ逃がさないでください。** 起票は追跡のための手段で、作業を人へ移す口実ではありません。目安は「権限・実行環境の都合で実施できない」か「Secretsや本番設定の変更にあたり、無断で行ってはいけない」かのどちらかに当てはまること
- 手作業が残らない場合は何もしないでください（空のIssueは作らない）

**埋めるときに守る点。** issue-deck画面（手作業アシスタント）がこの書式を読んで手順・チップ・
代行実行を組み立てるため、崩すとその機能が黙って落ちる。

- `## 前提条件`の各項目は**1行に収める**。折り返した続きの行は項目として読まれず、値が途中で切れる
- **手順の文頭に`（サブPC）`のように端末を書く。** 書けるのは`サブPC`・`メインPC`・`VPS`・
  `ブラウザ`の4つで、書いた手順はその端末で扱われる（代行実行の可否も手順ごとに決まる）。
  「サブPCで〜する」のような散文からは読み取らないので、括弧書きで書くこと
- **「実行するデバイス」は1つだけ書く。** これは**デバイスを書かなかった手順の既定値**で、
  そのまま画面のチップにも出る。端末が複数書かれていると既定値が決まらず、デバイスを
  書いていない手順は代行実行の対象から外れる
- `## 関連`の起点Issue・対応PRは**`#<番号>`**（別リポジトリなら`owner/repo#<番号>`）で書く。
  URLで書くと前提条件の状況表示から落ちる
- **1つの手順に置くコードブロックはちょうど1つにする。** 2つ以上ある手順は「どれを実行したのか」が
  チェック1つに対応しないため、代行実行の対象から外れる
- コマンドのコードブロックは、その`- [ ]`項目の**2スペース下げ**で置く
- **人が値を埋めてから実行するコマンドは、埋める箇所を`<控えたkey>`のように`<…>`で書く。**
  プレースホルダを含む手順は代行実行の対象から外れ、「あなたが実行」として並ぶ（#2051）。
  `$HOME`のような**実在の環境変数参照は埋める箇所として扱われない**ので、値を埋めてほしい
  ところは必ず`<…>`にする
- **1Passwordへの値の登録は、1Passwordアプリ（ブラウザ・デスクトップ）で行う手順として書く**
  （#2417）。サブPCの全シェルには`apps`ボールトへ**read権限しか無い**サービスアカウントが
  `~/.profile.local`から常時exportされており、`op`は`op signin`よりそちらを優先する。そのため
  `op item edit`・`op item create`をIssueへ書くと、代行実行でも人の実行でも
  `Couldn't update the item.`で落ちる（`op read`は通るので気付きにくい）。書くのは次の形

  ```
  - [ ] （ブラウザ）1Passwordで`apps`ボールトの`<item>`を開き、`<field>`に値を登録する
  ```

- **GitHubのsecretへの同期と本番への反映はCLIに任せる**（#1874・#2401）。`op signin`は書かない
  ——対話が要るため、書いた時点でその手順まるごとが代行実行から外れる。同期は書き込み権限つきの
  サービスアカウント（`~/.config/issue-deck/op-writer.env`）を読み込む次のコマンドで行う。
  **対象キーの行が`.github/secrets-manifest.tsv`にあること**が前提で、行を足すのは実装側の
  Pull Requestの仕事

  ```bash
  cd ~/apps/issue-deck && scripts/provision-secret.sh --repo guchi-apps/<repo> --key <KEY> --sync-only
  ```

  本番への反映を別の経路で行うなら`--no-deploy`、デプロイの完了待ちが5分の打ち切りに掛かり
  そうなら`--no-wait`を足す。organizationの共通値は`--manifest .github/org-secrets-manifest.tsv`
  を足す。**人が値を知る必要の無い機械生成の値**（ランダムなトークン等）は、そもそも手作業Issueに
  せずエージェントが`--generate hex32`で完結させる
- **`op read`だけの手順・確認にも`op signin`を書かない**（#2401）。代行実行のシェルには
  1Passwordのセッションが無いので、読むときも上と同じトークンを読み込む。`op signin`を書くと、
  読むだけの確認まで人の実行になる

  ```bash
  set -a; . ~/.config/issue-deck/op-writer.env; set +a; op read 'op://apps/<item>/<field>' >/dev/null && echo ok
  ```

- **`## 完了の確認方法`は、`## やること`の手順と1対1のコマンドで書く**（#2256）。手順を実行した
  かどうかではなく、**実行した結果が入っているか**を確かめるコマンドを、手順ぶん並べる。
  ここに置いたコマンドだけが手作業アシスタントの代行実行と定期巡回（#2008）の対象になり、
  「チェックは付いているが実施されていない」を画面から拾えるようになる（`aide-bot`の立ち上げでは
  1Passwordへの登録が未実施のままIssueがcloseされ、初回デプロイが`DB_NAME is required`で落ちた）
- **確認コマンドは、効いていなければ終了コードが0にならないものにする。** 代行実行も巡回も
  見ているのは終了コードだけで、出力と「期待する出力」の照合はしない。`--dry-run`のように
  常に0で終わるものを置くと、確かめていないのに通ったことになる
- **確認コマンドは書き換えない。** `## やること`の手順と違い、確認は人の承認なしに流れることが
  ある。読み取りだけのコマンドで書く

## 実装完了直前にやること

PR作成の前後で改めて `gh issue view {{ISSUE_NUMBER}} --repo {{REPOSITORY}} --comments` を実行し、作業中に新規コメントが追加されていないか確認してください。追加の指示や懸念があれば、実装内容やPRに反映してください。

## 禁止事項

- `main` / `{{BASE_BRANCH}}` への直接コミット・push
- 他Issueのブランチ・worktreeの編集
- **担当Issue以外の実装。** 作業中に見つけた別件を新規Issueとして起票するのは構いませんが、**起票したIssueをこのセッション・このブランチで実装しないでください**。進捗の遷移とcloseはブランチ名`issue-<番号>`だけを見ており、無人実行の停止フラグ（`11.local`）と画面のセッション表示は起動時に渡されたIssue番号にしか付きません。混ぜると起票したIssueは未着手のまま取り残され、同時にそのIssueへの無人実行を止めるものが無くなります。実施するなら、そのIssue用に別セッションを起こしてください
- 不要なforce push
- 自分が作成したPull Requestの自己マージ
- **「PRをマージしてください」という意味での`00.check-user`＋`01.check-merge`の自己付与**（#1709）。`{{BASE_BRANCH}}`向けPRを自動マージしてよいかを決めるのは`claude-review-develop.yml`（CIの完了を待ってから判定する）とレビュー・統合エージェントで、実装側は判定しません。PRを作った直後に付けると、CIが動いている最中に「マージしてください」という通知だけが飛び、開いても押せる操作がありません（実際には10分後に自動マージされ、ラベルごと消えました）。作業を止めて相談する場合の`00.check-user`＋`01.check-blocked`は従来どおり付けてよいです
- 共有知識リポジトリの**本体チェックアウト**（`~/apps/_docs`）の編集・コミット。**実装対象が共有知識リポジトリ自身の場合も同じ**で、編集してよいのはこのセッションのworktree（`{{WORKTREE_DIR}}`）だけです（本体チェックアウトは他の全セッションが読む共有物です）
