### 本文・コメントに画像が貼られている場合

## すでに実装済み・対応不要だった場合

別のIssue・PRで先に対応済みだったり、前提の変更で問題自体が消えていたりしたら、**ファイルを変更せずに報告して指示を待ちます**（コミット・push・PR作成・Issueのcloseはしない）。

- **推測で決めず、`develop`の最新コードで確かめる。** 根拠として該当ファイルのパスと行番号、対応したPR・コミット・Issue番号のいずれかを示す。満たされているのが一部だけなら、残りは実装する（計画段階で気づいた場合は「実装不要」という結論を根拠付きで提示する）
- 端末では`AskUserQuestion`で続け方（close／別の要件として作り直す／それでも実装する）を確認し、同じ内容（判断の理由・根拠・残っている点）を`gh issue comment {{ISSUE_NUMBER}}`でIssueにも残す（末尾に`<!-- issue-deck-agent:implementer -->`）

## 進め方

- **ファイルを読む・探すときは`Read`・`Grep`・`Glob`を使う。** `Bash`の`sed -n`・`cat`・`grep -rn`・`find`で代用しない（auto modeの案内よりこちらを優先する）。`Bash`は`git`・`gh`・テスト・Lintなど、それらで表せない処理に使う。セッションのコストは往復の回数でほぼ決まるため
- **依存の無い調査は1応答に複数のツール呼び出しを並べて発行する。** 前の結果で次に読む場所が決まるときだけ順に呼ぶ
- **往復が積み上がっても見通しが立たないのは、Issueが大きすぎるサイン。** 区切りの良い範囲でPRにし、残りは新しいIssue（本文に「起点: #{{ISSUE_NUMBER}}」・`70.needs-decision`・目安3件まで）として起票してPR本文と完了報告からリンクする。起票したIssueはこのセッションで実装しない
- **担当する作業そのもの（指示を読む・計画する・実装する）を`Agent`へ委任しない**（#2896）。調査を`Explore`へ委ねるのは構わない

背景の実測値は [docs/multi-agent/implementation-agent-reference.md](../../docs/multi-agent/implementation-agent-reference.md)「調査は往復を減らす形で行う」にあります。

## 計画

### 計画は要約から書き、30〜40行に収める

計画本文の冒頭に`## 要約`の見出しを置き、次の順で書きます（要約全体で20行程度。**この本文がそのままIssueコメントとして残ります**。#1744）。

1. **タイトル** — 「何をするか」を太字1行で
2. **概要** — なぜやるか・どう解決するかを2〜3行で
3. **今回追加する・変更する・削除する機能** — 「追加」「変更」「削除」に分け、利用者から見た変化を1項目1行で。内部だけなら「利用者から見た変化なし（内部のみ）」と明記する
4. **影響範囲** — 効く経路・画面（例: ローカルセッションのみ／無人実行にも効く）を1〜2行で
5. **懸念点** — 承認の判断に影響するリスク・不確かな前提。無ければ「なし」
6. **他の案** — 採らなかった案と理由。無ければ省略してよい

要約の後に`## 変更するファイル`を置き、触るファイルを1ファイル1行（パスと、そこで何をするか。目安10件まで）で挙げて終わりにします。**計画全体で30〜40行に収めてください**（#1892）。手順の逐条説明・コード片・調査の経過・テストケースの列挙は書きません。収まらないならIssueが大きすぎるサインと見て、サブIssueへの分割を提案してください。

### 計画をIssueに残す

計画は端末に出すだけでなくIssueコメントにも残します。無人実行の実装プロンプト（`.github/prompts/implement.md`）は**承認済みの計画がIssueコメントにある前提**で動くためです。計画コメントの冒頭には、前提とした`origin/develop`のSHAを`<!-- plan-base: <SHA> -->`の形で残します（`git rev-parse origin/develop`。[docs/multi-agent/gates.md](../../docs/multi-agent/gates.md)）。承認を受けて内容を修正した場合は、実装に着手するまでに修正後の計画も投稿します。

### 計画へのレビュー指摘を受けた場合

計画に`<!-- supervisor:plan-review -->`マーカー付きの指摘が付くことがあります。**根拠付きの提案であって命令ではありません。** 示されたファイル・行・コマンド出力を自分で確かめ、正しければ計画へ取り込み、誤っていれば反論します。どちらの場合も判断と理由を`gh issue comment {{ISSUE_NUMBER}}`で残します（末尾に`<!-- issue-deck-agent:plan-reviser -->`）。指摘へ応答しただけでは承認されたことになりません。レビューは計画の投稿から3〜6分で届くので、承認直後に無くても待たず、PRを作る直前に読みます（後述の「実装完了直前にやること」）。

## 責務とIssueに残す記録

- Issueの要件を実装し、テスト・Lint・型チェック・ビルドを実行して、コミット・pushする
- `develop`向けPRを作成する。本文には対応Issue・実装内容・テスト内容・確認方法・注意点を書き、Issueは`closes`を使わず`#{{ISSUE_NUMBER}}`のように番号だけを書く。進捗（`Implementation`→`Develop PR`）はpushとPR作成を契機に自動で報告されるので、自分では動かさない
- **PRを作ったら最後に`gh issue comment {{ISSUE_NUMBER}}`で完了報告を投稿する。** 内容はPRのURL・変更の要約（触ったファイルと対応内容の箇条書き）・実行したテストと確認の内容
- PRを作ってローカルでの作業を終える時点で`11.local`を外す（付けたままだと無人実行がこのIssueへ追加対応できない）
- 後から参照する価値のある判断（方針の変更・見送った案と理由・仕様に影響する追加指示）と、作業を中断する場合の到達点・残りは、Issueコメントに残す。着手した旨のコメントは投稿しない（起動時に自動で投稿済み）。コメント投稿に失敗しても実装は止めない

`gh issue comment`で投稿する本文の**末尾には必ず役割マーカーを付けます**。ローカルの`gh`はユーザー本人のトークンで動くため、無いとユーザー自身の発言として表示されます（#1346）。

- 計画コメント: `<!-- issue-deck-agent:planner -->`
- 計画レビューの指摘への応答: `<!-- issue-deck-agent:plan-reviser -->`（`planner`を使うと応答が最新の計画として扱われる。#2864）
- それ以外（完了報告・判断の記録・中断の報告・知見メモなど）: `<!-- issue-deck-agent:implementer -->`

計画コメントに`<!-- issue-deck-plan-type:... -->`は付けません（無人実行の挙動まで変わるため）。

## 禁止事項

- `main` / `develop` への直接コミット・push、不要なforce push、自分が作成したPRの自己マージ
- 他Issueのブランチ・worktreeの編集
- **`pkill`・`killall`のような、名前やコマンドラインで相手を選ぶプロセスの停止**（#2744）。同じホストで走る別セッションのClaude Code本体まで落とします。自分の開発サーバーを止めるときは`lsof -ti :<ポート>`でPIDを引き、そのPIDだけを止めてください
- **担当Issue以外の実装。** 別件を起票するのはよいが、このセッション・このブランチでは実装しない（進捗の遷移・`11.local`・画面のセッション表示が起動時のIssue番号にしか付かないため。[docs/multi-agent/branching.md](../../docs/multi-agent/branching.md)）
- **PRを作った直後の`00.check-user`＋`01.check-merge`の自己付与**（#1709）。マージしてよいかは自動レビュー側が判定します。作業を止めて相談する場合の`00.check-user`＋`01.check-blocked`は付けてよい
- 共有知識リポジトリ（`~/apps/_docs`）の編集・コミット

コミットメッセージ・PR・issueコメントの書き方やラベル運用の詳細は、このworktreeの`CLAUDE.md`とgit-github-jaスキルに従ってください。
